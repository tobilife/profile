- 승인은 새로 만들지 않고 기존 결재선에 얹되, 모든 호출에 묻지 않도록 행위의 위험 등급으로 나눕니다. 승인 과부하도 통제 실패입니다.
- 감사 로그는 지시한 사람, 실행한 에이전트, 모델, 승인자, 실제 부작용을 한 줄로 이을 수 있어야 합니다.
- 배포는 섀도, 읽기 전용, 승인부 쓰기, 범위 확장 순서로 넓히고, 각 단계의 통과 기준과 멈추는 방법을 먼저 만들어 둡니다.

"에이전트에게 운영 계정만 하나 주면 배치 장애 분석부터 재처리까지 알아서 해준다"는 기대가 있습니다.

기술적으로는 가능합니다. 문제는 가능하다는 것과 맡겨도 된다는 것 사이의 거리입니다.

**레거시 시스템 옆에 에이전트를 둘 때 어려운 것은 연결이 아니라, 에이전트의 행위를 기존 통제 체계가 이해할 수 있는 단위로 쪼개는 일입니다.**

근거로 삼을 공개 자료는 이미 있습니다. NIST의 AI RMF는 자발적으로 쓰는 프레임워크이고, 2024년 7월 26일에는 생성형 AI의 고유 위험을 식별하고 관리 조치를 제안하는 프로파일(NIST AI 600-1)이 나왔습니다 [\[NIST: AI Risk Management Framework\]](https://www.nist.gov/itl/ai-risk-management-framework). 국내에서는 금융위원회가 2026년 6월 18일 「금융분야 인공지능 가이드라인」 개정안을 발표했고, 가이드라인은 6월 22일부터 시행됐습니다 [\[금융위원회: 금융권 AX 현장 간담회 보도자료\]](https://fsc.go.kr/po010101/87142). 금융보안원은 10월 8일 에이전트 전용 보안 평가기준을 내놓았습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

이 글의 체크리스트는 그 자료들을 읽고 정리한 제 의견입니다. 특정 회사의 사례가 아니며, 규제 해석을 대신하지도 않습니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사의 야간 정산 배치가 실패하면, 로그를 읽고 원인을 정리해 아침 출근한 담당자에게 보고하는 에이전트를 만든다고 해봅시다. 배치는 Java로 짠 잡이 Oracle 원장 테이블을 스텝 단위로 갱신하는 구조입니다.

로그 테이블을 봐야 하니 운영자의 DB 계정을 그대로 줍니다. 어느 날 에이전트는 원인을 찾은 뒤 "실패한 스텝을 재실행하면 해결됩니다"라고 판단하고, 실제로 재실행합니다.

그 스텝은 이미 절반쯤 처리된 상태였고, 일부 건이 두 번 반영됩니다.

다음 날 감사 로그에는 운영자 본인의 계정으로 실행된 SQL만 남아 있습니다. 운영자는 그 시각에 자고 있었습니다.

시스템 설계 용어로 짚으면 네 가지가 빠졌습니다. 분석과 실행의 권한이 분리되지 않았고, 재실행이 멱등하지 않았으며, 승인 지점이 없었고, 행위 주체가 로그에서 사람과 구별되지 않았습니다.

모델이 틀린 판단을 한 것이 아닐 수도 있습니다. 판단이 옳았더라도 이 구조에서는 같은 일이 생깁니다.

이 장면은 지어낸 것이지만, 감독 당국이 걱정하는 유형과 겹칩니다. 금융위원회 가이드라인은 프런티어 모델의 시스템 카드에 공개된 이상 행동 사례를 표로 정리해 두었는데, 그중에는 DB 오류 확인만 요청했는데 확인 후 임의로 수정한 경우가 들어 있습니다 [\[금융위원회: 금융분야 인공지능 가이드라인\]](https://fsc.go.kr/comm/getFile?fileNo=6&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142). 가이드라인은 이런 상황에 대비해서도 고위험 시스템이 최종 의사결정을 하지 않도록 설계하는 것이 중요하다고 적습니다.

이제 이 배치 분석 에이전트를 네 가지 축으로 다시 설계해 보겠습니다.

## 1. 기본값은 읽기 전용이고, 쓰기는 따로 뚫습니다

### 먼저 닿는 자원의 목록을 만듭니다

NIST AI RMF의 Core는 govern, map, measure, manage 네 기능으로 이루어져 있고, 거버넌스는 나머지 셋에 걸쳐 스며드는 기능으로 설계되어 있습니다. 같은 문서는 govern의 결과를 갖춘 뒤 대부분의 사용자가 map에서 시작해 measure나 manage로 이어 간다고 설명합니다 [\[NIST AIRC: AI RMF Core\]](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/).

하네스 관점에서 map에 해당하는 첫 작업은 에이전트가 닿는 자원의 목록을 만드는 것이라고 봅니다. 그리고 그 목록의 기본값을 읽기 전용으로 둡니다.

배치 분석 에이전트라면 목록은 이런 모양이 됩니다.

| 자원 | 기본값 | 쓰기를 열 때의 조건 |
| --- | --- | --- |
| 운영 DB(원장, 로그 테이블) | 전용 계정, 조회용 뷰 또는 복제본만 | 직접 DML 금지. 기존 애플리케이션 API나 프로시저를 경유 |
| 배치 스케줄러 | 실행 이력과 스텝별 로그 조회 | 재실행은 멱등 키가 있는 잡만, 승인 후 |
| 소스 저장소 | 읽기, 브랜치 작성 | 병합은 사람의 리뷰를 거침 |
| 대외 채널(메일, 문자, 대외계) | 초안 작성까지 | 발송은 승인 후, 수신자 범위 고정 |
| 개인(신용)정보 | 마스킹된 값 | 원문은 업무상 필요한 건만, 조회 기록을 남김 |
| 운영 서버 셸 | 없음 | 원칙적으로 열지 않음. 필요한 조회는 전용 도구로 감쌈 |

표의 행은 제가 든 예시입니다. 핵심은 칸을 채우는 순서입니다. 쓰기 칸은 읽기 칸이 운영에서 문제없이 돌아간 뒤에 채웁니다.

### 쓰기를 기존 애플리케이션 API로 돌리는 이유

수십 년간 쌓인 업무 규칙과 검증 로직은 대개 애플리케이션 코드와 저장 프로시저 안에 있습니다. 테이블을 직접 고치면 그것을 전부 우회하게 됩니다.

정산 배치를 예로 들면, 재처리 화면에는 보통 "이미 처리된 건은 건너뛴다", "마감된 기간은 막는다" 같은 검사가 붙어 있습니다. 에이전트가 같은 효과를 SQL로 직접 내면, 그 검사는 한 번도 실행되지 않습니다.

그래서 에이전트에게 주는 쓰기 도구는 기존 API를 감싸는 얇은 어댑터로 만드는 편이 좋습니다.

```text
// 예시(Java): 기존 재처리 서비스를 감싸는 에이전트용 도구 (특정 프레임워크의 API가 아닙니다)
public RerunResult rerunStep(AgentContext ctx, String jobId, int stepNo) {
    policy.requireApproval(ctx, "batch.rerun_step", jobId, stepNo); // 승인 없으면 예외
    RerunPlan plan = settlementService.planRerun(jobId, stepNo);     // 기존 검증 로직 그대로
    if (!plan.isIdempotent()) {
        throw new ToolRefused("멱등 키가 없는 스텝은 에이전트가 재실행할 수 없습니다");
    }
    return settlementService.execute(plan, ctx.agentIdentity());      // 실행 주체를 에이전트로 기록
}
```

에이전트는 `jobId`와 `stepNo`만 고릅니다. 재실행이 안전한지는 기존 서비스가 판정하고, 판정할 수 없는 스텝은 도구 수준에서 거부됩니다.

### 금융보안원 평가기준이 보는 지점

금융보안원의 「금융분야 AI 에이전트 보안 평가기준」은 6개 분야 17개 점검 항목으로 되어 있습니다. 이 중 목표 무결성, 연쇄적 실패 대비, 취약한 도구 사용 금지, 도구 권한 제어, 샌드박스 환경 구축, 에이전트 간 통신보안, 인적 승인체계 구축, 인적 개입 과부하 방지는 기존 항목의 확장이 아니라 에이전트 도입으로 새로 생기는 위협에 대한 항목으로 표시되어 있습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

같은 발표는 에이전트가 가진 자율성과 실행력이 기존 위협을 실제 행위로 옮긴다고 설명하면서, "시스템 성능 최적화"라는 목표를 받은 에이전트가 가용성을 위해 백신을 스스로 중단하는 경우를 예로 듭니다. 배치 분석 에이전트가 "배치를 성공시켜라"라는 목표를 받았다면, 실패한 검증 스텝을 건너뛰는 것도 같은 유형이 될 수 있습니다.

17개 항목을 하네스가 맡을 부분으로 옮겨 보면 대략 이렇습니다.

| 평가기준 항목 | 하네스에서 구현할 자리 |
| --- | --- |
| 도구 권한 제어, 취약한 도구 사용 금지 | 도구 목록과 도구별 범위를 설정으로 고정, 승인되지 않은 도구 등록 금지 |
| 샌드박스 환경 구축 | 명령 실행은 격리 환경에서만, 운영 서버 셸 도구 없음 |
| 목표 무결성, 연쇄적 실패 대비 | 작업 범위를 시작 시점에 고정, 범위 밖 도구 호출 거부, 실패 시 중단 |
| 메모리 오염 방지, 메모리 격리 | 세션 간 기억 공유 금지, 작업 종료 시 상태 삭제 |
| 인적 승인체계, 인적 개입 과부하 방지 | 위험 등급별 승인 게이트, 승인 건수 상한과 모니터링 |
| 자원 고갈 방지, 킬스위치 구현 | 호출 횟수와 비용 상한, 에이전트 신원 단위 즉시 정지 |
| 로깅 및 감사체계 구축 | 도구 호출 단위 감사 레코드 |

오른쪽 열은 제 해석입니다. 항목 이름은 평가기준 발표문의 표에서 가져왔습니다.

### 실패 모드와 비용

읽기 전용도 공짜가 아닙니다.

복제본을 쓰면 지연이 생깁니다. 배치가 실패한 직후의 상태를 봐야 하는데 복제본이 몇 분 늦다면, 에이전트는 실패 이전의 상태를 보고 틀린 원인을 보고할 수 있습니다. 조회 시점과 복제 시점을 보고서에 함께 적게 하는 편이 안전합니다.

조회용 뷰를 너무 넓게 만들면 읽기 전용이라도 정보 노출 문제가 생깁니다. 로그 분석에 고객 이름과 주민번호가 필요한 경우는 드뭅니다. 뷰 단계에서 빼 두면 뒤의 마스킹 부담도 줄어듭니다.

반대로 이 모든 것이 과한 경우도 있습니다. 개인정보가 없는 개발 환경의 빌드 로그만 읽는 에이전트라면, 전용 계정과 조회 권한 정도로 충분하다고 봅니다.

## 2. 승인은 기존 결재선에 얹고, 위험 등급으로 나눕니다

### 보조수단성 원칙을 코드로 옮기면

개정 가이드라인의 7대 원칙 가운데 하네스 설계와 가장 직접 닿는 것은 보조수단성 원칙입니다. 현 단계에서 인공지능은 업무의 보조수단이며 최종 의사결정과 그에 따른 책임은 임직원이 수행한다는 내용입니다 [\[금융위원회: 금융권 AX 현장 간담회 보도자료\]](https://fsc.go.kr/po010101/87142).

가이드라인 본문은 이를 구체화하면서 사람이 개입하는 방식을 네 가지로 나눈 표를 싣고 있습니다. 사람이 승인해야만 결정이 나는 Human-in-the-Loop, 인공지능이 결정하되 사람이 실시간으로 감독하며 언제든 개입하는 Human-on-the-Loop, 운영 후 사람이 사후에 결과를 분석하는 Human-over-the-Loop, 사람의 개입 없이 자율적으로 결정하는 Human-out-of-the-Loop입니다 [\[금융위원회: 금융분야 인공지능 가이드라인\]](https://fsc.go.kr/comm/getFile?fileNo=6&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142). 고위험 인공지능은 사람의 의사결정을 보조하는 용도로만 쓰도록, 즉 시스템이 최종 결정을 하지 않도록 설계하라는 것이 같은 절의 요구입니다.

배치 분석 에이전트의 행위를 이 네 가지에 배치해 보면 이렇습니다.

| 행위 | 개입 방식 | 이유 |
| --- | --- | --- |
| 로그 조회, 원인 분석 보고서 작성 | Human-over-the-Loop | 되돌릴 것이 없고, 보고서를 사람이 읽음 |
| 재처리 계획 초안 작성 | Human-on-the-Loop | 계획만 만들고 실행하지 않음, 담당자 화면에 실시간 표시 |
| 멱등 스텝 재실행 | Human-in-the-Loop | 원장에 반영됨, 건마다 승인 |
| 비멱등 스텝 재실행, 원장 직접 보정 | 에이전트 도구에서 제외 | 사람이 기존 절차로만 수행 |

표의 배치는 제 예시입니다.

### 위험 등급은 행위 단위로 매깁니다

가이드라인은 위험에 따른 차등을 인정합니다. 뉴스 요약, 번역, 코드 생성처럼 고객에게 직접 영향을 주지 않는 저위험 서비스는 승인 절차를 간소화할 수 있고, 고위험 서비스에는 최고 의사결정기구의 사전 승인과 사후 검증, 제3자 평가, 운영 단계의 모니터링 강화 같은 추가 통제를 적용한다고 적고 있습니다 [\[금융위원회: 금융분야 인공지능 가이드라인\]](https://fsc.go.kr/comm/getFile?fileNo=6&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142).

등급을 정하는 방법도 예시로 나와 있습니다. 원칙별 평가 항목에 배점을 두고 경감 조치 후 남은 위험 점수를 합산해, 예컨대 25점 미만은 저위험, 25점 이상 50점 미만은 중위험, 50점 이상은 고위험으로 나누고, 75점 이상이면 출시 여부를 다시 심의하는 식입니다.

가이드라인의 등급은 서비스 단위입니다. 저는 하네스에서는 한 단계 더 내려가 행위 단위로 등급을 매기는 편이 실용적이라고 봅니다. 같은 배치 분석 서비스 안에서도 로그 조회와 재실행의 위험은 전혀 다르기 때문입니다.

```yaml
# 예시: 행위 단위 위험 등급과 승인 규칙 (특정 제품의 설정 문법이 아닙니다)
service_risk: medium              # 서비스 단위 등급은 내부 위험평가 결과를 따름
actions:
  log.query:            { risk: low,    approval: none }
  report.draft:         { risk: low,    approval: none }
  batch.plan_rerun:     { risk: low,    approval: none, visible_to: [on_call] }
  batch.rerun_step:     { risk: high,   approval: { line: [on_call_lead], quorum: 1 } }
  ledger.adjust:        { risk: banned }   # 에이전트에게 노출하지 않음
approval_budget:
  max_requests_per_day: 20       # 넘으면 승인 대상 정의를 다시 검토
  escalate_if_rejected_rate_over: 0.3
```

`approval.line`은 새 결재선이 아니라 기존 당직 체계의 직책을 그대로 씁니다. 에이전트를 위해 별도의 승인자를 만들면, 그 사람이 시스템과 업무를 동시에 이해해야 하는 부담이 생깁니다.

### 승인 과부하는 통제 실패입니다

금융보안원 평가기준에는 인적 승인체계 구축과 나란히 인적 개입 과부하 방지가 별도 항목으로 들어 있습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

저는 이 두 항목이 한 쌍이라는 점이 중요하다고 봅니다. 하루에 승인 요청이 수백 건 오면 사람은 읽지 않고 누르게 되고, 그 순간 승인은 통제가 아니라 책임 전가 장치가 됩니다.

도구 공급자 쪽에서도 같은 관찰이 나옵니다. Anthropic은 Claude Code에서 계속 승인 버튼을 누르다 보면 사용자가 무엇을 승인하는지 주의 깊게 보지 않게 되는 승인 피로를 문제로 들고, 격리 경계를 먼저 만든 뒤 그 안에서는 묻지 않는 방식으로 사내 사용의 권한 확인 요청을 84% 줄였다고 밝혔습니다 [\[Anthropic: Beyond permission prompts\]](https://www.anthropic.com/engineering/claude-code-sandboxing).

그래서 승인이 필요한 행위를 좁게 정의하는 편이 안전합니다.

- 되돌릴 수 없는 쓰기(원장 반영, 대외 발송, 배치 재실행)
- 범위가 넓은 조회(다건 개인정보, 전체 계약 목록)
- 권한 경계를 넘는 요청(다른 업무 영역의 도구 호출)

위 YAML의 `approval_budget`은 이 원칙을 숫자로 감시하는 장치입니다. 하루 승인 요청이 정해 둔 수를 넘으면, 승인자를 늘리기보다 승인 대상의 정의가 너무 넓지 않은지부터 다시 봅니다.

### 승인 화면과 반려 사유

승인 화면에는 에이전트의 설명이 아니라 실제로 실행될 내용을 보여 줘야 합니다. 실행될 프로시저 이름, 인자, 영향받는 건수, 마지막으로 성공한 스텝과 그 시각 같은 것들입니다.

가이드라인의 준수 사례에도 비슷한 장치가 있습니다. 인공지능이 고위험으로 분류한 거래를 담당자가 정상으로 판단해 승인하려면 근거 사유를 시스템에 입력해야만 조치가 완료되도록 해, 권고를 채택하지 않을 때의 책임 소재를 분명히 했다는 예입니다 [\[금융위원회: 금융분야 인공지능 가이드라인\]](https://fsc.go.kr/comm/getFile?fileNo=6&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142).

에이전트 승인에도 그대로 옮길 수 있습니다. 승인과 반려 모두 사유를 남기게 하면, 반려 사유를 모아 도구 정의나 프롬프트를 고칠 근거로 쓸 수 있습니다.

### 이 방식이 맞지 않는 경우

행위 단위 등급과 승인 게이트는 행위가 잘 정의된 에이전트에 맞습니다. 셸이나 SQL을 자유롭게 쓰는 범용 에이전트에는 맞지 않습니다. 모든 명령이 잠재적으로 고위험이라 승인 대상을 좁힐 수 없기 때문입니다.

저는 기간계 옆에서는 범용 실행 도구를 주지 않는 것이 출발점이라고 봅니다. 필요한 조회와 실행을 이름 있는 도구로 하나씩 감싸는 비용이 들지만, 그 비용이 곧 승인 대상을 좁히는 비용입니다.

## 3. 감사 로그는 사람과 에이전트를 구분해 한 줄로 잇습니다

### "누가"가 둘로 갈라집니다

레거시 조직의 감사 추적은 대개 "누가, 언제, 무엇을"에 맞춰져 있습니다. 에이전트가 끼면 "누가"가 둘로 갈라집니다. 지시한 사람과 실행한 에이전트입니다. 배치 분석처럼 스케줄로 도는 에이전트라면 지시한 사람 자리에 서비스 계정이나 스케줄 이름이 들어갑니다.

OWASP의 에이전트용 Top 10은 이 지점을 신원 문제로 봅니다. 에이전트가 자기 자신의 관리되는 신원 없이 움직이면 귀속의 공백이 생기고 진짜 최소 권한을 강제할 수 없다는 것입니다. 완화책으로는 작업 단위로 범위를 좁힌 수명이 짧은 자격 증명, 에이전트별 신원, 비가역 행위에 대한 사람의 승인이 제시되어 있습니다 [\[OWASP: Top 10 for Agentic Applications 2026\]](https://genai.owasp.org/download/52117/).

### 감사 레코드에 들어갈 것

금융보안원 평가기준에도 로깅 및 감사체계 구축이 점검 항목으로 들어 있고, 레드티밍에서 실행 권한과 격리, 도구 실행과 승인 통제, 작업 범위와 결과 확인, 자율 실행 제한과 중단 여부를 중점 점검하겠다고 밝히고 있습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

이 네 가지에 답하려면 로그 한 건에 다음이 있어야 한다고 봅니다.

```json
{
  "_comment": "예시: 도구 호출 한 건의 감사 레코드",
  "trace_id": "run-20261014-0031",
  "session_scope": "JOB_SETTLE_D 실패 분석",
  "requested_by": "사번 또는 서비스 계정",
  "agent_identity": "agent-batch-analyst",
  "credential_id": "단기 자격 증명 식별자",
  "model": "응답을 만든 모델 식별자",
  "tool": "batch.rerun_step",
  "args_digest": "sha256:...",
  "risk_class": "high",
  "approval": { "required": true, "approver": "사번", "decision": "approved", "reason": "STEP 2까지 정상 확인", "decided_at": "2026-10-14T06:12:40+09:00" },
  "effect": { "target": "JOB_SETTLE_D / STEP 3", "rows_affected": 1284, "idempotency_key": "..." },
  "db_audit_ref": "기존 DB 감사 로그의 세션 식별자",
  "result": "committed"
}
```

필드마다 답하는 질문이 있습니다.

| 필드 | 답하는 질문 | 평가기준 중점 점검과의 연결 |
| --- | --- | --- |
| `agent_identity`, `credential_id` | 누가 실행했는가, 어떤 권한으로 | 실행 권한 및 격리 |
| `approval` | 누가 왜 허락했는가 | 도구 실행 및 승인 통제 |
| `session_scope`, `effect` | 무엇을 하기로 했고 실제로 무엇이 바뀌었는가 | 작업 범위 및 결과 확인 |
| `trace_id`, `result` | 언제 멈췄는가, 끝까지 갔는가 | 자율 실행 제한 및 중단 |

오른쪽 열의 연결은 제 해석입니다.

### 핵심은 effect와 대조 키입니다

모델이 무엇을 하려 했는지가 아니라 시스템에 실제로 무엇이 일어났는지를 남겨야, 기존 DB 감사 로그와 대조할 수 있습니다. `db_audit_ref`는 그 대조를 위한 키입니다. 에이전트용 어댑터가 DB 세션을 열 때 세션 정보에 `trace_id`를 실어 두면, DB 감사 로그 쪽에서도 같은 값을 찾을 수 있습니다.

가이드라인은 시스템 운영 과정에서 발생하는 로그와 승인·검토 기록을 사후 감사와 분쟁 해결을 위해 보존하라고 적고, 인적 개입의 결과도 설명 가능한 근거와 함께 사후 추적 가능한 로그로 보존하라고 요구합니다 [\[금융위원회: 금융분야 인공지능 가이드라인\]](https://fsc.go.kr/comm/getFile?fileNo=6&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142). 위 레코드의 `approval.reason`이 그 근거에 해당합니다.

### 개인정보는 컨텍스트에 들어가기 전에 다룹니다

평가기준의 17개 항목에는 메모리 격리와 데이터 유출 방지가 들어 있고, 발표문은 에이전트가 권한을 위임받아 세션이나 사용자 사이에서 정보를 유출하는 것을 추가 위협으로 적고 있습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

하네스에서는 마스킹을 도구 결과가 컨텍스트에 들어가기 전에 두는 편이 낫다고 봅니다. 컨텍스트에 한 번 들어간 값은 모델의 응답, 추적 데이터, 감사 로그, 다음 턴의 요약으로 흘러갑니다. 들어간 뒤에 걸러내려면 그 모든 출구를 따로 막아야 합니다.

```text
DB 조회 결과 ──> 어댑터: 컬럼 화이트리스트 + 패턴 마스킹 ──> tool_result ──> 모델 컨텍스트
                                                                  │
                                    감사 로그에는 args_digest와 effect만 (원문 행은 남기지 않음)
```

### 실패 모드와 비용

감사 로그의 가장 흔한 실패는 양입니다. 모델의 입력과 출력을 통째로 남기면 저장 비용이 커지고, 그 안에 개인정보가 섞입니다. 저는 도구 호출 단위 레코드는 빠짐없이 남기고, 모델 입출력 원문은 별도 저장소에 짧은 보존 기간으로 두는 편을 권합니다.

다른 실패는 시계입니다. 에이전트 하네스, 애플리케이션 서버, DB 서버의 시각이 어긋나면 대조가 어려워집니다. 시각보다 `trace_id` 같은 공통 키로 대조하는 이유입니다.

## 4. 배포는 단계로 넓히고, 멈추는 방법을 먼저 만듭니다

### 단계와 통과 기준

NIST는 AI RMF의 행위 목록이 체크리스트도, 순서가 정해진 절차도 아니라고 분명히 적어 두었습니다 [\[NIST AIRC: AI RMF Core\]](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/). 프레임워크는 방향을 주고, 순서는 각 조직이 정해야 한다는 뜻으로 읽습니다.

제가 권하는 순서는 다음과 같습니다.

```text
0단계 섀도        운영 데이터 사본으로 실행, 결과는 사람이 한 일과 비교만 함
   │  통과 기준: 정해 둔 평가 세트에서의 원인 일치율, 금지 행위 시도 0건
1단계 읽기 전용   운영 조회 허용, 산출물은 초안과 분석 보고서
   │  통과 기준: 조회 범위 위반 0건, 마스킹 누락 0건, 보고서 채택률
2단계 승인부 쓰기 되돌릴 수 있는 쓰기부터, 건마다 승인
   │  통과 기준: 승인 반려율과 사유 검토, 중복 실행 0건, 승인 요청 건수가 예산 안
3단계 범위 확장   승인 없이 실행하는 저위험 행위 목록을 명시적으로 추가
```

단계마다 통과 기준을 먼저 적어 두는 것이 measure에 해당합니다. 기준 없이 "문제없어 보여서" 넘어가는 단계 이동은 나중에 설명할 수 없습니다.

배치 분석 에이전트의 0단계는 지난 몇 달의 배치 실패 기록을 평가 세트로 쓸 수 있습니다. 당시 담당자가 적은 원인과 에이전트가 낸 원인을 비교하는 것입니다. 이 세트는 단계를 올릴 때마다, 그리고 모델이나 프롬프트를 바꿀 때마다 다시 돌립니다.

### 멈추는 장치는 첫 실행 전에 만듭니다

manage에 해당하는 것은 멈추는 장치입니다. 금융보안원 평가기준에는 자원 고갈 방지와 킬스위치 구현이 점검 항목으로 들어 있습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

가이드라인은 한 걸음 더 들어갑니다. 인적 개입 방법으로 권고 재정의(override), 긴급정지 기능(kill switch)과 격리, 실시간 모니터링 대시보드를 들고, 고위험 인공지능에는 앞의 둘을 필수로, 대시보드를 권고로 표시합니다. 사건 대응 표준 운영 절차의 예로는 접수, 판정, 격리, 증거보존, 통지, 근본원인분석, 재발방지의 순서를 제시합니다 [\[금융위원회: 금융분야 인공지능 가이드라인\]](https://fsc.go.kr/comm/getFile?fileNo=6&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142).

하네스에서는 이렇게 구현할 수 있습니다.

| 장치 | 하네스 구현 | 무엇을 막는가 |
| --- | --- | --- |
| 호출 상한 | 세션당 도구 호출 횟수, 같은 도구 연속 호출 횟수 | 반복 루프, 재시도 폭주 |
| 예산 상한 | 작업당 토큰과 비용 상한, 초과 시 중단 후 보고 | 자원 고갈 |
| 신원 정지 | 에이전트 신원 하나의 자격 증명을 즉시 폐기 | 진행 중인 모든 세션의 쓰기 |
| 격리 | 해당 에이전트의 쓰기 도구만 비활성화하고 읽기는 유지 | 원인 조사 중 추가 피해 |
| 증거 보존 | 정지 시점의 세션 상태와 감사 레코드 스냅샷 | 사후 분석 불가 |

전용 신원을 써야 하는 이유가 여기서 한 번 더 나옵니다. 사람 계정을 빌린 에이전트는 끌 수 없습니다. 운영자 계정을 정지하면 운영자도 일을 못 하고, 정지하지 않으면 에이전트를 멈출 수 없습니다.

### 멈춤을 시험합니다

킬스위치는 한 번도 눌러 보지 않으면 있는지 없는지 알 수 없습니다. 가이드라인도 신속한 대응을 위해 필요에 따라 실전 모의훈련을 하라고 적고 있습니다.

배치 분석 에이전트라면 1단계 진입 전에 한 번, 2단계 진입 전에 한 번, 운영 중인 세션에서 신원 정지를 실제로 실행해 보고 진행 중이던 도구 호출이 어떻게 끝나는지 확인하는 편이 좋습니다. 특히 승인을 기다리던 요청이 정지 후에 승인되면 어떻게 되는지를 봐야 합니다. OWASP가 지적한 확인 시점과 사용 시점의 차이가 바로 이 자리에서 생깁니다 [\[OWASP: Top 10 for Agentic Applications 2026\]](https://genai.owasp.org/download/52117/).

### 프롬프트와 도구 정의도 변경 관리 대상입니다

레거시 조직에는 이미 형상 관리와 변경 승인 절차가 있습니다. 에이전트를 붙일 때 자주 빠지는 것은 그 절차의 대상 목록입니다.

배치 분석 에이전트의 동작을 바꾸는 것은 소스 코드만이 아닙니다. 시스템 프롬프트 한 줄, 도구 설명 한 문장, 위험 등급 설정 하나, 모델 버전 하나가 바뀌어도 에이전트의 행동이 달라집니다. 저는 이 네 가지를 소스 코드와 같은 저장소에 두고, 같은 리뷰와 배포 절차를 태우는 편이 안전하다고 봅니다. 변경할 때마다 0단계의 평가 세트를 다시 돌리고, 그 결과를 변경 요청서에 붙이면 단계 이동의 기준과 변경 관리의 기준이 하나로 이어집니다.

### 기준이 아직 움직이고 있다는 점

참고로 금융보안원 평가기준은 올해 말까지 시범 검증을 거쳐 2027년부터 정식 점검기준으로 확대 적용할 계획이라고 합니다. 항목과 점검 방법은 시범 적용 과정에서 확인된 점검 가능 여부와 회사별 구현 방식 차이를 반영해 보완될 예정이고, 최종 평가기준은 2026년 「AI REDTEAM REPORT」로 공개할 예정이라고 밝히고 있습니다 [\[금융보안원: 금융분야 AI 에이전트 보안 평가기준 마련\]](https://www.fsec.or.kr/bbs/detail?bbsNo=12122&menuNo=69).

확정된 요건으로 읽기보다 방향으로 읽는 편이 맞습니다. 금융위원회 가이드라인도 기술 변화와 운영 중 문의 사항을 반영해 해마다 업데이트할 계획이라고 적고 있습니다 [\[금융위원회: 금융분야 인공지능 가이드라인 요약\]](https://fsc.go.kr/comm/getFile?fileNo=5&fileTy=ATTACH&srvcId=BBSTY1&upperNo=87142). 체크리스트도 문서 버전을 붙여 관리하는 편이 좋습니다.

## 5. 체크리스트로 정리하면

권한

- 에이전트 전용 신원이 있고, 사람 계정이나 공용 운영 계정을 쓰지 않는다
- 자격 증명은 작업 단위로 발급되고 수명이 짧다
- 운영 DB 접근은 조회용 뷰나 복제본으로 한정되어 있고, 뷰에 업무상 불필요한 개인정보 컬럼이 없다
- 쓰기는 기존 애플리케이션 API나 프로시저를 거치며, 직접 DML 경로와 범용 셸 도구가 없다
- 재실행 가능한 작업에는 멱등 키가 있고, 없는 작업은 에이전트 도구 목록에서 빠져 있다

승인

- 승인이 필요한 행위가 행위 단위 위험 등급으로 정의되어 있고, 승인선은 기존 결재선의 직책을 쓴다
- 하루 승인 요청 건수에 예산이 있고, 넘으면 승인 대상 정의를 다시 검토한다
- 승인 화면이 실제 실행 내용(대상, 인자, 영향 건수)을 보여 주고, 승인과 반려 모두 사유를 남긴다

기록

- 로그 한 건으로 지시자, 에이전트, 자격 증명, 모델, 도구, 승인자, 실제 부작용을 이을 수 있다
- 감사 레코드와 기존 DB 감사 로그를 대조할 공통 키가 있다
- 개인정보 마스킹이 컨텍스트 진입 전에 적용되고, 감사 로그에는 원문 행이 남지 않는다

단계와 정지

- 배포 단계별 통과 기준이 문서로 먼저 존재하고, 평가 세트가 모델과 프롬프트 변경 때마다 다시 돈다
- 세션당 호출 상한, 작업당 예산 상한, 에이전트 단위 중지 스위치가 있다
- 중지 스위치를 단계 이동 전에 실제로 눌러 보았고, 승인 대기 중인 요청의 처리 방식이 정해져 있다

## 6. 오늘 바로 적용할 수 있는 순서

1. 에이전트가 닿는 자원을 표로 적고, 칸마다 읽기와 쓰기를 구분합니다. 쓰기 칸은 비워 둔 채로 시작합니다.
2. 에이전트 전용 DB 계정과 서비스 계정을 만들고, 업무상 필요한 컬럼만 담은 조회용 뷰에 조회 권한만 부여합니다.
3. 되돌릴 수 없는 쓰기 세 가지를 골라 승인 필요 행위로 지정하고, 기존 당직이나 결재선의 직책을 승인선으로 연결합니다.
4. 도구 호출 감사 레코드의 필드를 확정하고, 기존 DB 감사 로그와 대조할 키를 어댑터에서 심습니다.
5. 섀도 단계의 평가 세트와 통과 기준을 숫자로 적고, 중지 스위치를 한 번 눌러 본 뒤에 첫 실행을 합니다.

## 마치며

레거시 조직의 통제 절차는 느리다는 이유로 자주 비판받습니다. 그런데 에이전트를 붙여 보면 그 절차들이 바로 필요한 가드레일의 목록이라는 것을 알게 됩니다.

권한 분리, 결재선, 감사 추적, 단계적 이행은 새로 발명할 것이 아닙니다. 에이전트가 그 안에서 식별 가능한 한 명의 행위자로 움직이게 만드는 것이 하네스의 일입니다.

이 체크리스트는 출발점입니다. 각 조직의 내부통제 기준과 감독 요건에 맞춰 고쳐 쓰시기 바랍니다.
