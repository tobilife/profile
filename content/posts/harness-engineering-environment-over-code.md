:::note
- Harness engineering은 에이전트의 실수를 그때그때 고치는 대신, 같은 실수가 다시 나올 수 없도록 환경을 고치는 일입니다. 출력을 고치는 시간은 한 번 쓰고 사라지지만, 환경을 고친 시간은 다음 실행마다 다시 쓰입니다.
- 축은 세 가지입니다. 에이전트가 알아야 할 것을 저장소 안에서 읽히게 하는 가독성, 어기면 무언가 실패하게 만드는 기계적 강제, 이미 들어온 나쁜 예를 상시로 치우는 수거입니다.
- 규칙은 문서에서 시작해 코드로 승격됩니다. 승격된 규칙의 오류 메시지는 사람이 아니라 에이전트가 읽는 다음 턴의 입력이므로, 고치는 방법까지 적어야 합니다.
- 공개된 대표 사례는 빈 저장소에서 시작한 벤더 자신의 실험입니다. 세 축은 레거시 환경에서도 쓸모가 있지만, 병합 게이트를 낮춘 부분까지 따라 하면 안 됩니다.
:::

코딩 에이전트가 기대만큼 일하지 못하면 보통 두 가지를 떠올립니다. 더 좋은 모델이 나오기를 기다리거나, 프롬프트를 더 공들여 쓰는 것입니다.

하지만 **에이전트가 막히는 원인의 상당수는 모델의 능력이 아니라, 에이전트가 일하는 환경이 덜 명세되어 있다는 데 있습니다.**

OpenAI는 2026년 2월 11일에 공개한 글에서 사람이 직접 쓴 코드 없이 내부 제품을 만든 5개월의 실험을 설명하며, 초기 진척이 예상보다 느렸던 이유가 Codex의 능력 부족이 아니라 환경이 덜 명세되어 있었기 때문이라고 적었습니다. 에이전트에게 목표를 향해 나아갈 도구, 추상화, 내부 구조가 없었다는 것입니다. [\[OpenAI: Harness engineering\]](https://openai.com/index/harness-engineering/)

그보다 엿새 앞선 2월 5일, Mitchell Hashimoto는 에이전트가 실수하는 것을 발견할 때마다 그 실수를 다시는 하지 않도록 해결책을 만들어 넣는 일을 "harness engineering"이라고 부르게 됐다고 썼습니다. [\[Mitchell Hashimoto: My AI Adoption Journey\]](https://mitchellh.com/writing/my-ai-adoption-journey)

이 글은 이 이름이 가리키는 일을 세 축으로 나누고, 각 축이 실제로 어떻게 작동하는지, 어디서 깨지는지, 보수적인 조직이 어디까지 가져올 수 있는지를 하나의 예로 끝까지 따라가 봅니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사의 보험금 청구 접수 서비스를 맡은 팀이 코딩 에이전트를 쓰고 있다고 해봅시다. Java 백엔드이고, 접수 화면에서 받은 청구 건을 검증해 심사 대기열로 넘기는 서비스입니다. 이 글은 끝까지 이 저장소를 예로 씁니다.

에이전트에게 "청구 접수 시 서류 누락 사유 코드를 저장하는 필드를 추가해 줘"라고 시킵니다.

에이전트는 화면 요청을 받는 컨트롤러 안에서 저장소 계층을 건너뛰고 직접 SQL을 실행하는 코드를 넣습니다. 저장소 어딘가에 3년 전에 그렇게 짠 코드가 하나 남아 있었기 때문입니다. 로그는 청구인 이름과 연락처를 문자열로 이어 붙여 남깁니다.

리뷰에서 이런 코멘트가 달립니다.

```text
리뷰어: 컨트롤러에서 SQL 을 직접 실행하지 않기로 지난 분기에 합의했잖아요.
        로그도 구조화 로깅으로 통일했고, 개인정보 필드는 마스킹 유틸을 거쳐야 합니다.

작성자: (에이전트 출력을 손으로 고쳐서 다시 올림)
```

다음 주에 다른 사람이 "청구 취소 사유를 추가해 줘"라고 시키고, 에이전트는 같은 실수를 합니다. 리뷰어는 같은 코멘트를 다시 씁니다.

시스템 설계 관점에서 잘못된 것은 세 가지입니다.

- 합의는 메신저 스레드와 회의록에 있었습니다. 에이전트가 볼 수 없는 곳입니다.
- 규칙을 어겨도 실패하는 것이 없었습니다. 컴파일도, 단위 테스트도, CI도 통과했습니다.
- 규칙에 어긋나는 옛 코드가 저장소에 남아 있었고, 에이전트는 그것을 본보기로 삼았습니다.

각각이 가독성, 강제, 수거의 문제입니다. 사람이 출력을 고쳐서 올린 것은 증상 치료였고, 환경은 그대로였습니다. 그래서 같은 증상이 다음 주에 다시 나왔습니다.

## 1. 실수를 고치지 말고, 같은 실수가 나올 수 없게 환경을 고친다

### 이름은 한 달 사이에 자리를 잡았다

이 용어의 흐름을 날짜로 정리하면 이렇습니다.

| 날짜 | 글 | 요지 |
| --- | --- | --- |
| 2026-02-05 | Mitchell Hashimoto, My AI Adoption Journey | 에이전트의 실수를 볼 때마다 다시는 그 실수를 하지 않게 해결책을 만드는 일을 harness engineering이라 부름 |
| 2026-02-11 | OpenAI, Harness engineering | 수동 작성 코드 0줄로 제품을 만든 실험과 그 과정에서 만든 환경 |
| 2026-02-17 | Birgitta Böckeler, Harness Engineering | OpenAI 글을 읽고 하네스 구성 요소를 세 범주로 묶고 한계를 지적 |

Böckeler는 OpenAI 글이 제목과 달리 본문에서 "harness"라는 단어를 한 번만 쓴다고 짚으면서, 이 용어가 Hashimoto의 글에서 영감을 받은 것일 수 있다고 추측했습니다. 그리고 에이전트를 통제 아래 두는 도구와 관행을 가리키는 단어로 마음에 든다고 적었습니다. [\[Birgitta Böckeler: Harness Engineering\]](https://web.archive.org/web/20260219105049/https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html)

용어의 원조를 따지려는 것은 아닙니다. 서로 다른 배경의 세 사람이 같은 달에 같은 단어로 같은 종류의 일을 설명했다는 점이, 이 일이 개인 취향이 아니라 공통의 작업 방식으로 굳어 가고 있다는 신호라고 봅니다.

### 하네스 루프는 이렇게 돈다

Hashimoto의 글은 이 일을 두 형태로 나눕니다. 하나는 AGENTS.md 같은 파일을 고쳐 암묵적인 지시를 개선하는 것입니다. 에이전트가 틀린 명령을 반복해서 실행하거나 틀린 API를 찾는 정도의 단순한 문제가 여기에 해당합니다. 그가 예로 든 Ghostty의 AGENTS.md는 각 줄이 에이전트의 나쁜 행동 하나에 대응하고, 그 파일로 해당 행동이 거의 다 사라졌다고 합니다.

다른 하나는 실제로 프로그래밍한 도구입니다. 스크린샷을 찍는 스크립트, 필터링된 테스트만 돌리는 스크립트 같은 것이고, 보통 그 도구가 있다는 사실을 알리는 AGENTS.md 수정과 짝을 이룹니다. 글의 요점은 에이전트에게 자기가 틀렸다는 것을 자동으로 알려 주는 빠르고 질 좋은 도구를 주라는 것입니다.

OpenAI 글도 같은 태도를 보입니다. 무언가 실패했을 때 해법은 거의 언제나 "더 열심히 시도하라"가 아니었고, 엔지니어는 "어떤 능력이 빠져 있고, 그것을 에이전트가 읽을 수 있고 강제할 수 있는 형태로 어떻게 만들 것인가"를 물었다고 합니다. 에이전트가 고전하면 그것을 신호로 보고, 빠진 도구, 가드레일, 문서를 찾아 저장소에 되먹인다는 설명도 있습니다.

두 글을 합쳐 한 번의 루프로 그리면 이렇습니다.

```text
에이전트 실행 -> 결과물 (PR, 로그, 테스트 결과)
        |
        v
사람이 실패를 발견 (리뷰 코멘트, 버그, 손으로 고친 흔적)
        |
        v
분류: 에이전트가 몰랐나? / 어겨도 막는 게 없었나? / 나쁜 본보기가 있었나?
        |                    |                          |
        v                    v                          v
   문서·도구 추가        린트·구조 테스트 추가       기존 위반 정리
   (가독성)              (강제)                      (수거)
        |                    |                          |
        +--------------------+--------------------------+
        |
        v
같은 작업을 다시 시켜 재발하지 않는지 확인 -> 다음 실행부터 기본값이 됨
```

마지막 칸이 빠지기 쉽습니다. 환경을 고친 뒤 같은 작업을 다시 시켜 보지 않으면, 고친 것이 실제로 작동하는지 모릅니다. 청구 접수 예에서는 문서를 고친 뒤 "청구 취소 사유 추가"를 새 세션에서 시켜 보고, 컨트롤러에 SQL이 들어오는지를 확인하는 것이 그 칸입니다.

### 세 축과 각 축이 던지는 질문

Böckeler는 OpenAI 하네스의 구성 요소를 세 범주로 묶었습니다. 코드베이스 안의 지식 베이스와 관측 데이터, 브라우저 같은 동적 컨텍스트를 포함하는 컨텍스트 엔지니어링, LLM뿐 아니라 결정적인 커스텀 린터와 구조 테스트가 감시하는 아키텍처 제약, 그리고 주기적으로 돌며 불일치와 위반을 찾는 "garbage collection"입니다. 그는 이 하네스가 결정적인 방식과 LLM 기반 방식을 섞고 있다고도 적었습니다.

저는 이 분류를 질문 형태로 바꿔 씁니다.

| 축 | 던지는 질문 | 대표 수단 | 청구 접수 예에서 |
| --- | --- | --- | --- |
| 가독성 | 에이전트가 이 사실을 알 방법이 있었는가 | 저장소 안 문서, 실행 가능한 앱, 조회 가능한 로그 | 계층 규칙과 로깅 규칙이 저장소 문서에 없었다 |
| 강제 | 어겼을 때 무엇이 실패하는가 | 커스텀 린터, 구조 테스트, CI | 컨트롤러의 SQL을 막는 검사가 없었다 |
| 수거 | 이미 들어온 나쁜 예를 누가 언제 치우는가 | 주기적으로 도는 정리 작업 | 3년 전 코드가 그대로 본보기로 남아 있었다 |

이름이 새로울 뿐 내용은 낯설지 않습니다. 신입 개발자 온보딩, 정적 분석, 기술 부채 관리입니다. 달라진 것은 대상이 사람에서 에이전트로 바뀌면서 눈치와 복도 대화로 통하던 것이 더 이상 통하지 않는다는 점입니다.

### 실패 모드와 비용: 모든 실수를 하네스로 만들 필요는 없다

이 루프에도 비용이 있습니다. 문서 한 줄, 린트 규칙 하나, 정리 작업 하나가 모두 유지보수 대상입니다.

제가 보기에 흔한 실패는 두 가지입니다. 하나는 한 번 본 실수마다 규칙을 만들어 규칙이 수백 개로 불어나는 것입니다. 규칙끼리 충돌하기 시작하면 에이전트도 사람도 무엇이 중요한지 모르게 됩니다. 다른 하나는 반대로, 매번 손으로 고치는 편이 빠르다며 루프를 아예 돌리지 않는 것입니다.

그래서 저는 하네스로 만들 실수를 고르는 기준을 둡니다.

- 같은 실수가 두 번 이상 나왔는가.
- 그 실수가 리뷰에서 걸러지지 않았을 때 비용이 큰가. 개인정보 노출, 데이터 정합성, 보안이 여기에 해당합니다.
- 기계적으로 판정할 수 있는가. 판정에 사람의 맥락 판단이 필요한 것은 문서에 두고 리뷰에 맡깁니다.

세 질문에 모두 "예"인 것부터 강제로 내리고, 첫 번째만 "예"인 것은 문서로 시작하는 편이 안전하다고 봅니다.

## 2. 가독성: 저장소에 없는 지식은 에이전트에게 없는 지식이다

OpenAI 글의 표현은 단호합니다. 에이전트 입장에서, 실행 중에 컨텍스트 안에서 접근할 수 없는 것은 사실상 존재하지 않는다는 것입니다. Google Docs, 채팅 스레드, 사람들 머릿속에 있는 지식은 시스템이 볼 수 없고, 에이전트가 볼 수 있는 것은 코드, 마크다운, 스키마, 실행 계획처럼 저장소 안에서 버전 관리되는 산출물뿐이라고 합니다.

그래서 그 팀은 시간이 갈수록 더 많은 컨텍스트를 저장소 안으로 밀어 넣어야 했다고 적습니다. 아키텍처 패턴을 정한 Slack 논의도 에이전트가 찾을 수 없다면, 3개월 뒤 입사한 사람이 모르는 것과 마찬가지로 에이전트에게도 없는 정보라는 설명입니다. 앞의 상황에서 메신저 스레드의 합의가 바로 이 경우입니다.

### 한 턴에 에이전트가 보는 것

가독성을 설계하려면 먼저 에이전트가 실제로 무엇을 보는지 알아야 합니다. 대부분의 코딩 에이전트에서 흐름은 대략 이렇습니다.

```text
세션 시작
  |
  +-- 하네스가 지침 파일(AGENTS.md 등)을 컨텍스트에 넣는다     <- 항상 보임
  |
  +-- 사용자 요청: "서류 누락 사유 코드 필드를 추가해 줘"
  |
  +-- 에이전트가 파일 검색, 읽기, 명령 실행으로 필요한 것을 찾는다  <- 찾아야 보임
  |       지침 파일이 가리키는 문서가 있으면 그쪽으로 간다
  |       가리키는 곳이 없으면 비슷해 보이는 기존 코드를 연다
  |
  +-- 변경 -> 테스트·린트 실행 -> 출력이 다시 컨텍스트로 들어온다  <- 실행해야 보임
```

세 칸이 각각 다른 가독성 수단에 대응합니다. 항상 보이는 칸에는 짧은 지도가, 찾아야 보이는 칸에는 잘 정리된 문서가, 실행해야 보이는 칸에는 결과가 분명한 도구가 필요합니다.

AGENTS.md는 이 첫 칸을 위한 형식입니다. 공식 사이트는 README가 사람을 위한 파일이라면, AGENTS.md는 코딩 에이전트에게 필요한 빌드 단계, 테스트, 관례처럼 README를 어지럽힐 수 있는 맥락을 담는 파일이라고 설명합니다. 큰 모노레포에서는 패키지마다 AGENTS.md를 두고, 에이전트가 디렉터리 트리에서 가장 가까운 파일을 읽으므로 가까운 쪽이 우선한다고 안내합니다. [\[AGENTS.md\]](https://web.archive.org/web/20260215102729/https://agents.md/)

같은 사이트의 FAQ는 AGENTS.md에 테스트 명령을 적어 두면 에이전트가 관련 검사를 실행하고 작업을 마치기 전에 실패를 고치려 한다고 답합니다. 지침 파일이 단순한 설명서가 아니라 "실행해야 보이는" 칸으로 가는 입구 역할도 한다는 뜻입니다.

### 지침 파일은 백과사전이 아니라 목차다

OpenAI 팀은 처음에 큰 AGENTS.md 하나에 모든 것을 넣는 방식을 시도했고, 예측 가능한 방식으로 실패했다고 적습니다. 이유는 네 가지입니다.

- 컨텍스트는 희소한 자원이라, 거대한 지침 파일이 작업과 코드와 관련 문서를 밀어냅니다.
- 전부 중요하다고 하면 아무것도 중요하지 않게 되고, 에이전트는 의도적으로 탐색하는 대신 국소적인 패턴 매칭으로 흐릅니다.
- 한 덩어리 문서는 금방 낡은 규칙의 무덤이 됩니다.
- 한 덩어리는 범위, 최신성, 소유자, 상호 링크 같은 기계적 검사를 하기 어렵습니다.

그 대신 약 100줄의 짧은 AGENTS.md를 지도로 쓰고, 실제 지식은 구조화된 `docs/` 디렉터리에 두어 그곳을 기록의 원천(system of record)으로 삼았다고 합니다. 설계 문서는 검증 상태와 함께 색인되고, 아키텍처 문서는 도메인과 패키지 계층의 지도를 제공하며, 품질 문서는 제품 도메인과 계층마다 등급을 매겨 빈틈을 추적합니다. 계획도 일급 산출물입니다. 작은 변경은 가벼운 계획으로, 복잡한 작업은 진행 상황과 결정 로그를 담은 실행 계획으로 저장소에 커밋됩니다.

OpenAI 글은 이 구조를 점진적 공개(progressive disclosure)라고 부릅니다. 에이전트는 작고 안정된 진입점에서 출발하고, 다음에 어디를 볼지 배우며 움직입니다.

여기서 말하는 아키텍처 문서는 matklad가 2021년에 권한 ARCHITECTURE.md 관행과 이어집니다. 그 글은 처음 온 기여자에게 패치를 쓰는 시간보다 어디를 고쳐야 하는지 찾는 시간이 훨씬 오래 걸린다고 말하며, 짧게 유지해야 덜 낡는다고 권합니다. [\[matklad: ARCHITECTURE.md\]](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) 사람 신규 기여자를 위한 처방이 그대로 에이전트에게 통하는 셈입니다.

청구 접수 저장소에 이 구조를 적용하면 아래와 같은 모양이 될 것입니다. OpenAI 글의 디렉터리 예를 참고해 제가 구성한 예시입니다.

```text
AGENTS.md                 # 100줄 안팎. 어디에 무엇이 있는지, 검증 명령이 무엇인지
ARCHITECTURE.md           # 청구 접수 / 서류 검증 / 심사 연계 도메인과 계층 지도
docs/
  design/
    index.md              # 설계 결정 목록과 검증 상태
    layering.md           # 컨트롤러 -> 서비스 -> 저장소 방향, 예외 없음
    logging.md            # 구조화 로깅, 개인정보 마스킹 유틸 사용법
  plans/
    active/               # 진행 중인 실행 계획과 결정 로그
    completed/
    tech-debt.md          # 알려진 위반 목록 (수거 대상)
  references/
    legacy-procedures.md  # 호출해도 되는 Oracle 프로시저와 호출 규약
  quality.md              # 도메인별 품질 등급
```

앞의 상황에서 메신저에 있던 합의는 `docs/design/layering.md`와 `docs/design/logging.md`로 옮겨지고, AGENTS.md에는 "계층과 로깅 규칙은 docs/design 아래를 먼저 읽는다"는 한 줄이 들어갑니다.

### 코드만이 아니라 실행 중인 앱도 읽혀야 한다

가독성은 문서에서 끝나지 않습니다.

OpenAI 팀은 코드 처리량이 늘자 병목이 사람의 QA 여력이 됐다고 합니다. 그래서 앱을 git worktree마다 띄울 수 있게 만들어 에이전트가 변경마다 인스턴스 하나를 구동하게 했고, Chrome DevTools Protocol을 에이전트 런타임에 연결하고 DOM 스냅샷, 스크린샷, 화면 이동을 다루는 스킬을 만들었습니다. 그 결과 에이전트가 버그를 재현하고 수정을 검증할 수 있었다고 합니다.

로그, 메트릭, 트레이스도 worktree마다 생겼다 사라지는 로컬 관측 스택으로 노출했고, 에이전트는 LogQL로 로그를, PromQL로 메트릭을 조회할 수 있었습니다. 이렇게 되면 "서비스 시작이 800ms 안에 끝나게 하라" 같은 요구를 에이전트가 스스로 측정하며 다룰 수 있게 된다고 합니다.

Anthropic이 2025년 11월에 공개한 장시간 실행 에이전트용 하네스 글도 같은 방향의 관찰을 담고 있습니다. 명시적으로 지시하지 않으면 Claude가 단위 테스트나 `curl`로만 확인하고 기능이 끝에서 끝까지 작동하지 않는다는 것을 알아채지 못하는 경향이 있었고, 브라우저 자동화 도구로 사람 사용자처럼 테스트하게 하자 코드만 봐서는 드러나지 않는 버그를 찾아 고쳤다는 내용입니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

같은 글에는 가독성을 다른 각도에서 다룬 장치도 있습니다. 첫 세션의 에이전트가 개발 서버를 띄우는 `init.sh`, 작업 기록을 남기는 진행 파일, 초기 git 커밋을 만들고, 이후 세션은 진행 파일과 git 로그를 읽고 기본 테스트를 돌린 뒤 시작합니다. 기능 목록은 JSON으로 두고 에이전트가 `passes` 필드만 바꾸게 했는데, 모델이 Markdown보다 JSON 파일을 부적절하게 고쳐 쓸 가능성이 낮았기 때문이라고 설명합니다.

여기서 제가 가져가는 원칙은 이렇습니다. **에이전트에게 요구하려는 것은 에이전트가 측정할 수 있어야 합니다.** 측정할 방법을 주지 않은 요구사항은 결국 사람이 확인하게 되고, 그 지점이 처리량의 상한이 됩니다.

청구 접수 서비스라면 다음 정도가 출발점입니다. 모두 제가 구성한 예시입니다.

- 테스트용 DB 스냅샷을 붙여 로컬에서 서비스를 띄우는 스크립트 하나.
- 청구 한 건을 접수 API로 넣고 심사 대기열 테이블에 들어갔는지 확인하는 검증 스크립트 하나.
- 최근 실행의 애플리케이션 로그에서 마스킹되지 않은 전화번호 패턴을 찾는 명령 하나.

세 번째가 있으면 "로그에 개인정보를 남기지 마라"는 요구를 에이전트가 자기 변경에 대해 직접 확인할 수 있습니다.

### 실패 모드와 비용: 문서는 썩고, 컨텍스트는 넘친다

가독성 축의 가장 큰 위험은 문서가 코드와 어긋나는 것입니다. 사람은 낡은 문서를 보면 "이건 옛날 얘기"라고 걸러 듣지만, 에이전트는 저장소에 적힌 것을 사실로 받아들입니다. 낡은 문서는 문서가 없는 것보다 나쁠 수 있습니다.

OpenAI 팀이 지식 베이스 자체를 강제 대상으로 둔 이유가 여기 있다고 봅니다. 전용 린터와 CI 작업이 지식 베이스가 최신인지, 상호 링크가 맞는지, 구조가 올바른지 검사하고, 주기적으로 도는 "doc-gardening" 에이전트가 실제 코드 동작을 반영하지 않는 낡은 문서를 찾아 수정 PR을 연다고 합니다.

두 번째 위험은 반대 방향입니다. 문서를 많이 만들수록 에이전트가 읽어야 할 양이 늘고, 정작 중요한 규칙이 묻힙니다. 지침 파일을 목차로 유지하는 이유가 이것입니다.

세 번째는 보수적인 조직에서 특히 중요합니다. 저장소에 옮기는 지식에 넣으면 안 되는 것이 있습니다. 운영 접속 정보, 고객 데이터 표본, 보안 통제의 세부 우회 방법 같은 것입니다. "저장소 안에 있어야 에이전트가 안다"는 원칙은 "무엇이든 저장소에 넣으라"는 뜻이 아닙니다. 에이전트가 알아야 할 규칙과, 에이전트가 접근하면 안 되는 정보는 따로 분류해야 합니다.

## 3. 강제: 문서로 부탁한 규칙은 린터와 테스트로 승격시킨다

문서만으로는 에이전트가 만든 코드베이스의 일관성이 유지되지 않는다는 것이 OpenAI 글의 진단입니다. 그래서 그 팀은 구현을 세세하게 지시하는 대신 불변 조건을 강제하는 쪽을 택했다고 합니다.

### 불변 조건을 강제하고, 구현은 맡긴다

OpenAI 글이 드는 예는 경계에서 데이터 형태를 파싱하라는 요구입니다. 그 방법은 정하지 않았고, 모델이 Zod를 선호하는 것 같지만 그 라이브러리를 지정하지는 않았다고 합니다. 이 요구는 Alexis King의 2019년 글 "Parse, don't validate"를 가리킵니다. 그 글의 요지는 입력을 검사만 하고 원래 타입으로 흘려보내지 말고, 경계에서 더 정확한 타입으로 바꿔 이후 코드가 검사 결과를 다시 의심할 필요가 없게 만들라는 것입니다. [\[Alexis King: Parse, don't validate\]](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)

불변 조건과 구현 지시를 구분하는 이유는 비용 때문이라고 봅니다. "청구 금액은 경계에서 음수가 아닌 금액 타입으로 바뀌어야 한다"는 불변 조건은 기계로 검사할 수 있고 오래 유지됩니다. "금액 검증에는 이 유틸 클래스의 이 메서드를 써라"는 구현 지시는 리팩터링 한 번에 낡습니다.

### 계층 규칙은 사람 수백 명 규모에서나 하던 것을 초기에 한다

그 팀은 애플리케이션을 엄격한 계층 구조 위에 세웠습니다. 각 비즈니스 도메인 안에서 코드는 Types, Config, Repo, Service, Runtime, UI의 정해진 순서를 따라 앞 방향으로만 의존할 수 있고, 인증, 커넥터, 텔레메트리, 기능 플래그 같은 횡단 관심사는 Providers라는 하나의 명시적 인터페이스로만 들어옵니다. 그 밖의 의존은 허용되지 않으며, 커스텀 린터와 구조 테스트가 이를 기계적으로 강제합니다.

글은 이런 구조가 보통 엔지니어가 수백 명이 될 때까지 미루는 종류의 것이지만, 코딩 에이전트와 일할 때는 초기의 전제 조건이 된다고 말합니다. 제약이 있어야 속도를 내면서도 아키텍처가 흐트러지지 않는다는 설명입니다.

계층 규칙 말고도 "취향 불변 조건(taste invariants)"이라는 이름으로 구조화 로깅, 스키마와 타입의 명명 규칙, 파일 크기 제한, 플랫폼별 신뢰성 요구사항을 커스텀 린트로 정적 강제한다고 합니다. 사람 중심 워크플로에서는 이런 규칙이 깐깐하게 느껴질 수 있지만, 에이전트에게는 한 번 적으면 모든 곳에 동시에 적용되는 배수가 된다는 표현을 씁니다.

Böckeler는 이 대목에서 신뢰성을 얻기 위해 해법 공간을 좁혔다는 점에 주목했습니다. "무엇이든 생성할 수 있다"는 유연성을 일부 포기하고 특정 아키텍처 패턴, 강제된 경계, 표준화된 구조를 택했다는 해석입니다. 동시에 "경계에서 데이터 형태를 파싱하라"가 그 하네스에서 실제로 어떤 모습인지 구체적인 예가 없어 상상하기 어렵다는 아쉬움도 적었습니다.

### 오류 메시지는 다음 턴의 프롬프트다

강제의 방식에서 가장 실무적인 부분은 오류 메시지입니다. OpenAI 글은 린트가 커스텀이기 때문에 오류 메시지에 고치는 방법을 적어 에이전트의 컨텍스트로 넣는다고 설명합니다.

이것이 왜 중요한지는 한 턴의 흐름을 보면 분명합니다.

```text
에이전트: ClaimIntakeController 에 SQL 실행 코드 추가
        |
        v
에이전트: 검증 명령 실행 (AGENTS.md 에 적힌 대로)
        |
        v
구조 테스트 실패. 출력 전체가 에이전트 컨텍스트로 들어감
        |
        +-- 메시지가 "layer violation" 한 줄이면
        |       -> 에이전트는 위반을 피하는 아무 방법이나 찾는다
        |          (예: 같은 코드를 이름만 바꾼 유틸 클래스로 옮김)
        |
        +-- 메시지에 고치는 방법과 문서 경로가 있으면
                -> 에이전트는 저장소 계층에 메서드를 추가하고
                   서비스에서 호출하는 쪽으로 다시 쓴다
```

사람에게는 "위반"이라는 한 단어로 충분할 수 있습니다. 맥락을 알기 때문입니다. 에이전트에게는 그 메시지가 다음 행동을 결정하는 거의 유일한 입력입니다.

아래는 청구 접수 저장소에 맞춰 계층 방향을 검사하는 구조 테스트의 핵심 로직을 그려 본 예시입니다. 실제로는 Java 쪽 아키텍처 테스트 도구로 구현하겠지만, 판정과 메시지의 모양을 보이려고 짧게 썼습니다.

```python
# 예시: 청구 접수 저장소의 계층 의존 방향 검사
LAYERS = ["types", "config", "repository", "service", "controller"]

def check_import(importer: str, imported: str) -> str | None:
    """importer 계층의 코드가 imported 계층을 가져올 때의 위반 메시지를 돌려준다."""
    src, dst = LAYERS.index(importer), LAYERS.index(imported)
    if dst <= src and not (importer == "controller" and imported == "repository"):
        return None  # 앞선 계층 의존은 허용. 단 컨트롤러가 저장소를 직접 쓰는 것은 금지
    return (
        f"[layer-direction] {importer} 계층은 {imported} 계층을 직접 사용할 수 없습니다.\n"
        f"고치는 방법: 필요한 조회나 저장을 repository 계층의 메서드로 만들고 "
        f"service 계층에서 호출하세요. controller 는 service 만 호출합니다.\n"
        f"참고: docs/design/layering.md"
    )
```

메시지의 마지막 세 줄이 이 코드의 본체입니다. 앞의 판정 로직은 누구나 쓸 수 있지만, 고치는 방법과 문서 경로는 그 팀의 합의를 아는 사람만 쓸 수 있습니다.

### 규칙의 승격 경로와 어느 수단을 고를지

OpenAI 글은 리뷰 코멘트와 버그를 문서 갱신으로 반영하고, 문서로 부족하면 규칙을 코드로 승격한다고 설명합니다. 청구 접수 예에 적용하면 이런 순서입니다.

```text
리뷰에서 "컨트롤러 SQL 금지" 지적이 반복됨
        |
        v
docs/design/layering.md 에 규칙과 이유를 적고 AGENTS.md 에서 가리킨다   (가독성)
        |
        |  새 세션에서 같은 작업을 시켜도 반복됨
        v
구조 테스트로 만들고 오류 메시지에 고치는 방법을 넣는다                 (강제)
        |
        v
기존 위반을 찾아 tech-debt.md 에 올리고 정리 PR 을 연다                 (수거)
```

수단을 고를 때는 판정의 성격을 봅니다. 아래는 제가 쓰는 기준입니다.

| 규칙의 성격 | 맞는 수단 | 청구 접수 예 |
| --- | --- | --- |
| 맥락 판단이 필요하고 예외가 잦다 | 문서와 리뷰 | 심사 연계 메시지의 필드 순서를 어떻게 정할지 |
| 한 파일 안의 문법 패턴으로 판정된다 | 린트 규칙 | 로그 호출에 문자열 연결 사용 금지 |
| 모듈이나 계층 사이의 관계로 판정된다 | 구조 테스트 | 컨트롤러에서 저장소 계층 직접 사용 금지 |
| 실행해 봐야 판정된다 | 통합 테스트, 검증 스크립트 | 접수된 청구가 심사 대기열에 들어가는가 |
| 어기면 되돌릴 수 없다 | 에이전트 실행 경로의 차단과 사람 승인 | 운영 DB 접속, 개인정보 원본 조회 |

마지막 줄은 하네스 엔지니어링보다 가드레일의 영역입니다. 린트와 테스트는 변경이 들어오기 전에 걸러 내지만, 되돌릴 수 없는 행동은 에이전트가 시도하는 순간 막아야 하기 때문입니다.

### 실패 모드와 비용: 규칙이 너무 많거나, 규칙을 우회하거나

강제 축의 첫 번째 실패는 거짓 양성입니다. 규칙이 정당한 코드를 막기 시작하면 에이전트는 규칙을 피해 가는 이상한 코드를 쓰고, 사람은 규칙을 끄는 예외 주석을 남발합니다. 새 규칙은 기존 코드에 먼저 돌려 보고, 거짓 양성이 많으면 범위를 좁힌 뒤에 켜는 편이 안전합니다.

두 번째는 우회입니다. 에이전트가 테스트를 통과시키려고 규칙 설정 파일이나 테스트 자체를 고치는 경우를 생각해 둬야 합니다. Anthropic의 장시간 하네스 글도 기능 목록 파일에서 테스트를 지우거나 고치는 것을 받아들일 수 없다는 강한 지시를 넣었다고 적습니다. 저는 지시에 더해, 린트 설정과 구조 테스트 파일의 변경은 별도 리뷰어 승인이 필요하도록 저장소 규칙을 거는 편이 낫다고 봅니다.

세 번째는 속도입니다. 검사가 느리면 에이전트도 사람도 덜 돌립니다. Hashimoto가 "빠르고 질 좋은 도구"라고 쓴 데는 이유가 있습니다. 변경한 모듈에 관련된 검사만 골라 돌리는 명령을 따로 두는 것이 좋습니다.

## 4. 수거: 에이전트는 나쁜 예도 복제하므로 청소를 상시 프로세스로 만든다

### 에이전트는 저장소에 있는 패턴을 따라 한다

OpenAI 글은 Codex가 저장소에 이미 있는 패턴을 복제하며, 고르지 않거나 최적이 아닌 패턴도 마찬가지라고 적습니다. 시간이 지나면 피할 수 없이 drift가 생긴다는 것입니다.

앞에서 본 에이전트의 한 턴을 떠올리면 이유가 보입니다. 지침 파일이 가리키는 문서가 없으면 에이전트는 비슷해 보이는 기존 코드를 엽니다. 청구 접수 예에서 3년 전 코드가 바로 그 "비슷해 보이는 기존 코드"였습니다. 문서와 린트를 아무리 갖춰도, 저장소에 위반 사례가 남아 있으면 그것이 계속 후보로 읽힙니다.

### 손으로 치우는 방식은 확장되지 않았다

처음에는 사람이 직접 치웠다고 합니다. 매주 금요일, 한 주의 20%를 "AI slop" 정리에 썼고, 당연하게도 이 방식은 확장되지 않았습니다.

대안은 두 가지를 합친 것이었습니다. 저장소에 "golden principles"라고 부르는 의견이 분명한 기계적 규칙을 적어 넣고, 주기적인 정리 프로세스를 만든 것입니다. 글이 드는 원칙의 예는 손으로 만든 헬퍼 대신 공유 유틸리티 패키지를 쓴다, 데이터를 추측으로 다루지 말고 경계에서 검증하거나 타입이 있는 SDK에 기댄다는 것입니다. 정해진 주기로 백그라운드 Codex 작업이 위반을 찾고, 품질 등급을 갱신하고, 범위가 좁은 리팩터링 PR을 엽니다. 대부분은 1분 안에 검토할 수 있고 자동 병합된다고 합니다.

글은 이것을 garbage collection에 비유하고, 기술 부채를 고금리 대출에 빗댑니다. 조금씩 계속 갚는 편이 쌓아 두었다가 한꺼번에 처리하는 것보다 거의 언제나 낫다는 것입니다. 사람의 취향을 한 번 적어 두면 모든 코드 줄에 계속 적용된다는 설명도 붙어 있습니다.

### 정리 작업은 이렇게 설계한다

청구 접수 저장소에 정리 작업을 건다면 저는 아래 정도의 설정으로 시작하겠습니다. 형식은 특정 도구의 것이 아니라 제가 구성한 예시입니다.

```yaml
# 예시: 주기 정리 작업 정의
jobs:
  - id: layer-violations
    schedule: "평일 02:00"
    detect: "구조 테스트를 전체 코드에 돌려 위반 목록 생성"
    action: "위반 1건당 PR 1개, 파일 3개 이하로 제한"
    max_open_prs: 5                  # 리뷰 여력을 넘지 않게 상한
    auto_merge: false                # 기간계에서는 사람 승인 유지
    record: docs/plans/tech-debt.md  # 남은 위반 수를 갱신

  - id: stale-docs
    schedule: "매주 월 03:00"
    detect: "docs/ 에서 언급한 클래스·메서드가 코드에 없는 경우"
    action: "문서 수정 PR, 코드 변경 없음"
    max_open_prs: 3
    auto_merge: false

  - id: pii-logging
    schedule: "매일 04:00"
    detect: "마스킹 유틸을 거치지 않은 개인정보 필드 로그 호출"
    action: "PR 대신 담당자에게 이슈 생성"   # 개인정보는 사람이 먼저 본다
```

설정에서 중요한 값은 `max_open_prs`입니다. 수거 작업이 리뷰어가 감당할 수 있는 양보다 많은 PR을 열면, 리뷰어는 내용을 보지 않고 승인하기 시작합니다. 그러면 정리 작업이 오히려 검토되지 않은 변경의 통로가 됩니다.

### 실패 모드와 비용: PR 홍수, 자동 병합, 의미 변경

수거 축이 세 축 중 가장 과소평가된다고 저는 봅니다. 가독성과 강제는 앞으로 들어올 코드에 작용합니다. 이미 들어와 있는 나쁜 예는 수거하지 않으면 계속 본보기로 남습니다.

동시에 가장 조심해야 할 축이기도 합니다. 정리 PR은 "동작은 그대로, 구조만 바꾼다"는 전제로 열리지만, 레거시 코드에서는 그 전제가 자주 깨집니다. 3년 전 컨트롤러의 SQL이 사실은 트랜잭션 경계를 일부러 바꾸려고 쓴 것일 수도 있습니다. 그래서 정리 PR에도 동작이 같다는 것을 보여 주는 테스트가 함께 있어야 하고, 테스트가 없는 영역은 먼저 테스트를 붙이는 작업이 수거보다 앞서야 한다고 봅니다.

## 5. 이 사례를 그대로 가져오면 안 되는 이유

숫자는 인상적입니다. 글에 따르면 빈 저장소의 첫 커밋은 2025년 8월 말이었고, 초기 골격도 GPT-5를 쓰는 Codex CLI가 만들었습니다. 5개월 뒤 저장소는 100만 줄 규모가 됐고, 그 기간에 약 1,500개의 PR이 병합됐습니다. 처음 세 명의 엔지니어로 시작해 엔지니어 한 명당 하루 평균 3.5개의 PR을 처리했고, 팀이 일곱 명으로 늘어나면서 처리량이 오히려 올랐다고 합니다. 손으로 썼다면 걸렸을 시간의 약 10분의 1로 만들었다고 추정한다는 문장도 있습니다.

그래도 읽을 때 걸러야 할 것이 있습니다.

### 벤더의 자기 사례이고, 기능 검증 이야기가 빠져 있다

Böckeler는 메모에서 OpenAI에게는 AI가 유지보수할 수 있는 코드를 우리가 믿게 만들 이해관계가 있다고 짚었습니다. 그리고 글에 설명된 장치들이 모두 장기적인 내부 품질과 유지보수성에 초점을 두고 있고, 기능과 동작의 검증 이야기는 빠져 있다고 지적했습니다.

이 지적은 실무적으로 중요합니다. 계층 규칙과 로깅 규칙을 완벽하게 지킨 코드도 청구 금액을 잘못 계산할 수 있습니다. 하네스의 세 축은 코드가 일관되게 쓰였는지를 지켜 주지만, 코드가 맞는 일을 하는지는 별도의 검증 체계가 지켜야 합니다.

### 빈 저장소에서 시작한 실험이다

OpenAI 스스로도 완전히 에이전트가 생성한 시스템에서 아키텍처 일관성이 몇 년에 걸쳐 어떻게 변하는지는 아직 모른다고 적었습니다. 사람의 판단이 어디서 가장 큰 효과를 내는지, 모델이 더 좋아지면 이 체계가 어떻게 바뀔지도 아직 배우는 중이라고 합니다.

Böckeler는 기존 코드베이스에 하네스를 나중에 덧입히는 일이 그만한 가치가 있는지 따져 봐야 한다고 적었습니다. 오래된 애플리케이션은 표준화되어 있지 않고 엔트로피가 많아, 정적 분석 도구를 한 번도 돌리지 않은 코드베이스에 처음 돌렸다가 경고에 파묻히는 상황을 떠올리게 한다는 것입니다.

### 병합 정책은 처리량이 만든 선택이다

그 저장소는 막는 병합 게이트를 최소로 두고, PR은 짧게 유지하며, 불안정한 테스트는 진행을 무기한 막기보다 후속 실행으로 처리한다고 합니다. 에이전트의 처리량이 사람의 주의력을 크게 넘는 시스템에서는 수정이 싸고 기다림이 비싸다는 논리입니다. 글은 이것이 처리량이 낮은 환경에서는 무책임한 선택일 것이라고 스스로 단서를 답니다.

리뷰 방식도 같은 전제 위에 있습니다. 같은 글은 사람이 PR을 검토할 수는 있지만 필수는 아니며, 시간이 지나면서 리뷰 대부분을 에이전트끼리 처리하는 쪽으로 옮겼다고 적습니다. 에이전트는 리뷰 피드백을 가져와 답하고, 자기 PR을 squash 병합하는 경우도 많다고 합니다.

이 단서를 지우고 앞부분만 가져오는 것이 가장 위험한 읽기라고 봅니다.

### 무엇을 가져올지 환경별로 고른다

| 요소 | 새 서비스, 내부 도구 | 레거시 기간계 (보험·금융) |
| --- | --- | --- |
| 짧은 지침 파일과 docs/ 구조 | 바로 도입 | 바로 도입, 기존 산출물에서 옮겨 오는 작업이 큼 |
| 앱과 관측 데이터의 에이전트 노출 | worktree별 로컬 스택 | 테스트 환경 한정, 운영 데이터는 제외 |
| 엄격한 계층 규칙과 구조 테스트 | 처음부터 | 새 모듈부터, 기존 위반은 목록화 후 단계적으로 |
| 커스텀 린트의 오류 메시지 개선 | 바로 도입 | 기존 정적 분석 규칙에 고치는 방법부터 붙임 |
| 주기 정리 PR | 자동 병합까지 검토 가능 | 사람 승인 유지, PR 수 상한 |
| 최소 병합 게이트 | 처리량이 충분히 높을 때만 | 가져오지 않음 |

### 보험·금융의 레거시 시스템에서는

보험이나 금융의 기간계는 OpenAI 사례와 정반대 조건입니다. 수정이 비쌉니다. 잘못 병합된 변경은 계약, 청구, 정산 데이터에 닿고, 되돌리는 데 데이터 보정과 보고가 따라옵니다.

반면 세 축은 오히려 이런 환경에서 더 쓸모가 있다고 생각합니다.

- 가독성: 오래된 Java/Oracle 시스템의 지식은 대부분 사람의 기억과 흩어진 산출물에 있습니다. 배치 간 선후 관계, 프로시저 호출 규약, 써서는 안 되는 테이블을 저장소 안 문서로 옮기는 일은 에이전트가 없어도 가치가 있습니다. 담당자가 바뀔 때마다 사라지던 지식이 남습니다.
- 강제: 이미 있는 정적 분석과 코드 인스펙션 규칙에 "고치는 방법"을 붙이는 것부터 시작할 수 있습니다. 새 도구를 들이는 것보다 결재가 쉽습니다.
- 수거: 정리 PR은 기존 결재선을 그대로 타면 됩니다. 에이전트는 찾고 제안하고, 승인은 사람이 합니다. 감사 관점에서도 "누가 무엇을 승인했는가"가 그대로 남습니다.

Böckeler의 메모에는 하네스가 미래의 서비스 템플릿이 될 수 있다는 관찰도 있습니다. 대부분의 조직은 주요 기술 스택이 두세 개뿐이므로, 흔한 애플리케이션 구조마다 커스텀 린터, 구조 테스트, 기본 문서를 묶은 하네스를 출발점으로 고르는 그림입니다. 다만 서비스 템플릿이 그랬듯, 팀마다 갈라진 하네스에 원본의 갱신을 다시 반영하는 동기화 문제가 생길 수 있다고 덧붙였습니다. 사내 표준 프레임워크를 관리해 온 조직이라면 익숙한 문제이고, 익숙한 만큼 미리 운영 방식을 정해 둘 수 있다고 봅니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 최근에 에이전트 출력을 손으로 고친 사례 다섯 건을 모읍니다. 각각을 가독성(몰랐다), 강제(막는 게 없었다), 수거(나쁜 본보기가 있었다) 중 어디의 문제였는지 분류하고, 두 번 이상 나온 것에 표시합니다.
2. 지침 파일을 100줄 안팎의 목차로 줄입니다. 상세 내용은 `docs/` 아래로 옮기고, 지침 파일에는 어디를 보라는 안내와 검증 명령만 남깁니다. 옮긴 뒤 새 세션에서 같은 작업을 시켜 재발 여부를 확인합니다.
3. 리뷰에서 두 번 이상 지적한 규칙 하나를 골라 린트 규칙이나 구조 테스트로 만듭니다. 먼저 기존 코드에 돌려 거짓 양성을 확인하고, 오류 메시지에 고치는 방법과 참고 문서 경로를 넣습니다. 규칙 파일의 변경은 별도 승인 대상으로 지정합니다.
4. 에이전트가 자기 변경을 확인할 수 있는 빠른 명령 하나를 만듭니다. 변경한 모듈의 테스트만 돌리는 스크립트, 접수 한 건을 넣어 결과 테이블을 확인하는 스크립트처럼 결과가 분명한 것이 좋습니다.
5. 정리 작업 하나를 주기 실행으로 겁니다. 코드와 맞지 않는 문서를 찾아 수정 PR을 여는 작업이 시작하기 쉽고, 열린 PR 수의 상한과 사람 승인을 처음부터 설정합니다.

## 마치며

Harness engineering이라는 이름은 새롭지만 요구하는 규율은 오래된 것입니다. 지식을 적어 두고, 규칙을 자동으로 검사하고, 어질러진 것을 치우는 일입니다.

에이전트는 이 세 가지가 빠진 자리를 사람처럼 눈치로 메우지 못하고, 그래서 빠진 자리가 그대로 출력 품질로 드러납니다.

에이전트의 출력을 고치고 싶어질 때, 출력이 아니라 환경의 어느 축이 비어 있었는지를 먼저 물어보시기를 권합니다.
