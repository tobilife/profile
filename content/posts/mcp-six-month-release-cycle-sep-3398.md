:::note
- MCP 메인테이너들이 2026년 11월 11일, 사양 릴리스를 3월과 9월 마지막 화요일의 6개월 주기로 옮긴다고 발표했습니다. 다음 릴리스 목표는 2027년 3월 30일입니다.
- 준비되지 않은 제안은 릴리스를 늦추지 않고 다음 주기로 넘어갑니다. 날짜가 고정이고 범위가 변수입니다.
- 릴리스 2.5개월 전 소프트 프리즈, 1.5개월 전 Tier 1 SDK 베타, 1개월 전 하드 프리즈가 하네스 팀이 호환성을 시험할 수 있는 창입니다.
- 7월 개정에서 들어온 폐기 정책과 겹치면, 폐기 예정 기능이 가장 이르게 사라질 수 있는 릴리스가 달력 위에 놓입니다. 지금 운영 중인 클라이언트와 서버를 당장 바꿀 것은 없습니다.
:::

"MCP는 표준이니까 한 번 붙여 두면 계속 돌아간다"고 생각하기 쉽습니다.

메시지 형식만 보면 그렇습니다. 하지만 MCP는 날짜로 버전을 매기는 살아 있는 사양이고, 개정 때마다 무언가가 추가되고 무언가가 사라집니다.

**하네스에 MCP 서버를 여러 개 붙여 운영하는 팀의 실제 문제는 프로토콜이 바뀐다는 사실이 아니라, 언제 무엇이 바뀔지 미리 알 수 없었다는 점입니다.**

그 부분이 이번에 달라졌습니다. MCP 블로그는 2026년 11월 11일 사양 릴리스를 정기적인 6개월 일정으로 옮긴다고 발표했고 [\[MCP Blog: A More Predictable Release Cycle for MCP\]](https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/), 그 절차는 SEP-3398에 문서로 정리되어 있습니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md).

이 글은 새 일정이 무엇을 정했는지, 그리고 7월 개정에서 이미 들어온 폐기 정책과 합쳐졌을 때 하네스 팀의 업그레이드 계획이 어떻게 바뀌는지를 봅니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사의 사내 에이전트 하네스에 MCP 서버 열두 개가 붙어 있다고 해봅시다. 계약 조회처럼 사내 팀이 만든 것, 문서 검색처럼 외부 벤더가 제공하는 것, 오픈소스를 그대로 띄운 것이 섞여 있습니다.

어느 날 새 사양 개정이 나오고, 서버 몇 개가 각자의 일정으로 SDK를 올립니다. 클라이언트 쪽 하네스는 아직 이전 버전입니다.

대부분은 버전 협상으로 문제없이 지나갑니다. 그런데 한 서버가 이전 방식의 기능을 정리하면서, 그 기능에 기대던 워크플로 하나가 조용히 동작을 바꿉니다. 예컨대 서버가 클라이언트에게 모델 호출을 대신 부탁하던 경로가 사라져, 문서 요약 단계가 빈 결과를 내기 시작하는 식입니다.

시스템 설계 용어로 짚으면, 프로토콜 버전이 관리되는 의존성이 아니라 각 구성 요소가 알아서 올리는 암묵적 상태였습니다. 어떤 조합이 시험된 조합인지 아무도 말할 수 없었습니다.

일정이 없으면 이런 관리 자체가 어렵습니다. 언제 시험해야 하는지를 알 수 없기 때문입니다.

## 1. 날짜가 먼저 정해지고, 기능이 그 날짜에 맞춥니다

### 발표의 핵심

발표의 핵심은 두 문장입니다. 사양 릴리스를 대체로 3월과 9월의 마지막 화요일에 내고, 준비되지 않은 제안은 전체 사양을 늦추는 대신 다음 릴리스로 넘긴다는 것입니다 [\[MCP Blog: A More Predictable Release Cycle for MCP\]](https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/).

다음 릴리스의 목표일은 2027년 3월 30일이고, 버전 이름은 `2027-03-30`이 될 예정입니다. 발표문에 실린 일정 그림에는 그다음 목표로 2027년 9월 28일도 표시되어 있습니다. 발표문은 릴리스 날짜와 함께 제안 마감일과 SDK 베타 날짜도 공유해, 구현하고 시험하는 쪽이 거꾸로 계획을 세울 수 있게 하겠다고 적고 있습니다.

SEP-3398에 따르면 이것은 원래 2026년 12월을 목표로 하던 릴리스를 3월 말로 옮기는 것이기도 합니다. 직전 릴리스는 2026년 7월 28일이었습니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md).

### 어떻게 정해졌는가

SEP-3398은 2026년 9월 17일에 만들어졌고, 10월 14일에 마감된 투표에서 투표 자격자 8명 중 7명이 참여해 전원 찬성으로 수락됐습니다 [\[MCP: SEP-3398 투표 결과\]](https://voting.modelcontextprotocol.io/p/v98cy36vp5). 발표문은 코어 메인테이너들이 MCPCon Europe에서 이 질문들을 함께 다뤘고, 그 결과를 SEP-3398로 정리했으며 이것이 앞으로의 릴리스 지침이라고 설명합니다.

### 늦은 제안은 어떻게 되는가

소프트웨어 릴리스 관리에서는 익숙한 방식입니다. 범위를 고정하고 날짜를 미루는 대신, 날짜를 고정하고 범위를 조절합니다. 사용하는 쪽에서는 기능 목록보다 날짜가 확실한 편이 계획하기 쉽습니다.

SEP는 넘어가는 제안의 처리도 정해 둡니다. 수락됐지만 마감까지 완성되지 못한 제안은 Accepted 상태를 유지한 채 다음 릴리스 후보로 추적되고, 넘어갔다는 이유만으로 수락 투표를 다시 할 필요는 없습니다. 다만 설계가 크게 바뀌면 다시 검토를 받습니다.

하네스 팀에게 이것은 로드맵을 읽는 방법이 달라진다는 뜻입니다. "수락됨"은 "다음 릴리스에 들어감"이 아닙니다. 들어갈지는 소프트 프리즈 시점의 범위 목록이 정합니다.

### 필요한 기능이 있다면 언제 말해야 하는가

SEP-3398은 각 SEP를 워킹 그룹이나 코어 메인테이너 그룹이 후원하도록 하고, 제안 작업은 연중 계속되지만 모든 유형의 SEP가 정해진 코어 메인테이너 리뷰 기간을 쓰도록 정합니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md).

하네스 팀이 프로토콜에 바라는 것이 있다면, 예컨대 첫머리 시나리오처럼 서버가 쓰는 기능을 클라이언트가 미리 알 수 있는 방법이 필요하다면, 말할 때가 정해진 셈입니다. 릴리스 8개월 전의 계획 단계에서 관련 워킹 그룹에 의견을 내고, 6개월 전부터 열리는 리뷰 기간 안에 SEP가 심사받게 하는 것입니다. 소프트 프리즈가 지나면 그 릴리스에는 들어갈 수 없고, 다음 주기로 넘어갑니다.

저는 이것이 일정의 숨은 효과라고 봅니다. 쓰는 쪽도 언제 영향력을 행사할 수 있는지 알게 됩니다.

### 새로 생긴 역할: 릴리스 매니저

릴리스마다 주 릴리스 매니저와 보조 릴리스 매니저를 두고, 보조가 다음 주기에 주 매니저가 되는 구조입니다. 주 매니저는 릴리스 일정, 리뷰 일정, 범위 추적, 프리즈 조정, SDK 준비 상태, 공개와 소통을 맡습니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md). 발표문은 다음 사양 주기에 새로 합류하는 릴리스 매니저도 소개합니다.

하네스 팀 입장에서는 일정과 범위에 대해 물을 창구가 생긴 셈입니다.

### 날짜 고정의 비용

날짜를 고정하면 생기는 비용도 있습니다. 기다리던 기능이 소프트 프리즈를 놓치면 다음 릴리스까지 6개월을 더 기다려야 합니다. 예전처럼 "준비되면 나온다"였다면 몇 주 늦게라도 들어왔을 기능이, 이제는 한 주기를 통째로 건너뛸 수 있습니다.

이 공백을 메우는 경로로 확장(extension)이 있습니다. 7월 개정은 실험적이던 tasks를 코어 프로토콜에서 빼 공식 확장(`io.modelcontextprotocol/tasks`)으로 옮겼고, 기능 협상에 쓰는 capability에 `extensions` 필드를 추가했습니다 [\[MCP: 2026-07-28 Key Changes\]](https://modelcontextprotocol.io/specification/2026-07-28/changelog). 다만 SDK 등급 정책은 실험적 기능과 확장을 어느 등급에도 요구하지 않습니다 [\[MCP: SDK Tiers\]](https://modelcontextprotocol.io/community/sdk-tiers). SEP-3398도 SDK 베타 마일스톤이 확장을 Tier 1의 의무로 만들지 않는다고 적습니다.

하네스 팀 입장에서 정리하면, 코어 사양의 기능은 달력을 따라 오고 Tier 1 SDK가 따라온다는 약속이 있지만, 확장으로 오는 기능은 SDK마다 지원 시점이 따로라는 뜻입니다. 인벤토리에 서버가 쓰는 확장도 함께 적어 두는 편이 좋다고 봅니다.

### 바뀌지 않는 것

발표문은 한 가지를 분명히 해 둡니다. 이번 변화는 릴리스를 준비하는 방법에 관한 것이지 MCP 메시지나 버전 협상을 바꾸는 것이 아니므로, 이 발표 때문에 기존 클라이언트나 서버에서 바꿀 것은 없다는 것입니다. 사양 버전은 계속 날짜로 표기됩니다.

## 2. 소프트 프리즈와 SDK 베타가 하네스 팀의 시험 창입니다

하네스를 만드는 입장에서 더 쓸모 있는 것은 릴리스 날짜 자체보다 그 앞의 중간 지점들입니다.

### 8개월짜리 주기의 마일스톤

SEP-3398은 각 주기가 목표 릴리스 8개월 전에 시작하고, 앞의 두 달은 계획에, 마지막 두 달은 다음 릴리스의 계획과 겹친다고 정합니다. 마일스톤은 릴리스 기준 개월 수로 표시하고, 정확한 날짜는 주기마다 공개하는 일정표가 정합니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md).

| 시점(릴리스 기준) | 일어나는 일 | 하네스 팀이 할 수 있는 일 |
| --- | --- | --- |
| 8개월 전 | 계획 시작. 로드맵 제안, 메인테이너와 워킹 그룹의 의견 수렴 | 로드맵에서 영향받을 기능을 훑어봄 |
| 6개월 전 | 코어 메인테이너 리뷰 시작, 우선순위 공개 | 관심 있는 SEP의 진행을 추적, 필요하면 의견 제출 |
| 2.5개월 전 | 소프트 프리즈. 범위를 Final이고 병합된 SEP로 고정 | 확정된 변경 목록으로 영향 분석 |
| 2개월 전 | 다음 주기 계획 시작 | 그다음 릴리스의 로드맵 확인 |
| 1.5개월 전 | Tier 1 SDK 베타 공개 | 베타 SDK로 호환성 시험, 문제 보고 |
| 1개월 전 | 하드 프리즈. 사양 변경은 비상 상황으로 제한 | 시험 결과 확정, 전환 일정 수립 |
| 릴리스 당일 | 사양, 릴리스 노트, 구현과 이전 안내, SDK 준비 상태 요약 공개 | 계획대로 전환 시작 |

왼쪽 두 열은 SEP의 표를 옮긴 것이고, 오른쪽 열은 제 해석입니다.

### 소프트 프리즈의 조건은 꽤 엄격합니다

SEP-3398은 소프트 프리즈 시점에 릴리스에 들어갈 모든 SEP가 Final이고 병합되어 있어야 한다고 정하고, 그 범위에 사양 본문, 해당하는 스키마 변경, 변경 이력 항목, 완성된 참조 구현, 그리고 적합성 테스트 요구 SEP가 정한 테스트까지 포함시킵니다. 수락만으로는 마감을 넘지 못합니다. 릴리스 매니저는 고정된 범위와 미뤄진 제안을 공개하고, 그 뒤 하드 프리즈까지는 범위 안의 버그 수정, 다듬기, 설명 보완만 받습니다.

SEP는 그 이유도 적습니다. Final이고 병합된 SEP만 받아야 SDK 메인테이너가 구현하고 시험할 구체적인 사양을 갖게 된다는 것입니다.

즉 소프트 프리즈 시점의 변경 목록은 "논의 중"이 아니라 "구현이 존재하는" 목록입니다. 영향 분석을 그때 시작해도 헛수고가 될 가능성이 낮습니다.

### SDK 베타 뒤의 보름

Tier 1 SDK는 릴리스 1.5개월 전에 고정된 범위를 지원하는 베타를 내고, 이것으로 클라이언트와 서버 개발자는 하드 프리즈 전까지 보름 동안 문제를 보고할 수 있습니다. 베타 릴리스 노트에는 목표 사양, 사용 가능한 기능, 알려진 공백, 피드백 창구가 들어갑니다. 릴리스 매니저는 SDK 버전, 적합성 결과, 공백, 담당자, 예상 해결일을 담은 준비 상태 요약을 공개적으로 관리합니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md).

보름은 짧습니다. 하네스 팀이 이 창을 쓰려면 베타가 나오는 날 바로 돌릴 수 있는 회귀 테스트가 미리 준비되어 있어야 합니다. 4절의 인벤토리와 테스트가 그 준비입니다.

### 하드 프리즈 이후

하드 프리즈 이후 사양 변경은 코어 메인테이너 전체 투표를 거쳐야 하고, 대상은 치명적 보안 취약점이나 릴리스를 막는 정확성 또는 상호운용성 결함으로 한정됩니다. 기능 추가나 재량적 재설계는 해당하지 않습니다.

하네스 팀에게는 하드 프리즈 이후의 사양이 사실상 최종본이라는 뜻입니다. 이 시점부터 전환 계획을 확정해도 됩니다.

예외 절차도 꽤 무겁게 정해져 있습니다. 주 릴리스 매니저가 결함이 비상 기준에 맞는지 확인하고, 왜 기다릴 수 없는지, 가장 작은 수정안이 무엇인지, SDK와 릴리스 산출물에 어떤 영향이 있는지를 문서로 남긴 뒤 투표를 엽니다. 병합 전에는 영향받는 구현 메인테이너의 리뷰와 회귀 및 적합성 검사를 거치고, 결과는 SDK 메인테이너에게 알리고 준비 상태 요약과 릴리스 노트에 반영합니다 [\[MCP: SEP-3398 Release Cycle Updates\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/99a8e4605c4278b6f905c98e585f98b393b15623/seps/3398-release-cycle-updates.md).

보안 수정에는 단서가 하나 붙습니다. SEP는 공개 큐와 릴리스 노트가 엠바고 중인 취약점의 세부 내용을 너무 일찍 드러내서는 안 된다고 적습니다. 릴리스 직전에 들어온 보안 수정은 이유가 나중에야 설명될 수 있다는 뜻으로 읽힙니다. 하네스 팀은 그런 변경을 "설명이 부족하니 미룬다"가 아니라 "보안 수정이니 우선 적용한다"로 다루는 기준을 미리 정해 두는 편이 좋다고 봅니다.

### SDK가 늦어지면

SDK가 늦어지는 경우에 대한 원칙도 있습니다. 발표문은 Tier 1 SDK가 릴리스 전에 안정 버전을 내야 하지만, 늦어지더라도 사양 릴리스 날짜는 움직이지 않고 그 격차를 문서로 남긴다고 설명합니다 [\[MCP Blog: A More Predictable Release Cycle for MCP\]](https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/). SEP는 베타나 안정판 마일스톤을 놓치면 코어 메인테이너와 SDK 워킹 그룹에 올리고 릴리스 안내에 공개하되, 개별 SDK의 지연이 사양 공개를 미루거나 그 SDK의 등급을 자동으로 바꾸지는 않는다고 적습니다.

등급의 의미는 SDK 등급 정책에 있습니다. Tier 1은 적합성 테스트 100% 통과와 새 사양 버전 릴리스 전의 새 기능 지원을, Tier 2는 80% 통과와 6개월 안의 지원을 요구하고, Tier 3에는 시간 약속이 없습니다 [\[MCP: SDK Tiers\]](https://modelcontextprotocol.io/community/sdk-tiers).

| 쓰는 SDK | 릴리스 당일 기대할 수 있는 것 | 하네스 팀의 계획 |
| --- | --- | --- |
| Tier 1 | 안정판 지원, 늦으면 준비 상태 요약에 공개 | 베타로 시험, 릴리스 후 전환 |
| Tier 2 | 릴리스 후 6개월 안 지원 약속 | 그 SDK의 로드맵을 따로 추적, 전환을 한 주기 늦게 잡음 |
| Tier 3 | 약속 없음 | 해당 서버를 버전 고정 대상으로 두고 대체 경로 검토 |

오른쪽 열은 제 의견입니다.

### 첫 주기는 조금 다릅니다

다가오는 3월 릴리스는 전환 주기입니다. 발표문은 이번 릴리스의 계획 일부가 이미 올해 8월에 끝났다고 적고 [\[MCP Blog: A More Predictable Release Cycle for MCP\]](https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/), SEP도 첫 주기는 2026년 8월에 마친 계획을 쓰고, 전환 일정표가 절차가 가동되는 시점에 첫 리뷰 기간을 열어 3월 릴리스의 소프트 프리즈에서 닫는다고 정합니다. 안건 공지와 투표 기간을 온전히 확보할 수 있는 회의만 잡는다는 조건도 붙어 있습니다.

제 해석으로는, 3월 릴리스의 리뷰 기간은 정상 주기의 3.5개월(6개월 전부터 2.5개월 전까지)보다 짧아질 가능성이 큽니다. 3월에 들어갈 변경은 이미 상당 부분 논의가 진행된 것들일 가능성이 높고, 하네스 팀은 지금 열려 있는 SEP 목록을 보는 것만으로도 3월 범위를 어느 정도 가늠할 수 있다고 봅니다.

SEP는 이 과정 자체를 점검하는 장치도 둡니다. 새 절차의 첫 릴리스가 끝나면 릴리스 매니저가 리뷰 대기 시간, 소프트 프리즈 시점의 준비 상태, SDK 베타의 가용성, 비상 변경, 겹치는 기간의 업무량을 다룬 회고를 공개하도록 되어 있습니다. 3월 이후 이 회고를 읽으면, 9월 일정을 얼마나 믿고 계획할지 판단할 근거가 생깁니다.

### 3월 30일 기준의 대략적 위치

참고로 SEP의 개월 수 오프셋을 2027년 3월 30일에 기계적으로 적용하면, 소프트 프리즈는 1월 중순, SDK 베타는 2월 중순, 하드 프리즈는 2월 말 무렵이 됩니다. **이것은 제가 단순히 계산한 값이며 공식 일정이 아닙니다.** SEP는 수락 후 2주 안에 선출된 릴리스 매니저가 프리즈, 베타, 릴리스의 정확한 마감을 담은 전환 일정표를 공개한다고 정하고 있으니, 날짜는 그 일정표로 확인해야 합니다. 한편 SEP는 2027년 9월 릴리스의 계획이 2027년 1월 말에 시작된다고 명시합니다.

## 3. 폐기 정책과 합치면 업그레이드 달력이 나옵니다

릴리스 주기만으로는 절반입니다. 나머지 절반은 직전 개정에서 이미 들어왔습니다.

### 기능의 세 가지 상태

2026-07-28 개정은 기능의 상태를 Active, Deprecated, Removed로 정의하고 최소 12개월의 폐기 유예 기간을 두는 수명 주기 정책을 채택했습니다 [\[MCP: 2026-07-28 Key Changes\]](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

정책 문서는 각 상태에서 구현하는 쪽에 기대하는 바를 이렇게 정리합니다 [\[MCP: Feature Lifecycle and Deprecation\]](https://modelcontextprotocol.io/community/feature-lifecycle).

| 상태 | 의미 | 구현하는 쪽에 기대하는 것 |
| --- | --- | --- |
| Active | 현재 사양 개정의 일부 | 규범 요구 사항대로 구현 |
| Deprecated | 사양에 남아 있지만 제거 예정, 이전 경로가 문서화됨 | 새 구현은 채택하지 않음, 기존 구현은 가장 이른 제거 시점 전에 이전 |
| Removed | draft에서 삭제되어 다음 현재 개정에 없음 | 그 개정을 목표로 하는 구현은 이 기능에 의존하지 않음 |

### 가장 이른 제거 시점은 어떻게 정해지는가

같은 문서에 따르면 폐기 SEP는 최소 12개월 이상의 유예 기간을 정해야 하고, 기능의 가장 이른 제거 시점은 그 기간이 지난 날 또는 그 이후에 현재 개정으로 공개되는 첫 사양 개정입니다. 활성 보안 위험이 있으면 코어 메인테이너 승인으로 기간을 줄일 수 있지만, 그 경우에도 폐기와 가장 이른 제거 사이에 최소 90일은 남겨야 합니다.

7월 개정에서는 Roots, Sampling, Logging 기능이 폐기 예정으로 분류됐습니다. 유예 기간 동안은 그대로 동작하지만 새 구현은 이를 채택하지 말라는 안내와 함께 대안이 제시되어 있습니다. Roots 대신 도구 매개변수나 리소스 URI, 서버 설정으로 디렉터리와 파일을 넘기고, Sampling 대신 LLM 공급자 API와 직접 연동하고, Logging 대신 stdio에서는 `stderr`로 쓰거나 OpenTelemetry를 쓰라는 것입니다 [\[MCP: 2026-07-28 Key Changes\]](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

폐기 기능 목록에는 이 세 기능과 Dynamic Client Registration의 가장 이른 제거 시점이 "2027년 7월 28일 또는 그 이후에 공개되는 첫 개정"으로 적혀 있습니다. 같은 목록은 이것이 제거 가능해지는 시점일 뿐이고, 실제 제거는 릴리스를 준비하며 코어 메인테이너가 결정하므로 더 늦어질 수 있다고 밝힙니다 [\[MCP: Deprecated Features (2026-07-28)\]](https://modelcontextprotocol.io/specification/2026-07-28/deprecated).

### 더 먼저 살펴볼 항목

같은 목록에는 일정이 다른 항목도 있습니다. HTTP+SSE 전송 방식은 `2025-03-26` 버전부터 폐기 예정이었고, 7월 개정에서 새 정책 아래의 Deprecated로 다시 분류되면서 가장 이른 제거 시점이 "SEP-2596이 Final이 된 뒤 3개월"로 적혀 있습니다. Sampling 요청의 `includeContext` 값 일부는 Sampling의 일정을 따릅니다 [\[MCP: Deprecated Features (2026-07-28)\]](https://modelcontextprotocol.io/specification/2026-07-28/deprecated).

하네스에 오래된 서버가 붙어 있다면, Roots나 Sampling보다 전송 방식부터 확인하는 편이 좋다고 봅니다. 기준 시점이 다르기 때문에, 가장 먼저 제거 후보가 되는 것이 이쪽일 수 있습니다.

### 두 정책을 겹쳐 놓으면

두 정책을 겹쳐 놓으면 계획의 뼈대가 생깁니다.

```text
2026-07-28  개정 릴리스 (무상태 코어, Roots/Sampling/Logging 등 Deprecated 지정)
     │
     │  최소 12개월 유예
     │
2027-03-30  다음 정기 릴리스 목표 (SEP-3398) ── 유예 기간 안. 제거 대상 아님
     │
2027-07-28  유예 기간이 끝나는 날
     │
2027-09-28  그다음 정기 릴리스 목표 ── 위 기능들이 제거될 수 있는 첫 후보
```

그림은 세 문서의 날짜와 규칙을 제가 한 줄로 이어 본 것입니다. 9월 릴리스가 첫 후보라는 것은 "유예 기간 이후 첫 개정"이라는 규칙과 3월, 9월이라는 일정을 합쳐 제가 도출한 것이고, 실제로 그 릴리스에서 제거될지는 알 수 없습니다.

그래도 차이는 큽니다. 예전에는 "언젠가 없어진다"였던 것이, 이제는 "가장 이르면 어느 정기 릴리스"로 좁혀집니다.

### SDK 쪽의 신호

정책 문서는 Tier 1 SDK에도 의무를 둡니다. 기능이 Deprecated가 된 개정이 현재 개정으로 공개되면, 다음 릴리스에서 해당 API를 언어 고유의 방식(Java의 `@Deprecated`, TypeScript의 `@deprecated` JSDoc 등)으로 표시해야 하고, 폐기된 기능이 실제로 쓰일 때 런타임 경고를 내는 것이 권장됩니다. 다만 사양에서 제거되었다고 SDK가 그 기능을 바로 빼야 하는 것은 아니고, 그 시기는 SDK 자체의 개정 지원 정책이 정합니다 [\[MCP: Feature Lifecycle and Deprecation\]](https://modelcontextprotocol.io/community/feature-lifecycle).

정책 문서는 폐기 기능을 꾸준히 드러내지 않는 Tier 1 SDK를 등급 강등 대상으로 둡니다. 하네스 팀에게 이것은 공짜 탐지기입니다. Tier 1 SDK를 올린 뒤 빌드 경고와 런타임 경고를 모으면, 우리 코드와 서버가 어떤 폐기 기능을 쓰고 있는지 목록이 나옵니다.

### 7월 개정의 크기

참고로 2026-07-28 개정은 변화 폭이 컸습니다. 프로토콜 수준의 세션과 `initialize` 핸드셰이크를 없애고 요청마다 프로토콜 버전과 클라이언트 기능을 `_meta`에 싣는 무상태 구조로 바뀌었고, 서버가 지원 버전과 기능을 알리는 `server/discover`가 필수가 됐습니다. 서버가 `tools/list`의 도구를 결정적인 순서로 돌려주도록 권장하는 항목도 들어갔는데, 클라이언트 쪽 캐싱과 LLM 프롬프트 캐시 적중률을 높이기 위해서라고 설명되어 있습니다 [\[MCP: 2026-07-28 Key Changes\]](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

이 정도의 변경이 예고된 일정 없이 오는 것과 달력 위에서 오는 것은 준비의 질이 다릅니다.

## 4. 하네스에서는 프로토콜 버전을 설정값으로 끌어올립니다

### 서버 인벤토리

일정이 생겼으니 이제 관리할 수 있습니다. 제가 권하는 것은 서버별 프로토콜 버전을 하네스의 설정과 테스트에 명시하는 것입니다.

```yaml
# 예시: MCP 서버 인벤토리 (특정 제품의 문법이 아닙니다)
mcp_servers:
  - name: contracts-readonly
    owner: 계약팀
    sdk: { language: java, tier: 1 }
    protocol_versions: ["2025-11-25", "2026-07-28"]   # server/discover가 알린 버전
    pinned: "2026-07-28"                               # 하네스가 시험을 마친 버전
    deprecated_features_in_use: []
  - name: legacy-docs
    owner: 외부 벤더
    sdk: { language: python, tier: 2 }
    protocol_versions: ["2025-11-25"]
    pinned: "2025-11-25"
    deprecated_features_in_use: ["sampling"]           # 2027-07-28 이후 첫 개정 전에 걷어낼 대상
upgrade_window:
  target_release: "2027-03-30"
  test_from: "Tier 1 SDK 베타 공개일 (전환 일정표로 확정)"
  freeze_from: "하드 프리즈일"
  rule: "pinned 조합에 대한 회귀 테스트가 통과한 서버만 전환"
```

여기서 `pinned`가 핵심입니다. 서버가 지원하는 버전과 하네스가 시험한 버전을 구분해 적어 두면, 첫머리 시나리오의 "어떤 조합이 시험된 조합인가"에 답할 수 있습니다.

`deprecated_features_in_use` 칸은 폐기 예정 기능에 대한 부채 목록입니다. 유예 기간이 12개월 이상이라는 것은 여유가 있다는 뜻이지 미뤄도 된다는 뜻이 아닙니다. `sdk.tier` 칸은 2절의 표에 따라 전환 시점을 정하는 근거가 됩니다.

### 버전 불일치는 어디서 드러나는가

7월 개정 이후에는 버전 불일치가 드러나는 자리가 분명해졌습니다. 요청마다 프로토콜 버전이 실리고, 맞지 않으면 `UnsupportedProtocolVersionError`가 돌아옵니다. 클라이언트는 다른 요청 전에 `server/discover`를 불러 버전을 미리 고를 수 있고, stdio에서는 이전 버전과의 호환을 확인하는 탐침으로도 쓸 수 있습니다 [\[MCP: 2026-07-28 Key Changes\]](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

하네스에서는 이 오류를 일반 도구 실패와 섞지 말고 따로 세는 편이 좋습니다. 첫머리 시나리오처럼 조용히 동작이 바뀌는 경우는 이 오류로 잡히지 않지만, 서버가 버전을 올리면서 하네스가 따라가지 못한 경우는 이 숫자가 먼저 알려 줍니다. 연결 시점의 `server/discover` 결과를 인벤토리와 비교하는 것과 함께 두면, 버전 변화는 대부분 사람이 알아채기 전에 잡힙니다. 남는 것은 버전은 같은데 동작이 바뀌는 경우이고, 그것을 잡는 것이 다음의 회귀 테스트입니다.

### 회귀 테스트는 세 겹이면 충분합니다

회귀 테스트는 거창할 필요가 없습니다. 서버마다 세 가지를 기록해 두는 것으로 시작할 수 있습니다.

```text
1. 탐색      server/discover 응답: 지원 버전, 기능, 서버 정보
2. 목록      tools/list, resources/list 응답의 스냅샷 (이름, 스키마)
3. 대표 호출 업무상 중요한 도구 호출 3~5개의 입력과 출력 형태
        │
        v
새 SDK 베타나 새 서버 버전에서 같은 세 가지를 다시 기록하고 차이를 비교
```

7월 개정이 `tools/list`의 결정적 순서를 권장한 것은 이 비교에도 도움이 됩니다. 순서가 매번 바뀌면 스냅샷 비교가 잡음으로 가득 차지만, 순서가 고정되면 차이가 곧 변경입니다.

첫머리 시나리오의 문서 요약 단계라면, 대표 호출에 요약 도구를 넣어 두는 것만으로 "빈 결과"가 베타 시험 단계에서 드러났을 것입니다.

### 한 주기의 전환 절차

인벤토리와 회귀 테스트가 있으면, 한 주기의 전환은 매번 같은 순서로 돌릴 수 있습니다.

```text
(예시) 2027-03-30 릴리스에 대한 하네스 팀의 전환 절차

소프트 프리즈  고정된 범위 목록을 받아 서버별 영향 여부를 표시
     │
SDK 베타      스테이징 하네스의 클라이언트 SDK를 베타로 올리고, 서버별 세 겹 회귀 테스트 실행
     │        문제는 하드 프리즈 전 보름 안에 SDK 저장소에 보고
하드 프리즈    결과를 확정하고 변경 승인 요청서 작성 (기준 버전 = 하드 프리즈 시점 사양)
     │
릴리스        Tier 1 안정판으로 교체, 준비 상태 요약에서 쓰는 SDK의 공백 확인
     │
동결 해제 후   운영 전환, 서버별 pinned 갱신, 폐기 경고 목록 갱신
```

하드 프리즈 이후에도 치명적 보안 수정은 투표를 거쳐 들어올 수 있으므로, 승인 요청서의 기준 버전과 실제 릴리스 사이에 차이가 있는지 릴리스 노트로 한 번 더 확인하는 단계를 두는 편이 안전합니다.

### 실패 모드

인벤토리의 가장 흔한 실패는 낡는 것입니다. 서버 팀이 버전을 올리고 인벤토리를 고치지 않으면, `pinned`는 거짓말이 됩니다. 그래서 저는 하네스가 연결할 때마다 `server/discover` 결과를 인벤토리와 비교하고, 다르면 경고를 내게 하는 편을 권합니다.

다른 실패는 범위입니다. 모든 서버를 매 릴리스마다 따라가려 하면 팀의 시간이 모자랍니다. 업무상 중요한 서버만 베타 창에서 시험하고, 나머지는 릴리스 후 한 주기 늦게 따라가는 식으로 등급을 나누는 편이 현실적입니다.

마지막 실패는 등급을 한 번 적고 잊는 것입니다. SDK의 등급은 고정된 값이 아니라 SDK 워킹 그룹이 운영하는 정책에 따라 오르내릴 수 있습니다. 인벤토리의 `sdk.tier`는 릴리스 주기마다 SDK 목록 페이지와 대조해 갱신하는 편이 좋습니다.

### 보수적인 조직이라면

보험이나 금융 IT에는 대개 분기 말과 연말의 변경 동결 기간이 있고, 외부 의존성의 변경은 영향 분석과 승인을 거칩니다.

지금까지 MCP는 그런 절차에 태우기 까다로운 의존성이었다고 봅니다. 다음 개정이 언제 나올지 모르면 영향 분석 일정을 잡을 수 없기 때문입니다.

3월 말과 9월 말이라는 고정된 날짜는 이 점에서 반가운 변화입니다. 다만 두 날짜 모두 분기 말과 겹칩니다. 릴리스 당일에 따라가려 하기보다, SDK 베타가 나오는 시점에 시험을 시작하고 전환은 동결 기간이 끝난 뒤로 잡는 편이 현실적이라고 생각합니다. 소프트 프리즈의 범위 목록은 영향 분석서의 근거 자료로, 하드 프리즈 이후의 사양은 변경 승인 요청서의 기준 버전으로 쓸 수 있습니다.

외부 벤더가 제공하는 MCP 서버를 쓴다면, 계약이나 운영 협의에 지원 프로토콜 버전, 사용하는 SDK와 그 등급, 폐기 예정 기능의 이전 일정을 묻는 항목을 넣어 둘 만합니다.

여기에 한 가지를 더하고 싶습니다. 벤더에게 SDK 베타 기간의 시험 결과를 공유해 달라고 요청하는 것입니다. 릴리스 매니저가 공개하는 준비 상태 요약이 SDK 수준의 상태를 알려 준다면, 벤더의 시험 결과는 그 SDK 위에 올린 서버 수준의 상태를 알려 줍니다. 두 문서를 나란히 놓으면 영향 분석서의 빈칸이 대부분 채워집니다. 사내 서버 팀에게도 같은 양식을 쓰면, 서버 열두 개의 준비 상태를 한 표로 볼 수 있습니다.

## 5. 오늘 바로 적용할 수 있는 순서

1. 하네스에 붙은 MCP 서버를 전부 적고, 서버마다 지원 프로토콜 버전, 쓰는 SDK와 그 등급, 담당자를 기록합니다.
2. 각 서버와 클라이언트가 Roots, Sampling, Logging처럼 폐기 예정인 기능을 쓰고 있는지 확인하고, Tier 1 SDK의 폐기 경고를 모아 목록과 대조합니다.
3. 서버별로 탐색 응답, 목록 스냅샷, 대표 호출 몇 개를 회귀 테스트로 저장합니다.
4. 릴리스 매니저가 공개하는 전환 일정표의 소프트 프리즈, SDK 베타, 하드 프리즈 날짜를 팀 달력에 넣습니다. 공개 전까지는 개월 수 오프셋으로 계산한 임시 날짜를 쓰되, 임시라고 표시해 둡니다.
5. 2027년 7월 28일 이후 첫 개정, 즉 일정상 가장 이르면 9월 릴리스 전까지 폐기 기능을 걷어내는 계획을 세웁니다.

## 마치며

이번 발표에는 새 기능이 하나도 없습니다. 그래서 지나치기 쉽습니다.

하지만 여러 팀과 벤더의 서버를 묶어 운영하는 입장에서는, 기능 하나보다 예측 가능한 달력이 더 큰 도움이 될 때가 많습니다.

프로토콜 업그레이드를 닥쳐서 대응하는 사건이 아니라 반기마다 돌아오는 정기 작업으로 만들 수 있게 됐습니다. 그 준비는 서버 목록을 적는 것에서 시작합니다.
