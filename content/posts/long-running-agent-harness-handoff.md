:::note
- 긴 작업에서 에이전트는 세션마다 기억 없이 시작합니다. compaction은 대화를 이어 줄 뿐, 작업이 지금 어떤 상태인지는 보증하지 않습니다.
- 첫 세션은 환경을 준비하고, 이후 세션은 기능 하나씩 전진합니다. 같은 에이전트라도 두 세션에 주는 프롬프트가 달라야 하고, 어느 쪽을 줄지는 하네스가 파일로 판단합니다.
- 완료의 정의는 기능 목록 파일에 고정하고, 통과 여부는 사용자처럼 수행한 테스트로만 바꿉니다. 그 규칙이 지켜졌는지는 하네스가 확인합니다.
- 세션은 언제나 병합 가능한 상태로 끝나야 하고, 다음 세션은 정해진 순서로 상태를 파악하며 시작해야 합니다. 사람이 지켜보지 않는 실행일수록 권한과 승인 지점을 먼저 설계합니다.
:::

에이전트에게 며칠짜리 일을 맡기는 이야기가 나오면 대개 이런 답이 돌아옵니다. "컨텍스트 윈도우도 커졌고 자동 요약도 있으니 그냥 계속 돌리면 된다"는 것입니다.

돌리는 것은 됩니다. 일이 앞으로 가느냐가 문제입니다. **여러 컨텍스트 윈도우에 걸친 작업에서 진행 상태는 모델의 기억이 아니라 작업 환경에 남아 있어야 합니다.**

이 질문이 점점 중요해지는 이유도 있습니다. METR은 3월에 AI 에이전트가 50% 성공률로 끝낼 수 있는 작업의 길이가 지난 6년간 약 7개월마다 두 배로 늘어 왔다고 발표했습니다. [\[METR: Measuring AI Ability to Complete Long Tasks, 2025-11-02 스냅샷\]](http://web.archive.org/web/20251102185330/https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/) 맡길 수 있는 일이 길어질수록, 한 번의 컨텍스트 윈도우 안에 끝나지 않는 일도 늘어납니다.

Anthropic은 2025년 11월 26일 글에서 이 문제를 교대 근무에 비유했습니다. 교대할 때마다 앞 근무에서 무슨 일이 있었는지 전혀 기억하지 못하는 엔지니어들로 프로젝트를 운영하는 것과 같다는 것입니다. 그리고 compaction으로는 충분하지 않다고 적었습니다. Opus 4.5 같은 최전선 모델을 Claude Agent SDK 위에서 여러 컨텍스트 윈도우에 걸쳐 돌려도, "claude.ai 클론을 만들어라" 같은 상위 수준의 프롬프트만 주면 운영 수준의 웹 앱에 미치지 못한다는 관찰입니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

이 글은 그 틈을 하네스가 어떻게 메우는지를 다룹니다. 에이전트 루프의 기본이나 컨텍스트 엔지니어링 일반론은 다른 글에서 다뤘으므로, 여기서는 세션과 세션 사이에서 무엇을 남기고 무엇을 확인하는지에 집중합니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사의 레거시 계약 관리 화면 40개를 새 프레임워크로 옮기는 일을 에이전트에게 맡기고 퇴근했다고 해봅시다. 프롬프트는 한 줄입니다.

```text
legacy/ 아래의 화면을 전부 새 프레임워크로 전환해 줘.
```

첫 세션은 의욕적으로 여러 화면을 한꺼번에 건드립니다. 공통 컴포넌트를 고치던 중에 컨텍스트가 끝납니다.

두 번째 세션은 빌드가 깨진 저장소에서 시작합니다. 무엇이 의도된 변경이고 무엇이 하다 만 것인지 알 수 없어, 세션의 대부분을 원상 복구에 씁니다.

일곱 번째 세션은 새 프레임워크로 된 화면이 여럿 있는 것을 보고 "전환을 완료했습니다"라고 보고합니다. 실제로는 열두 개가 남아 있고, 전환됐다는 화면 중 몇 개는 조회 버튼을 눌러도 결과가 나오지 않습니다.

Anthropic이 실험에서 관찰했다고 보고한 실패도 이와 같습니다. 한 번에 너무 많은 것을 하려다 구현 도중에 컨텍스트가 끝나 다음 세션이 상황을 추측해야 하는 경우, 나중 세션이 진척이 있는 것을 보고 일이 끝났다고 선언하는 경우, 그리고 제대로 테스트하지 않고 기능을 완료로 표시하는 경우입니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

설계의 말로 옮기면 네 가지가 없었습니다.

- 전체 범위를 적어 둔 곳이 없어, 완료를 판단할 기준이 없었습니다.
- 완료를 무엇으로 판정하는지에 대한 규칙이 없어, 코드가 있으면 끝난 것으로 보았습니다.
- 세션이 끝날 때의 상태에 대한 규칙이 없어, 하다 만 작업이 그대로 넘어갔습니다.
- 다음 세션이 상태를 파악하는 절차가 없어, 매번 추측으로 시작했습니다.

이 화면 전환 작업을 끝까지 들고 가면서, 네 가지 빈자리를 하나씩 채워 보겠습니다.

## 1. 세션을 넘어가는 수단은 여럿이고, 각각 보증하는 것이 다르다

### compaction은 대화를 잇는다

compaction은 대화가 한계에 가까워지면 내용을 요약해 새 컨텍스트 윈도우를 그 요약으로 다시 시작하는 기법입니다. [\[Anthropic: Effective context engineering for AI agents\]](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) Claude Agent SDK의 compact 기능도 컨텍스트 한계에 다가가면 이전 메시지를 자동으로 요약합니다. [\[Anthropic: Building agents with the Claude Agent SDK\]](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

요약은 대화를 이어 주지만, 요약하는 모델이 무엇을 중요하다고 보았는지에 따라 남는 것이 달라집니다. 화면 전환 사례에서 "공통 컴포넌트의 날짜 포맷 함수를 고치다 말았다"는 사실이 요약에서 빠지면, 다음 윈도우는 그 함수가 정상이라고 가정하고 다른 화면을 고칩니다.

### context editing과 memory tool은 무게를 덜고 메모를 남긴다

Anthropic은 9월에 두 가지 기능을 더 내놓았습니다. context editing은 토큰 한계에 다가가면 오래된 도구 호출과 결과를 자동으로 지우고, memory tool은 컨텍스트 밖의 파일 기반 저장소에 정보를 쓰고 읽게 합니다. memory tool은 클라이언트 쪽에서 도구 호출로 동작하므로 저장소는 개발자가 관리합니다. 발표 글은 자체 평가에서 두 기능을 함께 썼을 때 기준 대비 39%, context editing만으로 29%의 성능 향상이 있었다고 밝혔습니다. [\[Anthropic: Managing context on the Claude Developer Platform\]](https://www.anthropic.com/news/context-management)

이 두 기능은 하나의 긴 대화를 더 오래 끌고 가는 데 유용합니다. 그러나 무엇을 메모로 남길지는 여전히 모델이 정하고, 남긴 메모가 실제 작업 상태와 맞는지는 아무도 확인하지 않습니다.

### 작업 환경에 남기는 상태는 확인할 수 있다

이 글이 다루는 방식은 세 번째입니다. 진행 상태를 모델이 쓰는 메모가 아니라 작업 환경 자체, 곧 기능 목록 파일, Git 이력, 실행 가능한 테스트에 두는 것입니다. 이 셋은 모델의 기억과 무관하게 다시 읽고 다시 실행할 수 있습니다.

| 수단 | 넘어가는 것 | 보증하는 것 | 보증하지 않는 것 |
| --- | --- | --- | --- |
| compaction | 대화의 요약 | 대화의 흐름 | 요약에서 빠진 사실, 실제 코드 상태 |
| context editing | 정리된 대화 | 컨텍스트 여유 | 지운 결과에 있던 정보 |
| memory tool | 모델이 쓴 메모 | 메모의 지속 | 메모와 현실의 일치 |
| 기능 목록, Git, 테스트 | 범위, 이력, 판정 수단 | 다시 읽고 다시 실행할 수 있음 | 판정 수단 자체의 품질 |

네 번째 줄의 마지막 칸이 이 방식의 한계입니다. 테스트가 엉성하면 엉성한 판정이 그대로 이어집니다. 그래서 뒤의 절들은 판정 수단을 어떻게 단단하게 만드는지에 많은 부분을 씁니다.

### 언제 이 방식이 과한가

한두 시간 안에 끝나는 일, 사람이 옆에서 매번 확인하는 일에는 이 구조가 과합니다. compaction과 사람의 눈으로 충분합니다. 이 방식은 작업이 여러 컨텍스트 윈도우를 넘고, 그 사이에 사람이 없는 경우를 위한 것입니다.

## 2. 첫 세션과 나머지 세션은 하는 일이 다르다

### 초기화 세션과 코딩 세션

Anthropic이 제시한 구조는 두 부분입니다. 첫 세션의 초기화 에이전트가 환경을 준비하고, 이후 모든 세션의 코딩 에이전트가 점진적으로 전진하면서 다음 세션을 위한 기록을 남깁니다.

여기서 에이전트가 둘이라는 말은 오해하기 쉽습니다. 글의 각주에 따르면 system prompt, 도구, 하네스는 동일하고 달라지는 것은 첫 사용자 프롬프트뿐입니다. 멀티 에이전트 구성이 아니라 같은 에이전트에게 첫날과 그 이후에 다른 지시를 주는 것입니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

초기화 세션이 남기는 것은 네 가지입니다.

| 산출물 | 역할 | 다음 세션이 쓰는 방식 |
| --- | --- | --- |
| 기능 목록 파일 | 전체 범위와 완료의 정의 | 아직 통과하지 못한 항목 중 하나를 고름 |
| 진행 기록 파일 | 지금까지 한 일의 로그 | 최근 작업과 남은 문제를 파악 |
| `init.sh` | 개발 서버를 띄우는 스크립트 | 실행 방법을 다시 알아내지 않고 바로 실행 |
| 초기 Git 커밋 | 기준점 | 이후 변경을 비교하고 되돌릴 수 있는 지점 |

같은 권고는 Claude 프롬프트 가이드에도 실려 있습니다. 여러 컨텍스트 윈도우에 걸친 작업에서는 첫 윈도우에 다른 프롬프트를 써서 테스트와 설정 스크립트 같은 틀을 만들고, 이후 윈도우에서는 할 일 목록을 따라 반복하라는 것입니다. 서버 실행, 테스트, 린트를 한 번에 돌리는 `init.sh` 같은 스크립트를 만들게 하면 새 윈도우에서 같은 일을 반복하지 않는다는 설명도 붙어 있습니다. [\[Claude Docs: Prompting best practices, 2025-11-17 스냅샷\]](https://web.archive.org/web/20251117073945/https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices)

### 어느 프롬프트를 줄지는 하네스가 파일로 정한다

글과 함께 공개된 quickstart를 보면 이 전환이 어떻게 구현되는지 알 수 있습니다. 하네스는 프로젝트 디렉터리에 `feature_list.json`이 없으면 첫 실행으로 보고 초기화 프롬프트를, 있으면 코딩 프롬프트를 씁니다. 회차마다 새 클라이언트를 만들어 새 컨텍스트로 시작하고, 회차 사이에 3초를 기다린 뒤 자동으로 이어 가며, 최대 회차를 지정할 수 있습니다. [\[anthropics/claude-quickstarts: autonomous-coding, 2025-11-26 커밋\]](https://github.com/anthropics/claude-quickstarts/tree/25023412396a0bd082d50b4b4f39a864d35a3a73/autonomous-coding)

```text
하네스 루프 (quickstart 구조를 요약)
  │
  ├─ feature_list.json 있음? ── 아니오 ──> 초기화 프롬프트
  │                         └─ 예 ──────> 코딩 프롬프트
  │
  ├─ 새 클라이언트 생성 (새 컨텍스트 윈도우)
  ├─ 세션 실행 (에이전트가 파일, Git, 서버를 다룸)
  ├─ 세션 종료
  ├─ 최대 회차 도달? ── 예 ──> 정지
  └─ 3초 대기 후 처음으로
```

여기서 주목할 점은 "지금이 첫 세션인가"를 모델이 기억으로 판단하지 않는다는 것입니다. 작업 환경에 특정 파일이 있는지로 하네스가 판단합니다. 상태를 작업 환경에 둔다는 원칙이 하네스 코드의 첫 분기에서부터 지켜지는 셈입니다.

### 이 아이디어의 계보

이 아이디어가 완전히 새로운 것은 아닙니다. Geoffrey Huntley가 2025년 7월에 소개한 Ralph는 가장 단순한 형태로는 같은 프롬프트 파일을 Bash 루프로 코딩 에이전트에 반복해서 넣는 기법입니다. 그는 루프마다 한 가지 일만 하게 하라고 거듭 강조했고, 계획 파일과 명세 파일을 매 회차 다시 읽게 했습니다. [\[Geoffrey Huntley: Ralph\]](https://ghuntley.com/ralph/)

루프를 돌리는 것 자체는 쉽습니다. Anthropic의 글이 보탠 것은 루프의 각 회차가 무엇을 읽고 무엇을 남겨야 하는지, 그리고 첫 회차가 왜 달라야 하는지에 대한 구체적인 답이라고 봅니다.

### 초기화가 잘못되면 모든 회차가 잘못된다

이 구조의 가장 큰 위험은 초기화 세션에 집중되어 있습니다. 초기화 에이전트가 범위를 잘못 잡으면, 이후 모든 세션이 그 잘못된 목록을 성실하게 채웁니다. 화면 전환 사례에서 초기화 에이전트가 `legacy/` 아래 팝업 화면 여덟 개를 놓쳤다면, 마지막 세션은 32개를 끝내고 "모든 항목 통과"를 보고할 것입니다.

그래서 저는 초기화 세션과 첫 코딩 세션 사이에 사람의 검토를 반드시 두는 편이 안전하다고 봅니다. quickstart의 `--max-iterations` 옵션을 1로 주면 초기화만 돌리고 멈출 수 있습니다. 사람은 기능 목록을 레거시 화면 목록과 대조해 확정한 뒤에 나머지 회차를 시작합니다.

## 3. 완료의 정의는 파일에 고정하고, 판정은 사용자처럼 한 테스트로만 내린다

### 기능 목록은 검증 단위로 적는다

일곱 번째 세션이 성급하게 완료를 선언한 것은 전체 범위를 알 길이 없었기 때문입니다.

Anthropic의 실험에서 초기화 에이전트는 사용자의 한 줄 프롬프트를 확장해 기능 요구사항 파일을 작성했습니다. claude.ai 클론 예시에서는 200개가 넘는 기능이었고, 모든 항목은 처음에 실패 상태로 표시됩니다. 코딩 에이전트는 이 파일에서 통과 여부 필드만 바꿀 수 있도록 지시받습니다. 테스트를 삭제하거나 수정하는 것은 기능 누락이나 버그로 이어질 수 있어 용납되지 않는다는 강한 표현의 지시도 함께 씁니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

형식에 대한 관찰도 실려 있습니다. 실험 끝에 JSON을 택했는데, 모델이 Markdown 파일보다 JSON 파일을 부적절하게 바꾸거나 덮어쓸 가능성이 낮았기 때문이라고 합니다.

글에 실린 항목은 `category`, `description`, `steps`, `passes` 네 필드로 되어 있습니다. 같은 필드 구성으로 화면 전환 사례에 맞는 항목을 써 보면 이렇습니다.

```json
{
  "category": "functional",
  "description": "계약 조회 화면에서 계약 번호로 검색하면 결과 목록이 표시된다 (예시)",
  "steps": [
    "계약 조회 화면으로 이동한다",
    "계약 번호를 입력하고 조회를 누른다",
    "결과 목록에 해당 계약이 한 건 표시되는지 확인한다",
    "행을 선택하면 상세 화면으로 이동하는지 확인한다"
  ],
  "passes": false
}
```

제가 이 구조에서 중요하다고 보는 점은 항목이 구현 단위가 아니라 검증 단위로 적혀 있다는 것입니다. "ContractSearch 컴포넌트 작성"이 아니라 "검색하면 결과가 나온다"입니다. 구현 단위로 적으면 파일을 만든 것만으로 통과 처리하기 쉽습니다.

화면 전환이라면 화면 하나에 항목 하나가 아니라, 화면마다 사용자가 하는 주요 동작 몇 개가 항목이 됩니다. 조회, 상세 이동, 출력, 권한 없는 사용자의 접근 차단 같은 것입니다. 레거시 화면과 결과가 같아야 한다는 조건이 핵심이라면, 같은 계약 번호로 두 화면의 결과를 비교하는 단계를 `steps`에 넣을 수도 있습니다.

기능 목록은 평가 세트이기도 합니다. `passes`가 참인 항목의 비율이 곧 진행률이고, 사람은 대화 로그를 읽지 않고도 이 파일 하나로 상황을 파악할 수 있습니다.

### 통과 판정은 사용자처럼 해 본 테스트로만 내린다

기능 목록이 있어도 `passes`를 누가 어떤 근거로 참으로 바꾸느냐가 남습니다.

Anthropic이 관찰한 또 하나의 실패는 제대로 테스트하지 않고 기능을 완료로 표시하는 경향이었습니다. 명시적으로 요구하지 않으면 모델은 코드를 고치고 단위 테스트나 개발 서버에 대한 `curl`까지는 해 보지만, 기능이 처음부터 끝까지는 동작하지 않는다는 것을 알아채지 못했다고 합니다. 브라우저 자동화 도구를 주고 사람 사용자가 하듯 테스트하라고 명시하자 대부분 잘 검증했고, 코드만으로는 드러나지 않던 버그를 찾아 고칠 수 있었습니다. 프롬프트 가이드도 자율 작업이 길어질수록 사람의 피드백 없이 정확성을 확인할 도구, 예를 들어 Playwright MCP 서버나 computer use가 필요하다고 적습니다.

한계도 함께 적혀 있습니다. 모델의 시각 능력과 브라우저 자동화 도구의 제약 때문에 모든 종류의 버그를 찾지는 못합니다. 예를 들어 Puppeteer MCP로는 브라우저 기본 경고 창을 볼 수 없어, 그 창에 의존하는 기능은 버그가 더 많았다고 합니다.

여기서 얻을 설계 원칙은 웹 앱에만 해당하지 않는다고 봅니다. 통과 판정의 근거는 "코드를 작성했다"가 아니라 "기능 목록의 steps를 실제로 수행했다"여야 합니다. 작업 종류별로 바꿔 적으면 이렇습니다.

| 작업 종류 | "사용자처럼 해 본 테스트"에 해당하는 것 | 흔한 가짜 통과 |
| --- | --- | --- |
| 웹 화면 | 브라우저 자동화로 steps 수행, 스크린샷 | 컴포넌트 단위 테스트만 통과 |
| 배치 프로그램 | 표본 데이터로 실행 후 건수와 합계를 기대값과 대조 | 컴파일 성공, 예외 없이 종료 |
| API | 계약 테스트, 실제 호출과 응답 스키마 검증 | 핸들러 존재 확인 |
| 레거시 전환 | 같은 입력으로 옛 화면과 새 화면의 결과 비교 | 새 화면이 뜨는 것만 확인 |

### 규칙이 지켜졌는지는 하네스가 확인한다

"`passes`만 바꿔라", "테스트를 지우지 마라"는 강한 문장은 프롬프트입니다. 그것이 지켜졌는지는 세션이 끝난 뒤 하네스가 코드로 확인할 수 있습니다. 기능 목록 파일의 이전 판과 이번 판을 비교하면 됩니다.

```python
# 예시: 세션 종료 후 하네스가 feature_list.json 변경을 검사
import json, subprocess

def check_feature_list(prev_rev: str) -> list[str]:
    old = json.loads(subprocess.check_output(["git", "show", f"{prev_rev}:feature_list.json"]))
    new = json.load(open("feature_list.json", encoding="utf-8"))
    problems = []
    if len(new) != len(old):
        problems.append(f"항목 수 변경: {len(old)} -> {len(new)}")
    for i, (o, n) in enumerate(zip(old, new)):
        for key in ("category", "description", "steps"):
            if o.get(key) != n.get(key):
                problems.append(f"{i}번 항목의 {key} 변경")
    flipped = [i for i, (o, n) in enumerate(zip(old, new)) if not o["passes"] and n["passes"]]
    if len(flipped) > 1:
        problems.append(f"한 세션에서 {len(flipped)}개 항목이 통과로 바뀜 (규칙: 기능 하나)")
    return problems   # 비어 있지 않으면 다음 세션 첫 입력에 넣고, 사람에게 알림
```

마지막 검사는 다음 절의 "한 세션에 기능 하나" 규칙과 이어집니다. 통과로 바뀐 항목이 여럿이면 그 세션은 한꺼번에 너무 많이 했거나, 검증 없이 표시했을 가능성이 큽니다.

### 판정이 깨지는 방식

판정 수단이 약하면 이 구조 전체가 약해집니다. 앞의 표에서 "흔한 가짜 통과" 열이 실제로 가장 자주 일어나는 실패라고 봅니다. 또 하나는 회귀입니다. 공통 컴포넌트를 고친 세션이 자기가 맡은 화면은 통과시키면서 이미 통과했던 다른 화면을 깨뜨리는 경우입니다. 이것은 다음 절의 시작 순서로 잡습니다.

## 4. 한 세션에 기능 하나, 시작은 정해진 순서로, 끝은 병합 가능한 상태로

### 걸음의 크기를 정한다

범위가 고정되면 다음은 걸음의 크기입니다.

Anthropic은 코딩 에이전트에게 한 번에 기능 하나만 작업하도록 요청했고, 이 점진적 접근이 한꺼번에 너무 많이 하려는 경향을 다루는 데 결정적이었다고 적습니다. 그리고 세션을 깨끗한 상태로 끝내도록 요구합니다. 깨끗한 상태의 기준은 main 브랜치에 병합해도 될 만한 코드입니다. 큰 버그가 없고, 정돈되고 문서화되어 있어, 다음 개발자가 엉뚱한 뒷정리 없이 새 기능을 시작할 수 있는 상태입니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

이를 끌어내는 가장 좋은 방법으로는 두 가지를 들었습니다. 설명이 담긴 커밋 메시지로 Git에 커밋하게 하는 것, 그리고 진행 기록 파일에 요약을 쓰게 하는 것입니다. Git이 있으면 모델이 잘못된 변경을 되돌리고 동작하던 상태로 복구할 수 있습니다.

상태를 어디에 무엇으로 남길지에 대해서는 프롬프트 가이드의 구분이 실용적입니다. 테스트 결과나 작업 상태처럼 구조가 있는 정보는 JSON 같은 구조화된 형식으로, 전반적인 진행과 맥락은 자유 형식 메모로, 이력과 복원 지점은 Git으로 남기라는 것입니다. [\[Claude Docs: Prompting best practices, 2025-11-17 스냅샷\]](https://web.archive.org/web/20251117073945/https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices)

### 세션의 시작은 정해진 순서의 상태 파악이다

인수인계를 받는 쪽의 절차도 정해 둡니다. Anthropic은 모든 코딩 세션이 같은 순서로 시작하도록 프롬프트에 적었고, quickstart의 코딩 프롬프트는 이를 열 단계로 풀어 둡니다. 그 순서를 흐름으로 그리면 다음과 같습니다.

```text
세션 시작 (새 컨텍스트, 기억 없음)
  │
  ├─ 1. pwd 로 작업 디렉터리 확인
  ├─ 2. 진행 기록 파일, 기능 목록, git log 읽기
  ├─ 3. 남은 항목 수 세기
  ├─ 4. init.sh 로 개발 서버 실행
  ├─ 5. 이미 통과한 핵심 기능 1~2개를 다시 종단 간 테스트
  │       └─ 깨져 있으면: 그 항목을 false 로 되돌리고 새 기능보다 먼저 복구
  ├─ 6. 미완료 항목 중 우선순위가 가장 높은 것 하나 선택
  ├─ 7. 구현, 사용자처럼 검증
  └─ 8. passes 갱신, 커밋, 진행 기록 작성, 미커밋 변경 없음 확인
세션 종료 (병합 가능한 상태)
```

다섯 번째 단계가 왜 필요한지에 대한 설명이 설득력 있습니다. 새 기능에 손대기 전에 기본 테스트를 돌리면 앱이 깨진 채로 넘어왔는지 바로 알 수 있고, 그 확인 없이 새 기능부터 구현하면 문제를 더 키우게 된다는 것입니다. quickstart의 코딩 프롬프트는 여기서 문제가 보이면 해당 기능을 즉시 실패로 되돌리고, 새 기능보다 먼저 고치라고 적습니다. 한 세션에 기능 하나만 끝내도 괜찮다는 문장도 함께 있습니다. [\[anthropics/claude-quickstarts: autonomous-coding, 2025-11-26 커밋\]](https://github.com/anthropics/claude-quickstarts/tree/25023412396a0bd082d50b4b4f39a864d35a3a73/autonomous-coding)

화면 전환 사례에서 두 번째 세션이 원상 복구에 하루를 쓴 것은 다섯 번째 단계와 여덟 번째 단계가 없었기 때문입니다. 앞 세션이 병합 가능한 상태로 끝났다면 복구할 것이 없었고, 그렇지 않았더라도 다섯 번째 단계가 깨진 지점을 바로 짚었을 것입니다.

### 압축해서 이어 갈까, 새로 시작할까

프롬프트 가이드는 여기서 한 가지 선택지를 더 줍니다. 컨텍스트가 비워질 때 compaction을 쓰는 대신 완전히 새 컨텍스트 윈도우로 시작하는 방법입니다. 최신 모델이 로컬 파일시스템에서 상태를 찾아내는 데 능하므로 경우에 따라 이쪽이 낫다는 설명입니다. 같은 가이드는 Claude 4.5 모델이 남은 컨텍스트 예산을 스스로 추적한다는 점도 적습니다.

quickstart는 회차마다 새 컨텍스트로 시작하는 쪽을 택했고, 진행 상태는 `feature_list.json`과 Git 커밋으로만 유지합니다. 저는 이 선택이 위의 시작 순서와 짝을 이룬다고 봅니다. 시작 순서가 단단하면 앞 세션의 대화를 요약해 들고 올 필요가 없고, 요약에 섞여 들어올 수 있는 오해도 함께 사라집니다.

### 진행 기록에는 다음 사람이 물을 것을 쓴다

진행 기록 파일은 자유 형식이지만, 아무렇게나 써도 된다는 뜻은 아니라고 봅니다. 기능 목록과 Git이 이미 답하는 것, 곧 무엇이 통과했고 무엇이 바뀌었는지를 다시 적을 필요는 없습니다. 진행 기록에는 그 둘이 답하지 못하는 것을 적어야 합니다.

```text
[예시] claude-progress.txt 의 한 세션 기록

## 세션 14
- 한 일: 해지 신청 화면 조회 기능 전환, 브라우저로 steps 수행 후 통과 처리
- 결정과 이유: 레거시의 날짜 입력이 YYYYMMDD 문자열이라 새 화면도 같은 형식으로 서버에 보냄
  (공통 날짜 컴포넌트는 Date 객체를 쓰지만, 서버 계약을 바꾸지 않기 위해 변환 함수 추가)
- 시도했다가 버린 것: 공통 날짜 컴포넌트 자체를 문자열 기반으로 수정 → 다른 화면 6개에 영향, 되돌림
- 다음 세션이 알아야 할 것: 계약 조회 > 상세 이동이 간헐적으로 실패함. 원인 미확인
```

"결정과 이유"와 "시도했다가 버린 것"이 핵심입니다. 이 두 칸이 없으면 다음 세션은 같은 공통 컴포넌트를 다시 고치려다 같은 막다른 길에 들어섭니다. 사람의 인수인계 대장에서도 가장 쓸모 있는 칸이 "특이사항"인 것과 같은 이치입니다.

### 세션 사이에 하네스가 할 일

저는 여기에 하네스 쪽 장치를 하나 더 두는 편이 안전하다고 봅니다. 세션 종료 시점에 하네스가 직접 빌드와 기본 테스트를 돌려 보고, 실패하면 그 사실을 다음 세션의 첫 입력으로 넣는 것입니다. 깨끗한 상태로 끝내라는 지시는 프롬프트이고, 실제로 깨끗한지 확인하는 것은 코드여야 합니다.

```text
[예시] 다음 세션의 첫 입력에 하네스가 덧붙이는 내용

## 하네스 점검 결과 (세션 14 종료 시점)
- 빌드: 성공
- 미커밋 변경: 없음
- 기본 테스트: 실패 1건 (계약 조회 > 상세 이동)
- feature_list.json 검사: 통과로 바뀐 항목 1개 (해지 신청 화면 조회)
- 지시: 새 기능을 시작하기 전에 실패한 기본 테스트부터 복구할 것
```

Claude Code에는 9월부터 체크포인트 기능이 있어, 편집 전 상태를 자동 저장하고 되돌릴 수 있습니다. 다만 발표 글은 체크포인트가 Claude의 편집에만 적용되고 사용자 편집이나 bash 명령에는 적용되지 않으므로 버전 관리와 함께 쓰라고 권합니다. [\[Anthropic: Enabling Claude Code to work more autonomously\]](https://www.anthropic.com/news/enabling-claude-code-to-work-more-autonomously) 무인 실행의 복원 지점은 Git 커밋에 두는 편이 맞다고 봅니다.

### 걸음이 깨지는 방식

기능 하나가 한 세션에 끝나지 않을 만큼 크면 규칙이 오히려 해가 됩니다. 에이전트는 기능을 끝내지 못한 채 깨끗한 상태로 끝내라는 요구와 기능 하나를 끝내라는 요구 사이에서 하나를 어기게 됩니다. 이런 항목은 초기화 단계나 사람의 검토 단계에서 더 작게 쪼개야 합니다. 공통 컴포넌트 교체처럼 여러 화면에 걸친 일은 그 자체를 별도 항목으로 앞에 두고, 화면별 항목은 그 뒤에 두는 식입니다.

## 5. 무인 실행의 통제: 권한, 승인, 기록

### 사람이 없는 동안의 권한

같은 quickstart README는 보안 모델도 적어 두었습니다. 운영체제 수준 샌드박스, 프로젝트 디렉터리로 제한된 파일 작업, 그리고 허용 목록에 있는 Bash 명령만 실행하는 구성입니다. 허용 목록에는 파일 확인용 명령, Node.js, Git, 개발 프로세스 관리용 명령 정도만 들어 있고, 목록에 없는 명령은 보안 훅이 막습니다. [\[anthropics/claude-quickstarts: autonomous-coding, 2025-11-26 커밋\]](https://github.com/anthropics/claude-quickstarts/tree/25023412396a0bd082d50b4b4f39a864d35a3a73/autonomous-coding)

사람이 지켜보지 않는 긴 실행일수록 이 부분이 먼저 설계되어야 한다고 봅니다. 화면 전환 작업이라면 에이전트에게 필요한 것은 저장소, 로컬 개발 서버, 테스트용 DB 정도입니다. 운영 DB 접속 정보, 배포 명령, 외부 네트워크는 처음부터 닿지 않게 두는 편이 안전합니다.

### 시간과 비용의 상한도 하네스에 둔다

무인 실행에는 시간과 비용의 상한도 필요합니다. quickstart README는 첫 초기화 세션이 200개 항목을 쓰느라 몇 분 동안 멈춘 것처럼 보일 수 있고, 이후 코딩 세션은 하나에 5~15분, 전체 앱은 여러 세션에 걸쳐 몇 시간이 걸린다고 안내합니다. 빠른 시연을 원하면 초기화 프롬프트의 항목 수를 줄이라는 조언도 있습니다. [\[anthropics/claude-quickstarts: autonomous-coding, 2025-11-26 커밋\]](https://github.com/anthropics/claude-quickstarts/tree/25023412396a0bd082d50b4b4f39a864d35a3a73/autonomous-coding)

이 숫자는 그 예제의 것이지만, 계획을 세우는 방법은 그대로 가져올 수 있습니다. 화면 40개에 주요 동작 서너 개씩이면 항목이 150개 안팎이고, 한 세션에 항목 하나라면 세션도 그만큼 필요합니다. 하룻밤에 끝날 일인지, 최대 회차를 몇으로 두고 아침에 얼마나 진척되어 있기를 기대할지를 미리 계산해 두면, 아침의 결과를 보고 성패를 판단할 기준이 생깁니다.

### 보수적인 조직에서는 인수인계 대장이 이미 익숙한 도구다

금융이나 보험의 운영 조직은 교대 근무 인수인계 대장, 작업 계획서, 작업 결과서에 익숙합니다. 위 구조는 그 문서들을 에이전트가 읽고 쓰는 파일로 옮긴 것에 가깝습니다.

| 익숙한 문서 | 이 구조의 파일 | 감사에서 답하는 질문 |
| --- | --- | --- |
| 작업 계획서 | `feature_list.json` | 무엇을 하기로 했는가, 누가 승인했는가 |
| 작업 이력 | Git 커밋 | 무엇이 언제 바뀌었는가 |
| 인수인계 대장 | 진행 기록 파일 | 왜 그렇게 했고 무엇이 남았는가 |
| 작업 결과서 | `passes` 변경과 하네스 점검 결과 | 무엇을 근거로 완료로 보았는가 |

제가 이 구조가 보수적인 환경에 잘 맞는다고 보는 이유는 감사 추적이 부산물로 생기기 때문입니다. 대화 로그 수백 쪽을 읽지 않아도 네 가지로 경위를 재구성할 수 있습니다.

### 승인선을 둘 자리

승인선을 넣을 자리도 분명합니다.

- 범위 승인: 초기화 세션이 만든 기능 목록을 사람이 검토하고 확정한 다음에 코딩 세션을 시작합니다. 범위에 대한 승인이 구현보다 앞에 놓입니다.
- 결과 확인: 야간에 돌린 결과를 아침에 볼 때 `passes`가 바뀐 항목만 골라 직접 확인합니다. 하네스 점검에서 경고가 난 세션은 우선 확인 대상입니다.
- 반영 승인: 에이전트의 커밋은 작업 브랜치에 쌓고, main 반영은 평소처럼 PR 승인을 거칩니다. 병합 가능한 상태로 끝낸다는 규칙은 병합을 생략해도 된다는 뜻이 아닙니다.

### 아직 열려 있는 것

조심할 점도 있습니다. 이 글의 실험은 처음부터 새로 만드는 웹 앱을 대상으로 했고, Anthropic 스스로 과학 연구나 재무 모델링 같은 다른 분야로의 일반화를 앞으로의 과제로 남겼습니다. 단일 범용 에이전트가 나은지, 테스트나 품질 확인이나 정리를 맡는 전담 에이전트를 두는 구성이 나은지도 아직 열린 질문이라고 적었습니다. [\[Anthropic: Effective harnesses for long-running agents\]](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

레거시 전환은 새로 만드는 일과 다릅니다. 옛 화면의 동작이 곧 명세이고, 그 명세는 문서가 아니라 운영 중인 코드에 있습니다. 기존 시스템을 고치는 작업에 그대로 통한다고 가정하지 말고, 화면 서너 개 규모로 먼저 확인하는 편이 안전합니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 긴 작업에 쓰는 프롬프트를 둘로 나눕니다. 환경을 준비하는 첫 세션용과 한 걸음씩 전진하는 반복 세션용이고, 어느 쪽을 쓸지는 하네스가 기능 목록 파일의 존재로 판단하게 합니다.
2. 첫 세션의 산출물로 기능 목록 JSON을 받고, 사람이 검토해 범위를 확정합니다. 항목은 검증 절차로 적혀 있어야 하고, 한 세션에 끝나지 않을 항목은 쪼갭니다.
3. 반복 세션 프롬프트에 시작 순서를 고정합니다. 디렉터리 확인, 기록과 로그 읽기, 서버 실행, 이미 통과한 기능의 재확인, 그 다음에 새 기능입니다.
4. 종료 규칙을 정합니다. 기능 하나, 사용자처럼 검증, `passes` 갱신, 커밋, 진행 기록, 미커밋 변경 없음입니다.
5. 하네스가 세션 사이에 빌드와 기본 테스트, 기능 목록 변경 검사를 직접 돌리고 결과를 다음 세션의 첫 입력에 넣게 합니다. 명령 허용 목록과 작업 디렉터리 제한은 첫 실행 전에 설정합니다.

## 마치며

긴 작업을 맡긴다는 것은 한 명의 에이전트에게 오래 일을 시키는 것이 아니라, 기억이 없는 여러 세션에게 차례로 일을 넘기는 것입니다. 그래서 설계의 중심은 모델이 아니라 인수인계에 놓입니다. 범위는 기능 목록에, 이력은 Git에, 맥락은 진행 기록에, 판정은 테스트에 두면 세션이 바뀌어도 일은 같은 자리에서 이어집니다. 이 네 가지가 갖춰졌는지를 먼저 보고, 그 다음에 얼마나 오래 돌릴지를 정하는 순서가 맞다고 봅니다.
