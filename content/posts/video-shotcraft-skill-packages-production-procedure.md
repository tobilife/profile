- video-shotcraft는 코딩 에이전트가 Remotion으로 제품 영상을 만들게 하는 agent skill이고, 2026년 7월 19일에 만들어진 저장소입니다. 이 글은 7월 28일 커밋을 기준으로 합니다.
- 핵심은 프롬프트가 아니라 절차입니다. 어떤 모드로 갈지, 언제 무엇을 읽을지, 어디서 멈출지를 SKILL.md와 8단계 파이프라인 문서가 정합니다.
- 화면은 손으로 그리지 않고 실제 페이지를 캡처하며, 연출은 샷 카드의 파라미터 표와 조율이 끝난 참조 구현 코드로 고정합니다.
- 박자는 결과물에서 다시 재고, 렌더링은 결정적으로 만들고, 최종 검수는 제작에 참여하지 않은 깨끗한 컨텍스트의 에이전트가 프레임 번호 증거와 함께 합니다.
:::

코딩 에이전트로 영상을 만들어 본 분들은 대개 이렇게 생각합니다. "프롬프트를 잘 쓰면 좋은 영상이 나온다."

그래서 프롬프트를 다듬습니다. 톤을 적고, 참고 영상을 붙이고, 금지 사항을 늘립니다. 그래도 결과는 돌릴 때마다 달라지고, 화면 속 제품은 실제 제품과 미묘하게 다릅니다.

**결과가 흔들리는 이유는 프롬프트가 부족해서가 아니라, 제작 절차와 합격 기준이 어디에도 고정되어 있지 않기 때문입니다.**

`Vincentwei1021/video-shotcraft`는 이 문제를 skill 하나로 풀어 보려는 저장소입니다. README는 자신을 Claude Code나 Codex를 모션 디자인 스튜디오로 바꾸는 agent skill이라고 소개합니다. 제품을 가리키면 스토리보드를 짜고, 애니메이션을 만들고, 사운드를 입혀 Remotion으로 제품 영상을 만든다는 것이고, 실제 페이지 캡처, 2.5D 카메라 무브, 박자에 맞춘 컷, 효과음을 포함한다고 적습니다. [\[video-shotcraft: README\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/README.md)

이 글은 공개 열흘쯤 지난 2026년 7월 28일 커밋을 기준으로 씁니다. 저장소 생성일은 7월 19일이고, Apache-2.0 라이선스 파일은 다음 날 커밋으로 들어왔습니다. [\[GitHub: Vincentwei1021/video-shotcraft\]](https://github.com/Vincentwei1021/video-shotcraft)

영상에 관심이 없는 분께도 이 저장소를 권하는 이유가 있습니다. 감각에 기대는 작업을 에이전트에게 맡길 때 무엇을 문서로, 무엇을 코드로, 무엇을 측정으로 고정해야 하는지를 한 저장소 안에서 꽤 끝까지 보여 주기 때문입니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사 IT 조직이 사내 보험금 청구 현황 대시보드를 새로 만들었고, 경영진 보고에 쓸 30초 소개 영상을 에이전트에게 맡긴다고 해봅시다. 이 글 전체에서 쓸 예시입니다.

> 우리 청구 현황 대시보드 소개 영상 30초짜리 만들어 줘.

에이전트는 영상 코드를 씁니다. 그런데 화면 속 대시보드는 실제 제품과 닮은 듯 다른, 에이전트가 새로 그린 UI입니다. 글꼴과 색도 사내 디자인 시스템과 다릅니다. 컷은 배경 음악의 박자와 어긋나고, 같은 요청을 다시 하면 전혀 다른 영상이 나옵니다. 에이전트는 "완성했습니다"라고 말합니다.

시스템 설계 관점에서 보면 세 가지가 빠져 있습니다.

- 입력이 고정되지 않았다. 실제 화면이 아니라 모델의 상상이 소재가 되었다.
- 연출의 선택지가 열려 있었다. 어떤 움직임을 몇 프레임 동안 쓸지 매번 새로 정했다.
- 합격 기준이 없었다. 만든 쪽이 다 만들었다고 말하면 끝이었다.

video-shotcraft는 이 세 가지를 각각 캡처, 샷 카드와 참조 구현, 측정과 독립 검수로 막습니다. 아래 다섯 절은 그 장치를 하나씩 봅니다.

## 1. Skill의 단위는 프롬프트가 아니라 절차다

저장소의 진입점은 `SKILL.md`입니다. 여기에는 멋진 영상을 만들라는 주문 대신, 어떤 상황에서 어떤 문서를 읽고 어디서 멈출지가 적혀 있습니다. [\[video-shotcraft: SKILL.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/SKILL.md)

### 먼저 모드를 가린다

전체 홍보 영상에는 서로 섞지 않는 세 가지 모드가 있습니다. 7월 23일 커밋에서 자율 제작과 공동 제작을 분리한 뒤의 구조입니다.

| 모드 | 에이전트가 읽는 문서 | 사람이 확인하는 지점 |
| --- | --- | --- |
| 템플릿 사용 | `template/TEMPLATE.md` | 모드를 고르는 시점 |
| 자율 제작 | `references/pipeline.md` | 단계마다 멈추지 않음. 판단은 설계 문서에 기록 |
| 공동 제작 | `references/guided-free-creation.md` 후 `pipeline.md` 4단계부터 | 제품 요약, 요구 사항에서 실행 결정까지의 표, 시각 방향, 기능별 샷 매핑, 최종 스토리보드 |

사용자가 모드를 정하지 않았다면, 에이전트는 프로젝트를 읽기 전용으로 최소한만 점검합니다. 비즈니스 프로젝트를 고치지 않고, 민감 데이터를 수집하지 않고, 영상 코드도 쓰지 않습니다. 그 뒤 세 모드 각각이 이 제품에 맞는지 근거를 들어 설명하고, 하나를 추천한 다음 선택을 기다립니다. 완성 템플릿이 있다는 이유만으로 템플릿을 추천하지 말고, 임의로 정해 제작을 시작하지도 말라고 SKILL.md는 명시합니다.

예외도 정해져 있습니다. 사용자가 템플릿 이름을 직접 말했으면 템플릿 모드가 정해진 것으로 보고 다시 묻지 않습니다. 사용자가 특정 샷 카드를 쓰라고 지정했으면 템플릿 소개를 건너뛰고, 전체 영상이라면 자율과 공동 중 무엇으로 할지만 묻습니다.

예시의 대시보드라면 에이전트는 저장소를 읽기 전용으로 훑고 "사내 보고용이고 디자인 시스템이 엄격하니 공동 제작을 추천합니다"처럼 근거와 함께 묻게 됩니다.

이 구조가 주는 효과는 사람의 개입 지점이 문서에 고정된다는 것입니다. 공동 제작에서는 다섯 번 멈추고, 자율 제작에서는 한 번도 멈추지 않습니다. 에이전트가 그때그때 "확인해 드릴까요?"를 판단하지 않습니다.

### 언제 무엇을 읽을지도 정해져 있다

SKILL.md에는 시점별로 읽을 파일을 정한 표가 있습니다. 그 일부를 옮기면 이렇습니다.

| 시점 | 읽는 것 |
| --- | --- |
| 사용자가 BGM을 정했을 때 | `music-beat-sync.md`. 분석을 먼저 하고 스토리보드는 그다음 |
| 스토리보드 설계 | `sequences/`의 구조 템플릿, `shots/` 전체 카드의 머리말, 고른 카드의 전문 |
| 샷 하나 구현 | 그 카드 전문, 카드가 가리키는 참조 구현 소스 전문, `assets/lib/`의 해당 컴포넌트 |
| 사운드 디자인 | `sound-design.md`와 `assets/audio/` |
| 검수 | `final-review.md`와 `aesthetic-rules.md` 전문. 독립 subagent가 실행 |

카드 104장을 한꺼번에 읽지 않습니다. 스토리보드를 짤 때는 머리말만 훑고, 고른 카드만 전문을 읽고, 구현할 때만 소스를 읽습니다.

이 방식은 Anthropic이 Agent Skills를 소개하며 설명한 progressive disclosure와 같은 원리입니다. 에이전트는 처음에 skill의 이름과 설명만 알고, 관련이 있다고 판단할 때 본문을 읽고, 본문이 가리키는 추가 파일은 필요할 때만 엽니다. [\[Anthropic: Equipping agents for the real world with Agent Skills\]](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) Agent Skills 명세도 이름과 설명은 시작할 때, 본문은 활성화될 때, `scripts/`, `references/`, `assets/`의 파일은 필요할 때 읽는 세 단계를 권하고, `SKILL.md` 본문은 500줄 아래로 유지하라고 적습니다. [\[Agent Skills Specification\]](https://web.archive.org/web/20260723004319/https://agentskills.io/specification)

video-shotcraft의 `SKILL.md`는 7월 28일 기준 200줄 남짓이고, 무거운 지식은 전부 `references/`로 밀어 두었습니다. 제가 주목하는 건 여기서 skill이 문서 묶음이 아니라 라우터로 동작한다는 점입니다. 본문은 판단 기준과 다음에 열 파일을 알려 주는 역할만 합니다.

### 8단계 파이프라인

자율 제작 모드가 따르는 `pipeline.md`는 제작을 8단계로 나눕니다. 문서의 첫 문장이 방향을 정하는 질문은 비싼 샷 단위 구현 단계로 넘기지 않는다는 원칙입니다. [\[video-shotcraft: pipeline.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/pipeline.md)

```text
0 제품 이해와 제약 ──> 1 시각 방향, 정지 styleframe ──> 2 기능별 샷 매핑
                                                              │
        ┌─────────────────────────────────────────────────────┘
        ▼
3 스토리보드와 제작 승인 ──> 4 최종 소재 캡처 ──> 5 샷별 구현 (샷마다 정지 프레임 확인)
                                                              │
        ┌─────────────────────────────────────────────────────┘
        ▼
6 사운드 디자인 (화면 타임라인 고정 후) ──> 7 독립 검수와 최종 렌더링
```

앞의 네 단계는 모두 싼 산출물로 끝납니다. 1단계의 styleframe은 Remotion 코드가 아니라 HTML과 CSS로 만든 1920×1080 정지 화면 두세 장이고, 문서는 렌더링한 영상으로 스타일을 제안하면 비싸고 방향을 바꾸는 심리적 비용도 크다고 적습니다. 방향에 대한 논쟁을 첫 줄의 Remotion 코드보다 앞에 두려는 설계입니다.

### 실패 모드와 비용

- 문서가 많다는 것은 읽기 비용이 크다는 뜻입니다. 7월 28일 기준 `pipeline.md`, `aesthetic-rules.md`, `sound-design.md`는 각각 2만 바이트를 넘습니다. 시점별 읽기 규칙이 지켜지지 않으면 컨텍스트가 금방 찹니다.
- 모드 규칙은 사용자가 끼어들 때 흔들릴 수 있습니다. SKILL.md는 공동 제작 중 사용자가 "알아서 해"라고 하면 자율 제작으로 바꾸고 그 선택을 기록하라고 하는데, 이런 전환 규칙이 없는 skill은 반쯤 자율, 반쯤 확인하는 애매한 상태에 빠집니다.
- 짧은 단발 작업에는 과합니다. 로고 하나를 3초 움직이는 작업이라면 8단계 대신 샷 카드 한 장 경로를 쓰는 편이 맞고, SKILL.md도 단일 샷 용도를 별도 경로로 둡니다.

## 2. 화면은 그리지 않고 캡처한다

SKILL.md의 첫 번째 원칙은 기존 페이지를 재현할 때는 반드시 실제 스크린샷을 쓰라는 것입니다. 손으로 그린 UI는 실제 페이지를 재현하는 장면이 아닐 때만 허용하고, 그때도 출판물 수준의 질감이 안 나오거나 무엇을 표현하는지 관객이 알 수 없으면 캡처로 돌아가라고 합니다. [\[video-shotcraft: SKILL.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/SKILL.md)

### 캡처 단계의 산출물

파이프라인 문서는 캡처 단계의 산출물을 세 가지로 정합니다. 제품의 로컬 개발 서버를 띄우고, 저장소의 캡처 스크립트 템플릿을 복사해 주소와 선택자만 바꾼 뒤 한 번 돌리면 나오는 것들입니다. [\[video-shotcraft: pipeline.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/pipeline.md)

| 산출물 | 규칙 | 쓰이는 곳 |
| --- | --- | --- |
| 전체 페이지 2배율 스크린샷 | 뷰포트 1920×1080, `deviceScaleFactor: 2`, 글꼴 로딩 완료 후 600ms 대기, 실시간 동기화 페이지는 1.5에서 2초 추가 대기 | 2.5D 카메라가 비추는 바탕 |
| 요소 단위 잘라낸 이미지 | 의미 있는 선택자별로 따로. 떠다니는 요소는 투명 배경, 카드가 날아와 꽂히는 장면이면 빈 바탕도 따로 | 날아가고 쌓이는 요소 |
| `layout.json` | 각 요소의 페이지 좌표 `{x, y, w, h}`와 페이지 높이 | 날아갈 목표 위치, 마스크 위치 |

세 번째가 중요합니다. 카드가 날아가 꽂힐 위치, 강조 마스크를 씌울 위치를 에이전트가 짐작하지 않고 좌표표에서 읽습니다.

### 좌표계를 하나로 맞추는 장치

이 좌표표를 받는 쪽이 `PageCam`이라는 컴포넌트입니다. SKILL.md와 템플릿 문서는 이것을 실제 페이지를 보여 주는 모든 샷의 기반이라고 부릅니다. 전체 페이지 이미지 위에 키프레임으로 정한 2.5D 카메라를 움직이고, 그 위에 얹는 요소는 페이지의 CSS 픽셀 단위로 배치합니다. `layout.json`과 같은 좌표계입니다. [\[video-shotcraft: pipeline.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/pipeline.md)

예시의 대시보드에서 "미결 청구 건수" 카드를 강조한다면 흐름은 이렇습니다. 캡처 스크립트가 그 카드의 선택자로 잘라낸 이미지와 좌표를 남기고, 샷 코드는 좌표표에서 그 카드의 위치를 읽어 카메라 초점과 하이라이트 위치를 잡습니다. 대시보드 레이아웃이 바뀌면 캡처를 다시 돌리면 되고, 샷 코드의 숫자를 손으로 고칠 일이 없습니다.

입력을 고정한다는 것은 이런 뜻이라고 봅니다. 에이전트가 화면을 해석해 다시 그리는 대신, 결정적인 스크립트가 화면을 측정해 넘깁니다.

### 캡처 시점과 데이터 규칙

캡처 시점도 정해져 있습니다. 최종 소재 캡처는 스토리보드가 확정된 뒤에 합니다. 문서는 확정 전에 전량 캡처하면 어떤 페이지 상태를 어떤 범위로 찍을지 정해지지 않아 다시 찍게 된다고 적고, 소재 방향이 틀린 것이 샷 구현 단계에서야 드러나면 장면 전체를 버리게 된다고 경고합니다. styleframe용으로 찍은 몇 장은 방향 확인용일 뿐 최종 소재로 쓰지 못합니다.

데이터 규칙도 있습니다. 고객, 개인, 내부, 비밀키, 실시간 데이터는 캡처 전에 가짜 데이터로 바꾸거나 가리거나 고정해야 합니다. 공개된 데모 데이터만 제품 요약에서 명시적으로 확인한 뒤 쓸 수 있습니다.

예시의 청구 현황 대시보드는 실제 청구 건수와 고객 이름이 그대로 보이는 화면입니다. 이 규칙대로라면 캡처 전에 개발 서버에 가짜 청구 데이터를 넣고, 그 상태를 고정한 뒤 찍어야 합니다.

### 시각 언어도 제품에서 가져온다

입력을 고정하는 원칙은 화면 밖으로도 이어집니다. SKILL.md는 영상 전체의 시각 언어가 제품에서 자라야 하고, 제품과 무관한 "홍보 영상 스킨"을 새로 만들지 말라고 합니다. styleframe 전에 제품의 디자인 시스템, 소스, 계산된 스타일에서 글꼴, 글자 크기 단계, 간격, 모서리, 배경과 강조색을 뽑아 설계 문서에 적고, 영상 속 제목, 자막, 숫자, 전환, 광원 효과의 색까지 그 토큰을 재사용하라는 것입니다. 템플릿이나 샷 카드에서 가져오는 것은 샷 구조, 움직임 문법, 리듬, 조율된 파라미터뿐이고, 글꼴과 색과 재질은 대상 제품에 맞춰 다시 입힙니다.

### 실패 모드와 비용

- 로컬 개발 서버를 띄우기 어려운 제품, 예를 들어 사내 인증이 얽힌 레거시 화면은 캡처 단계부터 막힙니다. 데스크톱 제품은 창 캡처 도구로 같은 세 가지를 만들라고 문서가 안내하지만, 준비 비용은 제품마다 다릅니다.
- 가짜 데이터를 넣는 작업은 생각보다 큽니다. 대시보드는 데이터가 화면의 대부분이라, 그럴듯한 가짜 데이터를 만드는 것 자체가 별도 작업이 됩니다.
- 실제 화면이 존재하지 않는 기획 단계의 제품에는 이 원칙이 맞지 않습니다. 그때는 손으로 그린 UI 경로를 써야 하고, 그만큼 품질 기준을 통과하기 어렵습니다.

:::caution
회사 화면을 영상 소재로 쓰면 캡처 이미지가 저장소와 렌더링 결과물에 남습니다. 이 저장소의 규칙처럼 캡처 전에 데이터를 고정하고 가리는 단계를 절차에 넣어 두는 편이 안전합니다.
:::

## 3. 샷 카드는 취향을 파라미터와 금지 사항으로 적어 둔 것이다

이 저장소에서 가장 독특한 자산은 샷 카드입니다. 7월 28일 기준 README에는 카드 104장과 모션 미리보기 161개가 있다고 적혀 있고, 카드는 오프닝, 카메라, 전환, 타이포그래피, UI 등장 같은 기능별 10개 분류로 나뉘어 있습니다. [\[video-shotcraft: README\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/README.md)

### 카드 한 장의 구성

카드 한 장의 구성을 보면 의도가 드러납니다. 오프닝 분류의 `spotlight-hero-card` 카드를 예로 들면 이렇습니다. [\[video-shotcraft: spotlight-hero-card 샷 카드\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/shots/opening/spotlight-hero-card.md)

| 카드의 부분 | 담긴 내용 | 하네스 관점의 역할 |
| --- | --- | --- |
| 머리말 | 이름, 한 줄 설명, 적합한 용도, 길이, 에너지 수준, 태그 | 선택 단계에서 싸게 훑는 색인 |
| 의도 | 이 샷이 관객에게 말하려는 한 가지 | 선택 기준 |
| 움직임 핵심 | 동작의 순서 | 구현 체크리스트 |
| 파라미터 표 | 카메라 각도, 구간별 프레임 수, easing 값, 조절 감각 | 연출의 고정값 |
| 사운드 | 어느 동작에 어떤 종류의 효과음을 붙이는지 | 소리와 그림의 결합 규칙 |
| 알려진 함정 | 과거에 반려된 시도와 그 이유 | 금지 사항 |
| 참조 구현 | 실제 TSX 파일 경로 | 정답 코드 |

### 수치로 적힌 취향

이 카드의 파라미터 표는 취향을 숫자로 적어 둔 것입니다. 카메라는 전체 페이지를 0.78배로 정면에서 보다가 16프레임 만에 2.6배로 다가가고, 좌우 회전 34도에 상하 회전은 8도만 줍니다. 카드는 10프레임 동안 과하게 튀어 오른 뒤 54프레임 떠 있고, 18프레임에 걸쳐 제자리로 내려앉습니다. 고정에서 착지까지 약 98프레임, 3.3초입니다.

숫자 옆의 조절 감각 칸에는 그 숫자가 나온 이유가 적혀 있습니다. 질감이 중요한 샷은 3초로 늦춰야 하고 첫 판은 거의 언제나 빠르다는 것, 아래에서 올려 찍는 것보다 옆에서 수평으로 찍는 쪽이 읽기 쉽다는 것입니다. 알려진 함정 칸에는 오프닝에서 카드 여러 장을 동시에 움직이는 안이 여러 번 반려되어 한 장으로 수렴했다는 기록과, 카드마다 반짝임을 넣는 안이 두 번 반려되었다는 기록이 있습니다.

예시의 대시보드 영상에 이 카드를 쓴다면 주인공 카드를 "미결 청구 건수" 위젯으로 정하고, 숫자는 그대로 둔 채 캡처 소재와 좌표만 바꾸게 됩니다.

### 카드보다 참조 구현이 우선한다

SKILL.md는 카드만 읽고 새로 짜는 것을 금지합니다. 샷 카드를 쓰려면 먼저 갤러리 색인 파일 `gallery/api/library.json`으로 카드 이름과 스타일 키를 검증하고, 카드의 참조 구현 칸이 가리키는 TSX를 찾아 전문을 읽어야 합니다. 카드가 주는 것은 의미와 파라미터 표이고, 조율이 끝난 easing, 시간 배분, 마스크 타이밍, 알려진 함정을 피하는 작성법의 실체는 참조 구현 소스에 있다는 이유입니다. 카드 이름과 이해만으로 새로 쓰면 조율의 누적을 전부 버리는 것이라고 SKILL.md는 적습니다. [\[video-shotcraft: SKILL.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/SKILL.md)

대상 제품에 맞춘 수정은 허용하되, 카드에 함정이나 급소로 표시된 파라미터는 낮추지 못하게 합니다. 품질 기준은 올라갈 수만 있고 내려갈 수 없다는 규칙입니다.

공동 제작 문서는 이름 해석 규칙을 더 엄격하게 적습니다. 색인에 없는 이름이면 가장 가까운 실제 카드 이름을 제시하고, 이름을 보고 지어내지 말라고 합니다. 갤러리에 "참고만 가능, 직접 구현 필요"로 표시된 스타일은 먼저 추천하지 않고, "미리보기 없음"으로 표시된 스타일은 쓸 수는 있지만 미리보기와 일치한다고 주장하지 못하게 합니다. [\[video-shotcraft: guided-free-creation.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/guided-free-creation.md)

하네스 관점에서 보면 이것은 "모델에게 설명하지 말고, 동작하는 코드를 주라"는 원칙입니다. 설명은 해석될 때마다 달라지지만 코드는 같은 프레임을 냅니다.

### 자유도를 세 단계로 나눈다

템플릿도 같은 생각의 연장입니다. 저장소에는 Ink Press라는 완성 템플릿이 들어 있는데, README에 따르면 36.2초, 1920×1080, 30fps, 샷 10개짜리 홍보 영상입니다. 에이전트는 구조와 타이밍을 그대로 두고 스크린샷, 문구, 브랜드만 바꿉니다.

정리하면 자유도를 세 단계로 제공하는 셈입니다.

| 경로 | 고정되는 것 | 에이전트가 정하는 것 | 예시의 대시보드에 맞는 경우 |
| --- | --- | --- | --- |
| 템플릿 | 샷 구성, 타이밍, 사운드 배치 전체 | 캡처 소재, 문구, 브랜드 | 종이와 잉크 느낌이 사내 보고 톤과 맞을 때 |
| 샷 카드 | 샷 하나의 움직임과 파라미터 | 샷의 순서와 조합 | 디자인 시스템이 엄격하고 구성은 새로 짜야 할 때 |
| 자율 제작 | 절차, 품질 기준, 검수 | 시각 방향, 샷 매핑, 스토리보드 | 카드에 맞는 움직임이 없어 새로 써야 할 때 |

### 브랜드를 움직임 숫자로 옮기는 표

카드 바깥에서 움직임을 정할 때도 감에 맡기지 않습니다. 파이프라인 문서는 브랜드를 에너지 축과 톤 축에 놓고 가장 가까운 프리셋에서 출발하라고 합니다. 예를 들어 금융이나 기업용 제품에 해당하는 "전문 신뢰" 프리셋은 주 동작 길이 약 21프레임, 튀지 않는 감속 곡선, 과도 튐 없음으로 정해져 있고, 스포츠나 스타트업용 "활력" 프리셋은 약 18프레임에 과도 튐 1.12배입니다. [\[video-shotcraft: pipeline.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/pipeline.md)

예시의 청구 대시보드라면 "전문 신뢰"에서 출발하게 됩니다. 그리고 문서의 자가 점검 질문대로, 완성된 움직임을 세 단어로 묘사했을 때 브랜드를 설명하는 단어와 맞는지 확인합니다.

### 실패 모드와 비용

- 카드와 참조 구현이 서로 다른 말을 하면 어느 쪽이 맞는지 모델이 고를 수밖에 없습니다. 검수 문서가 색인, 카드, 소스, 미리보기가 충돌하면 충돌 사실을 보고하고 하나를 임의로 진실로 고르지 말라고 따로 적어 둔 이유라고 봅니다.
- 카드가 늘수록 유지 비용도 늘어납니다. 7월 26일 커밋에는 샷 카드 안의 낡은 `demos/` 경로 96곳을 고친 기록이 있습니다. 카드와 코드의 연결이 깨지면 "참조 구현을 읽어라"는 규칙이 지켜질 수 없습니다.
- 카드에 없는 움직임이 필요한 제품에는 이득이 줄어듭니다. 그때는 새로 쓰는 범위와 검증 위험을 설계 문서에 적으라는 것이 저장소의 규칙입니다.

## 4. 박자와 소리도 측정 가능한 규칙으로 바꾼다

영상에서 가장 감각에 의존할 것 같은 부분이 음악과의 싱크입니다. 이 저장소는 그것도 수치로 바꿉니다.

### 박자를 재는 방법

박자가 강한 BGM을 쓰는 영상은 모든 전환과 주요 모션이 박자 위에 떨어져야 한다는 것이 원칙입니다. 문서의 절차는 이렇습니다. [\[video-shotcraft: music-beat-sync.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/music-beat-sync.md)

1. librosa로 박자 시각 목록을 뽑습니다. 이때 라이브러리가 주는 템포 값 하나는 믿지 않습니다. 문서는 그 값이 2% 넘게 어긋날 수 있다고 적고, 박자 시각 목록 전체에 등간격 직선을 최소제곱으로 맞춰 실제 BPM과 위상을 구합니다.
2. 맞춘 직선과 실제 박자의 잔차가 ±15ms 안이면 기계적인 드럼이라 격자를 믿을 수 있고, 크면 템포가 바뀌는 구간이 있으니 구간을 나눠 맞춥니다.
3. 킥 드럼 대역만 걸러 박자별 에너지를 재고, 가장 강한 박 두세 개를 영상의 가장 큰 순간에 배정합니다.
4. 타임라인의 컷 위치를 프레임 번호가 아니라 박자 번호로 적습니다.
5. 렌더링한 영상에서 오디오를 뽑아 1번을 다시 하고, 설계한 컷 프레임과 가장 가까운 실제 박의 프레임 차이를 표로 냅니다.

4번은 코드로 이런 모양입니다. 문서에 있는 형태를 줄여 옮겼습니다.

```ts
// music-beat-sync.md의 방식을 줄인 것
export const FPS = 30;
export const BEAT0 = 0.2244;      // 첫 박의 시각(초), 1번에서 구한 값
export const BEAT_INT = 0.45465;  // 박 간격(초)
export const beatF = (n: number) => Math.round((BEAT0 + n * BEAT_INT) * FPS);

export const SHOTS = {
  open: { from: 0, to: beatF(8) },
  hero: { from: beatF(8), to: beatF(16) },
};
```

곡을 바꾸면 상수 두 개만 고치면 전체가 다시 배치됩니다. 효과음 배치표도 같은 `beatF(n)`로 쓰니 그림과 소리가 같은 사실 원천을 봅니다.

### 결과물에서 다시 잰다

5번이 게이트입니다. 맞췄다고 주장하는 것이 아니라 결과물에서 다시 측정합니다. 문서의 판정 기준은 3프레임 이하면 합격, 1.5프레임 이하면 이상적, 3프레임을 넘는 컷이 하나라도 있으면 필수 수정입니다. BGM을 원본 파일이 아니라 렌더링된 영상에서 재는 이유도 적혀 있습니다. 오디오 인코딩과 정렬 오차까지 함께 검증하기 위해서입니다.

문서에는 실제로 밟은 함정도 남아 있습니다. 가장 큰 순간을 두 박 사이에 두었는데 가장 강한 킥은 정수 박 위에 있어서, 렌더링 후 재측정에서 5.75프레임이 어긋났다는 기록입니다. 그래서 반 박에 맞추려면 귀가 아니라 에너지 데이터의 뒷받침이 있어야 한다는 규칙이 생겼습니다.

### 소리를 고르고 붙이는 순서

효과음도 고르는 순서가 정해져 있습니다. 7월 27일 커밋으로 효과음 라이브러리가 149개, 장면과 재질 기준의 16개 분류로 재구성되었고, README는 분류를 먼저 고른 뒤 음색을 고르라고 안내합니다. [\[video-shotcraft: README\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/README.md)

파이프라인의 6단계에는 순서에 관한 규칙이 더 있습니다. [\[video-shotcraft: pipeline.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/pipeline.md)

- 사운드 작업은 화면 타임라인이 고정된 뒤에 시작합니다. 화면이 움직일 때마다 효과음 배치표 전체를 다시 맞춰야 하기 때문입니다.
- 효과음 배치표는 파일 하나에 모으고, 시작 프레임은 맨 숫자가 아니라 샷 시작점에서의 상대 표현으로 씁니다. 타임라인이 밀리면 배치표가 따라 움직입니다.
- 5초가 넘는 긴 효과음은 재생 길이를 명시해야 합니다. 빠뜨리면 동작이 끝난 뒤에도 소리가 이어집니다.
- 녹음이 작게 된 소재는 볼륨 계수를 1.0으로 줘도 BGM에 묻히니, 같은 분류의 다른 소재로 바꾸거나 미리 정규화하라고 합니다. 미리보기는 볼륨을 1.0으로 자르므로 렌더링 결과물에서 확인해야 한다는 주의도 붙어 있습니다.
- BGM을 쓴 영상은 같은 타임라인에서 BGM 있는 판과 없는 판, 두 가지를 함께 납품합니다. 이 규칙은 7월 28일 커밋으로 들어왔습니다.

예시의 대시보드 영상이 사내 행사에서 다른 음악과 함께 쓰일 수 있다면, 마지막 규칙 덕분에 효과음은 살린 채 음악만 바꿀 수 있습니다.

### 실패 모드와 비용

- 이 절차는 박자가 분명한 음악을 전제로 합니다. 문서도 보컬이나 복잡한 편곡의 곡은 박자 추적이 흔들려 타악 성분을 먼저 분리해야 하고, 템포가 바뀌는 곡은 구간별로 맞춰야 한다고 적습니다.
- 측정 도구가 추가 의존성입니다. librosa와 scipy, ffmpeg가 필요하고, 문서는 uv로 일회성 환경을 만들어 돌리는 방법을 안내합니다. 사내 PC에서 패키지 설치가 막혀 있다면 이 단계부터 막힙니다.
- 음악 없이 효과음만 쓰는 영상에는 이 절차 대부분이 필요 없습니다. 실제로 Ink Press 템플릿은 BGM 없이 효과음만 쓰는 영상으로 만들어져 있습니다. [\[video-shotcraft: TEMPLATE.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/template/TEMPLATE.md)

## 5. 게이트는 프레임 확인, 결정적 렌더링, 독립 검수다

절차 문서는 검수가 마지막 단계가 아니라 전 과정에 걸쳐 있다고 강조합니다. 7단계의 정식 검수는 그동안 해 온 확인을 한 번 더 묶는 마무리일 뿐이라는 것입니다. [\[video-shotcraft: pipeline.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/pipeline.md)

```text
스토리보드 확정 (샷마다 확인할 프레임 번호 2개를 계획에 기록)
   │  (확정 전에는 전량 캡처와 샷 구현을 시작하지 않음)
   ▼
실제 페이지 캡처 ──> 샷 구현 ──> 지정 프레임 정지 이미지 확인
                                    │ 통과
                                    ▼
                         전체 렌더링 ──> 프레임 추출 회고, 박자 오차 재측정
                                    │
                                    ▼
                    깨끗한 컨텍스트의 검수 에이전트
                    (설계 문서와 결과물만 받음, 제작 과정의 해명은 받지 않음)
                                    │
                        ┌───────────┴───────────┐
                     필수 수정                  통과
                        │                       │
             3, 5, 6단계로 되돌림          최종 렌더링, 납품
```

### 완료의 정의를 프레임 번호로 고정한다

첫째 게이트는 정지 프레임입니다. 샷마다 확인할 프레임 번호 두 개를 계획에 미리 적고, 구현이 끝나면 `npx remotion still`로 그 프레임을 정지 이미지로 뽑아 구도, 의도치 않게 드러난 빈틈, 글자 선명도를 눈으로 확인한 뒤에야 완료로 칩니다. 이미지는 반복 차수별로 보관해서, 사용자가 결과물의 한 프레임을 잘라 의견을 주면 바로 대조할 수 있게 합니다.

완료의 정의가 "다 했다"는 말이 아니라 프레임 번호로 고정됩니다. 예시의 대시보드 영상이라면 주인공 위젯이 착지한 직후와 숫자가 다 올라간 직후의 프레임이 그 두 개가 될 것입니다.

### 다시 렌더링해도 같은 프레임이 나와야 한다

둘째 게이트는 결정적 렌더링입니다. 현재 시각이나 `Math.random()`, 인자 없는 `new Date()`를 직접 쓰지 못하게 하고, 무작위가 필요하면 인덱스에서 파생한 고정 seed를 쓰게 합니다. 다시 렌더링해도 프레임이 같아야 비교와 검수가 성립하기 때문입니다.

Remotion도 같은 이유로 seed를 받는 `random()` API를 따로 제공하고, 같은 seed면 언제나 같은 값을 준다고 설명합니다. [\[Remotion Docs: random()\]](https://www.remotion.dev/docs/random) 검수의 근거가 프레임 번호인 이상, 같은 번호에서 매번 다른 그림이 나오면 검수 보고서가 의미를 잃습니다.

### 만든 쪽이 채점하지 않는다

셋째 게이트가 가장 흥미롭습니다. 최종 검수는 제작에 참여하지 않은 에이전트가 합니다. 검수 문서는 이 에이전트를 깨끗한 컨텍스트에 두고, 제작 과정의 이유, 해명, 수정 이력, 기대하는 결론을 주지 말라고 적습니다. [\[video-shotcraft: final-review.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/final-review.md)

대신 무엇을 줄지는 아주 구체적입니다. 최신 결과물과 샷별 핵심 프레임, 제작 모드, 제품 요약과 필수 기능, 요구 사항에서 실행 결정까지의 표, 확정된 시각 방향과 토큰, 기능별 샷 매핑, 카드 이름과 스타일 변형, 색인 기록, 참조 구현 소스, 갤러리 미리보기, 최종 스토리보드, 데이터 처리 기준입니다. 빠진 입력이 있으면 "검증 불가"로 표시하고 추측하지 말라고 합니다.

점검 항목은 머리글자로 묶여 있습니다.

| 묶음 | 보는 것 | 예시의 대시보드에서 걸릴 만한 것 |
| --- | --- | --- |
| P 제품 목표 | 포지셔닝, 없는 기능의 과장 | 아직 없는 예측 기능을 보여 주는 장면 |
| F 기능 완결성 | 필수 기능마다 장면이 있는지, 같은 정보의 반복 | 필수였던 지연 청구 알림이 빠짐 |
| V 시각 방향 | 확정된 토큰과의 일치, 무관한 스타일로의 표류 | 사내 색 대신 템플릿의 호박색이 남음 |
| S 샷 카드 | 지정한 변형인지, 함정 파라미터를 지켰는지 | 착지 직후 카메라가 미세하게 흘러감 |
| B 스토리보드 일치 | 순서, 길이, 브랜드 로고 1초 정지 | 마지막 로고가 0.5초 만에 사라짐 |
| D 데이터 안전 | 실제 고객 정보 노출, 캡처 사용 여부 | 가짜 데이터 사이에 실제 이름 한 줄 |
| A 오디오 | 컷 오차 3프레임 이하, 긴 효과음 길이, 두 판 납품 | 전환음이 화면보다 4프레임 늦음 |
| Q 기술 품질 | 글자 선명도, 흔들림, 이음매 | 줌인 후 숫자가 흐림 |

보고서는 항목 번호와 프레임 번호를 함께 적는 형식입니다. "F2 ✗ 340프레임: 확정된 기능이 결과물에 없음"처럼 씁니다. 문서는 근거 없는 "전체적으로 좋음"으로 항목별 점검을 대신하지 말고, 보고서를 보기 좋게 하려고 전부 통과로 적지도 말라고 덧붙입니다.

만든 쪽이 스스로 채점하면 후하게 주기 쉽습니다. SKILL.md도 제작자는 자기 결과물에 확인 편향이 있으니 첫 검수를 사용자에게 넘기지 말고 독립 subagent에게 맡기라고 적습니다. 검수자를 분리하고 정보를 제한하는 것은 영상 밖에서도 그대로 쓸 수 있는 패턴입니다.

### 실패 모드와 비용

- 독립 검수는 결과물 전체를 다시 보는 일이라 비용이 듭니다. 영상이라면 프레임 추출과 이미지 입력이 따라옵니다.
- 검수자에게 줄 설계 문서가 없으면 이 게이트는 성립하지 않습니다. 공동 제작 문서가 확정 사항을 설계 문서로 남기고, 검수 에이전트가 흩어진 대화 기록으로 사용자가 무엇을 확정했는지 추측하게 하지 말라고 적은 이유입니다. [\[video-shotcraft: guided-free-creation.md\]](https://github.com/Vincentwei1021/video-shotcraft/blob/d4915443232e89527fdc9d7e79f132ba411fc440/references/guided-free-creation.md)
- 검수 기준표가 길면 검수자도 일부만 보고 통과시킬 수 있습니다. 항목별 결론에 프레임 번호를 요구하는 형식이 그것을 막는 장치입니다.

### 보수적인 조직의 눈으로 보면

보수적인 조직이라면 한 가지 더 확인할 것이 있습니다. README는 Remotion이 자체 라이선스를 가지고 있고, 개인과 작은 팀은 무료지만 회사는 유료 라이선스가 필요할 수 있다고 따로 적어 둡니다. 저장소가 Apache-2.0이라고 해서 의존 도구까지 같은 조건은 아닙니다. 효과음과 음악 소재도 각 파일의 라이선스 조건을 따르라고 하고, 출처 문서를 따로 둡니다. 도입 전에 법무 검토 대상에 넣어야 한다고 봅니다.

또 하나는 결과물의 감사 가능성입니다. 이 저장소의 절차를 따르면 설계 문서, 정지 프레임 보관본, 검수 보고서가 남습니다. 사내 보고용 영상이라도 "이 숫자는 실제 데이터인가"라는 질문에 답할 근거가 파일로 남는다는 점은 보수적인 조직에 맞는 성질이라고 봅니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 설치합니다. README가 안내하는 명령은 다음과 같습니다.

```bash
npx skills add Vincentwei1021/video-shotcraft
```

직접 받아서 연결하는 방법도 README에 있습니다.

```bash
git clone https://github.com/Vincentwei1021/video-shotcraft.git
cd video-shotcraft
ln -s "$(pwd)" ~/.claude/skills/video-shotcraft   # Claude Code
# or
ln -s "$(pwd)" ~/.codex/skills/video-shotcraft    # Codex
```

2. 처음에는 템플릿 모드로 한 번 돌려 봅니다. 구조가 고정된 상태에서 캡처, 데이터 고정, 소재 교체 과정만 확인할 수 있습니다. 머리 없는 리눅스 서버에서 렌더링한다면 README의 동시성, 헤드리스 셸, 브라우저 경로 관련 주의를 먼저 읽습니다.
3. `SKILL.md`, `references/pipeline.md`, `references/final-review.md`를 직접 읽습니다. 영상에 관심이 없어도 모드, 단계, 게이트를 문서로 어떻게 적었는지 참고할 만합니다.
4. 자기 팀의 반복 작업 하나를 골라 같은 틀로 적어 봅니다. 입력을 측정해 고정하는 단계, 선택지를 카드와 참조 구현으로 좁히는 단계, 결과에서 다시 재는 단계, 만든 쪽이 아닌 검수자가 근거와 함께 판정하는 단계가 있는지 확인합니다.

## 마치며

video-shotcraft가 보여 주는 것은 영상 제작 요령보다 skill을 짜는 방식입니다. 소재는 실제 화면에서 측정해 가져오고, 연출은 카드와 조율된 코드로 좁히고, 완료 여부는 프레임 번호와 박자 오차로 확인하고, 판정은 만든 쪽이 아닌 검수자에게 맡깁니다. 프롬프트를 길게 쓰는 대신 절차와 기준을 파일로 남긴 것입니다. 감각에 기대는 다른 반복 작업에도 같은 틀을 적용해 볼 만합니다.
