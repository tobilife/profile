:::note
- 컨텍스트 엔지니어링은 문장을 다듬는 일이 아니라, 매 스텝마다 컨텍스트 창에 무엇을 넣고 뺄지 정하는 시스템을 만드는 일입니다.
- 컨텍스트 창이 커져도 입력이 길어질수록 모델 성능은 불안정해집니다. 다 넣는 것은 전략이 아닙니다.
- 앞부분은 고정하고 뒤에만 덧붙이면 KV-cache가 살아서 비용과 지연이 함께 줄어듭니다.
- 줄일 때는 되돌릴 수 있게 줄이고, 원본은 컨텍스트 밖에 남겨 둡니다. 조립 순서와 예산은 코드가 쥡니다.
:::

컨텍스트 창이 100만 토큰까지 커지면서 "필요할 만한 것은 다 넣고 모델이 알아서 고르게 하면 된다"는 말이 자주 들립니다.

Chroma가 2025년 7월에 낸 보고서는 이 가정을 직접 시험했습니다. GPT-4.1, Claude 4, Gemini 2.5, Qwen3를 포함한 18개 모델을 평가했고, 모델이 컨텍스트를 균일하게 쓰지 않으며 입력이 길어질수록 성능이 점점 불안정해졌다고 보고합니다. [\[Chroma: Context Rot\]](https://research.trychroma.com/context-rot)

**컨텍스트 창은 클수록 좋은 저장소가 아니라, 매 스텝마다 무엇을 넣고 무엇을 뺄지 설계해야 하는 한정된 작업 메모리입니다.**

2025년 6월을 지나며 이 설계 작업을 컨텍스트 엔지니어링이라고 부르는 글이 늘었습니다. Simon Willison은 6월 27일에 이 용어가 프롬프트 엔지니어링의 더 나은 대안으로 힘을 얻고 있다고 적었습니다. [\[Simon Willison: Context engineering\]](https://simonwillison.net/2025/Jun/27/context-engineering/)

LangChain의 Harrison Chase는 이를 LLM이 과제를 해낼 수 있도록 알맞은 정보와 도구를 알맞은 형식으로 제공하는 동적 시스템을 만드는 일이라고 정의했습니다. [\[LangChain: The rise of context engineering\]](https://blog.langchain.com/the-rise-of-context-engineering/)

이 글은 하나의 예시를 끝까지 끌고 갑니다. 보험료 자동이체 배치가 늦어진 원인을 찾는 장애 분석 에이전트입니다. 로그와 지표를 많이 읽어야 하고 스텝이 길어지는 업무라서, 컨텍스트 설계의 문제가 거의 다 나타납니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 운영 장애의 원인을 찾는 에이전트를 만들었다고 해봅시다. 새벽 자동이체 배치가 평소보다 두 시간 늦게 끝났고, 에이전트에게 "자동이체 지연의 원인을 찾아라"라고 맡깁니다.

시스템 프롬프트 첫 줄에는 초 단위의 현재 시각이 들어갑니다. 로그 조회 도구는 호출할 때마다 수천 줄을 그대로 돌려줍니다. 이력은 전부 쌓아 둡니다.

처음 열 스텝은 순조롭습니다. 서른 스텝쯤 지나면 에이전트는 이미 확인한 로그를 다시 조회하기 시작합니다. 처음에 받은 목표는 수만 토큰 앞에 묻혀 있습니다. 열다섯 번째 스텝에서 잘못 읽은 "DB 락 대기"라는 가설이 이후 판단마다 근거로 다시 등장합니다.

비용도 이상합니다. 매 스텝 입력이 조금씩 늘어날 뿐인데 청구되는 금액은 그보다 훨씬 가파르게 오릅니다.

모델을 더 좋은 것으로 바꿔도 이 문제는 그대로 남습니다. 시스템 설계 관점에서 잘못된 건 네 가지입니다.

- 도구 결과가 컨텍스트에 들어가는 양을 아무도 정하지 않았습니다.
- 맨 앞의 시각 한 줄이 매 호출마다 바뀌어, 그 뒤 전체가 캐시되지 않았습니다.
- 길어진 이력 속에서 목표를 다시 꺼내 주는 장치가 없었습니다.
- 틀린 중간 결론이 이력에 남아, 이후 판단을 계속 오염시켰습니다.

## 1. 컨텍스트에는 네 가지가 들어가고, 각각 수명이 다릅니다

LLM 호출 한 번에 들어가는 내용을 출처별로 나눠 보면 관리 방법이 달라야 한다는 점이 보입니다.

LangChain은 컨텍스트의 유형을 지시(프롬프트, 메모리, few-shot 예시, 도구 설명), 지식(사실, 메모리), 도구(도구 호출의 피드백)로 분류합니다. 같은 글은 Andrej Karpathy의 비유를 빌려, LLM을 CPU로, 컨텍스트 창을 용량이 제한된 RAM으로 봅니다. [\[LangChain: Context Engineering\]](https://blog.langchain.com/context-engineering-for-agents/)

실무에서는 아래 네 줄로 놓고 보는 편이 다루기 쉽다고 봅니다. 수명과 위험 열은 제 정리입니다.

| 들어가는 것 | 누가 넣는가 | 수명 | 방치하면 생기는 일 |
| --- | --- | --- | --- |
| 지시(시스템 프롬프트, 도구 정의) | 개발자 | 세션 내내 고정 | 길어질수록 서로 충돌 |
| 도구 결과 | 루프가 자동으로 | 스텝마다 누적 | 창을 가장 빨리 채움 |
| 메모리 | 에이전트 또는 harness | 세션을 넘어 지속 | 관련 없는 기억이 끼어듦 |
| 검색 결과 | 검색 단계 | 그 질문에만 유효 | 비슷하지만 틀린 문서가 섞임 |

### 한 스텝마다 입력이 어떻게 자라는가

에이전트 루프에서 컨텍스트가 자라는 방식은 단순합니다. Manus의 설명을 따르면, 모델은 현재 컨텍스트를 보고 행동 하나를 고르고, 그 행동이 환경에서 실행되어 관측을 만들고, 행동과 관측이 컨텍스트에 덧붙여져 다음 반복의 입력이 됩니다. [\[Manus: Context Engineering for AI Agents\]](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

컨텍스트는 스텝마다 커지는데 출력은 대개 짧은 함수 호출 하나입니다. 그래서 Manus는 자사 에이전트의 평균 입력 대 출력 토큰 비율이 약 100:1이라고 밝혔습니다.

에이전트의 비용과 품질은 대부분 입력 쪽에서 결정된다는 뜻입니다. 프롬프트 문장을 다듬는 것보다, 매 스텝의 입력에 무엇이 쌓이는지를 통제하는 쪽이 효과가 큽니다.

### 예산을 표로 적어 둡니다

장애 분석 에이전트의 한 호출을 예산으로 적으면 이런 모양이 됩니다. 아래 숫자는 제가 가정한 예시입니다.

```yaml
# 예시: 장애 분석 에이전트의 호출당 컨텍스트 예산 (총 60,000 토큰 가정)
context_budget:
  system_and_tools:   { max: 6000,  policy: "고정, 세션 중 변경 금지" }
  runbook_snippets:   { max: 4000,  policy: "증상 키워드로 상위 3개만 선택" }
  memory:             { max: 2000,  policy: "이번 장애와 같은 배치명에 대한 과거 메모만" }
  history:            { max: 40000, policy: "최근 관측 5개는 원문, 이전은 한 줄 요약 + 파일 경로" }
  tool_result_latest: { max: 6000,  policy: "초과 시 상위 N줄 + 패턴 요약 + 전체 파일 경로" }
  plan_recitation:    { max: 2000,  policy: "todo 파일을 매 스텝 맨 뒤에 다시 넣음" }
```

숫자 자체보다 중요한 것은 항목마다 "넘치면 무엇을 하는가"가 적혀 있다는 점입니다. 예산이 없는 컨텍스트는 넘칠 때까지 아무도 모릅니다.

### 실패 모드: 예산 없이 쌓을 때

예산이 없으면 가장 빨리 자라는 칸이 나머지를 밀어냅니다. 장애 분석에서는 그 칸이 거의 항상 도구 결과입니다.

그 결과는 두 가지로 나타납니다. 창 한도에 닿아 API 에러가 나거나, 그보다 먼저 품질이 조용히 떨어집니다. 첫 번째는 눈에 보이니 오히려 낫습니다. 다음 절은 두 번째 이야기입니다.

## 2. 긴 컨텍스트는 에러 없이 조용히 망가집니다

컨텍스트가 넘치면 API가 에러를 냅니다. 그건 오히려 다루기 쉬운 실패입니다.

더 곤란한 것은 한도에 닿기 한참 전부터 품질이 떨어지는 경우입니다. Chroma 보고서의 제목인 context rot가 바로 이 현상을 가리킵니다. [\[Chroma: Context Rot\]](https://research.trychroma.com/context-rot)

### Chroma 실험이 보여 준 것

보고서에서 실무에 바로 옮길 수 있는 실험은 LongMemEval을 쓴 대화형 질의응답입니다. 같은 질문을 두 가지 입력으로 물었습니다. 관련 부분만 담은 평균 약 300토큰의 입력과, 무관한 내용까지 포함한 평균 약 113,000토큰의 전체 입력입니다.

결과는 일관됐습니다. 모델들은 짧은 입력에서는 잘 풀었고, 전체 입력에서는 일관되게 성능이 떨어졌습니다. 풀어야 할 추론은 같고, 달라진 것은 주변의 무관한 텍스트뿐이었습니다.

방해 요소에 대한 관찰도 있습니다. 질문과 비슷하지만 답은 아닌 문장, 즉 distractor는 성능에 균일하지 않게 영향을 주고, 질문과 정답 문장의 유사도가 낮을수록 입력이 길어질 때 성능이 더 크게 떨어졌다고 합니다. 18개 모델 모두에서 논리적으로 이어진 글보다 문장을 무작위로 섞은 글에서 오히려 성능이 좋았다는 결과도 보고합니다.

장애 분석에 옮기면, "DB 락 대기"처럼 원인과 비슷해 보이지만 원인이 아닌 로그 줄이 바로 distractor입니다. 로그를 통째로 넣을수록 그런 줄도 함께 늘어납니다.

### 네 가지 실패 유형

Drew Breunig는 긴 컨텍스트가 실패하는 방식을 네 가지로 나눴습니다. [\[Drew Breunig: How Long Contexts Fail\]](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html)

| 실패 유형 | 무슨 일이 일어나는가 | 장애 분석 에이전트에서 |
| --- | --- | --- |
| Context Poisoning | 환각이나 오류가 컨텍스트에 들어가 계속 참조됨 | 잘못 읽은 "DB 락 대기" 가설이 계속 근거로 쓰임 |
| Context Distraction | 컨텍스트가 너무 길어져 모델이 학습한 것보다 이력에 매달림 | 이미 본 로그를 다시 조회함 |
| Context Confusion | 불필요한 내용이 응답에 영향을 줌 | 무관한 배치의 경고 로그를 원인 후보로 올림 |
| Context Clash | 컨텍스트 안의 정보나 도구가 서로 모순됨 | 오래된 runbook과 현재 설정값이 다름 |

오른쪽 열은 제가 예시에 맞춰 붙인 것입니다.

같은 글은 Gemini 2.5 기술 보고서의 관찰도 인용합니다. 포켓몬 게임을 하던 에이전트의 컨텍스트가 10만 토큰을 크게 넘어서자, 새 계획을 세우기보다 방대한 이력 속의 행동을 반복하는 경향을 보였다는 내용입니다. Poisoning의 예도 같은 보고서에서 가져옵니다. 에이전트가 게임 상태를 환각하고, 컨텍스트의 목표나 요약 부분이 그 잘못된 정보로 오염되면 되돌리는 데 오랜 시간이 걸리며, 이룰 수 없는 목표를 좇아 말이 안 되는 전략과 반복 행동을 보였다는 것입니다.

장애 분석에서 열다섯 번째 스텝의 잘못된 가설이 계속 근거로 쓰인 것이 이 구조입니다. 요약이나 계획 같은 "자주 다시 읽히는 칸"에 틀린 내용이 들어가면, 오류가 한 번이 아니라 매 스텝 다시 입력됩니다.

Breunig의 표현을 빌리면, 컨텍스트에 넣은 것은 모델이 주의를 기울여야 하는 대상이 됩니다. 관련 없는 정보든 쓸 일 없는 도구 정의든 마찬가지입니다.

### 위치도 결과를 바꿉니다

길이뿐 아니라 위치도 중요합니다. 2023년의 "Lost in the Middle" 연구는 관련 정보가 입력의 처음이나 끝에 있을 때 성능이 가장 높고, 긴 컨텍스트의 가운데에 있을 때 크게 떨어지며, 긴 컨텍스트용 모델에서도 그렇다고 보고했습니다. [\[Liu et al.: Lost in the Middle\]](https://arxiv.org/abs/2307.03172)

이 결과는 뒤에서 볼 "목표를 컨텍스트 끝에 다시 넣는" 기법의 근거가 됩니다. 처음에 준 목표는 스텝이 쌓일수록 점점 가운데로 밀려나기 때문입니다.

### 실패 모드: 이 문제를 과하게 걱정할 때

반대 방향의 실수도 있다고 봅니다. 스텝이 몇 개뿐이고 도구 결과도 작은 업무에 요약, 검색, 격리 장치를 모두 붙이면, 그 장치들이 오히려 새로운 오류 지점이 됩니다.

그래서 저는 먼저 실제 실행의 입력 길이 분포를 봅니다. 대부분의 실행이 창의 작은 일부만 쓰고 끝난다면, 다음 절의 캐시 구조만 챙기고 나머지는 미루는 편이 낫습니다.

## 3. 앞은 고정하고 뒤에만 붙입니다: KV-cache 친화적인 구조

컨텍스트 설계에는 품질 말고 비용이라는 축이 하나 더 있습니다.

Manus는 운영 단계의 에이전트에서 지표를 하나만 고른다면 KV-cache 적중률이라고 말합니다. 앞부분이 같은 컨텍스트는 캐시를 활용할 수 있어서 첫 토큰까지의 시간과 추론 비용이 크게 줄기 때문입니다. 글이 든 예로는 Claude Sonnet의 캐시된 입력 토큰이 100만 토큰당 0.30달러, 캐시되지 않은 입력이 3달러로 10배 차이였습니다. [\[Manus: Context Engineering for AI Agents\]](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

### Prefix 캐시는 어떻게 작동하는가

Anthropic의 prompt caching 문서를 보면 구조가 분명합니다. 캐시는 도구 정의, 시스템 프롬프트, 메시지 순서로 이어지는 prefix 전체를 기준으로 하고, 이 계층의 어느 단계가 바뀌면 그 단계와 그 뒤의 모든 단계가 무효가 됩니다. 도구 정의를 바꾸면 캐시 전체가 무효가 된다는 뜻입니다. [\[Anthropic: Prompt caching\]](https://web.archive.org/web/20250803210544/https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)

같은 문서의 수치도 설계에 영향을 줍니다. 2025년 8월 초 기준으로 정리하면 이렇습니다.

| 항목 | 문서의 설명 | 설계에 주는 의미 |
| --- | --- | --- |
| 기본 수명 | 5분, 사용할 때마다 추가 비용 없이 갱신 (1시간 옵션은 beta) | 스텝 간격이 길면 캐시가 식음 |
| 캐시 쓰기 비용 | 5분 캐시 쓰기는 기본 입력 가격의 1.25배 | 재사용되지 않는 캐시는 손해 |
| 캐시 읽기 비용 | 기본 입력 가격의 10% | 고정 prefix가 길수록 이득 |
| 최소 길이 | Opus 4, Sonnet 4 등은 1,024토큰, Haiku 계열은 2,048토큰 | 짧은 prefix는 캐시되지 않음 |
| breakpoint | 최대 4개, 각 breakpoint에서 약 20개 블록 앞까지 자동 탐색 | 긴 이력에는 중간 breakpoint 필요 |
| 무효화 | `tool_choice` 변경, 이미지 유무 변경도 캐시를 깸 | 호출마다 이 값을 바꾸지 않음 |

### Manus의 세 가지 실천 사항

Manus가 제시하는 실천 사항은 세 가지입니다.

- 프롬프트 앞부분을 안정적으로 유지합니다. 토큰 하나만 달라도 그 지점부터 캐시가 무효가 됩니다. 시스템 프롬프트 맨 앞에 초 단위 타임스탬프를 넣는 것이 흔한 실수로 꼽힙니다.
- 컨텍스트를 append-only로 만듭니다. 이전 행동과 관측을 고치지 않고, 직렬화를 결정적으로 합니다. JSON 키 순서가 보장되지 않는 라이브러리는 캐시를 조용히 깨뜨릴 수 있습니다.
- 필요하면 캐시 breakpoint를 명시적으로 지정합니다. 만료 가능성을 고려하고, 최소한 시스템 프롬프트의 끝은 breakpoint에 포함합니다.

구조로 그리면 이렇습니다. 아래는 설명을 위한 예시입니다.

```text
나쁜 배치                              좋은 배치
---------------------------------      ---------------------------------
[현재 시각: 03:14:27]   <- 매번 바뀜    [도구 정의]             <- 고정
[시스템 지시]                           [시스템 지시]           <- 고정
[도구 정의: 스텝마다 넣고 뺌]            ---- breakpoint 1 ----
[이력: 중간중간 수정]                    [이력 1..n]             <- 덧붙이기만
[새 관측]                               ---- breakpoint 2 (주기적으로 이동) ----
                                       [새 관측]
                                       [현재 시각, 남은 할 일] <- 맨 뒤에
```

장애 분석 사례에서 비용이 가파르게 오른 이유가 여기에 있습니다. 맨 앞의 시각 한 줄 때문에 매 스텝 전체 입력을 캐시 없이 다시 계산한 것입니다. 시각은 필요하지만, 맨 뒤에 두면 앞부분의 캐시를 깨지 않습니다.

### 도구 목록도 고정합니다

도구 목록도 같은 원칙을 따릅니다. Manus는 반복 도중에 도구를 동적으로 넣고 빼는 것을 피하라고 합니다. 도구 정의는 보통 컨텍스트 앞쪽에 놓여서 바뀌면 그 뒤의 캐시가 전부 무효가 되고, 이전 행동이 지금은 정의되지 않은 도구를 가리키면 모델이 혼란스러워하기 때문입니다.

대신 Manus는 도구 정의는 그대로 두고, 상태에 따라 고를 수 있는 행동을 디코딩 단계에서 제한하는 방식을 씁니다. 응답 prefill로 특정 이름 접두사로 시작하는 함수만 고르게 하는 식입니다.

### 적중률은 응답에서 바로 잽니다

캐시가 실제로 맞고 있는지는 추측할 필요가 없습니다. Anthropic의 문서는 응답의 `usage` 안에 세 필드를 둡니다. 캐시에 새로 쓴 토큰 수(`cache_creation_input_tokens`), 캐시에서 읽은 토큰 수(`cache_read_input_tokens`), 그리고 둘 다 아닌 입력 토큰 수(`input_tokens`)입니다. [\[Anthropic: Prompt caching\]](https://web.archive.org/web/20250803210544/https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)

장애 분석 에이전트라면 스텝마다 이 세 값을 trace에 남기고, "읽은 토큰 ÷ 전체 입력 토큰"을 스텝별로 그려 보는 것으로 충분합니다. 스텝이 진행될수록 이 비율이 올라가야 정상이고, 어느 스텝에서 뚝 떨어진다면 그 직전에 prefix의 무언가가 바뀐 것입니다. 원인을 찾을 때는 그 두 스텝의 입력을 앞에서부터 비교하면 됩니다.

### 실패 모드: 캐시를 깨는 흔한 원인

캐시가 깨지는 원인은 대개 사소해서 찾기 어렵습니다. 점검 목록으로 두면 이렇습니다.

- 시스템 프롬프트나 도구 설명 안의 시각, 요청 ID, 사용자별 값
- 키 순서가 보장되지 않는 JSON 직렬화
- 스텝마다 바뀌는 `tool_choice`나 도구 목록
- 이력의 중간을 고쳐 쓰는 요약이나 마스킹
- 스텝 간격이 캐시 수명보다 길어지는 사람 승인 대기

마지막 항목은 비용 계산을 바꿉니다. 승인 대기가 길어 캐시가 매번 식는다면, 쓰기 비용 1.25배만 내고 읽기 이득은 못 얻을 수 있습니다. 이런 흐름에서는 breakpoint를 줄이거나 긴 수명 옵션을 검토하는 편이 낫다고 봅니다.

## 4. 고르고, 줄이고, 나누되 되돌릴 수 있게

고정하고 덧붙이기만 하면 언젠가는 창이 찹니다. 그래서 줄이는 전략이 필요합니다.

LangChain은 에이전트의 컨텍스트 관리 전략을 네 묶음으로 정리했습니다. [\[LangChain: Context Engineering\]](https://blog.langchain.com/context-engineering-for-agents/)

| 전략 | 뜻 | 예 | 장애 분석에서 |
| --- | --- | --- | --- |
| Write | 컨텍스트 창 밖에 적어 둠 | scratchpad, 세션을 넘는 메모리 | 조사 메모와 todo 파일 |
| Select | 필요한 것만 창 안으로 가져옴 | 메모리 선택, 도구 설명 검색, RAG | 증상에 맞는 runbook 조각만 |
| Compress | 필요한 토큰만 남김 | 이력 요약, 도구 결과 후처리 | 오래된 로그 관측을 한 줄로 |
| Isolate | 컨텍스트를 나눔 | 서브에이전트, 샌드박스 | 배치별 로그 조사를 분리 |

### Write: 창 밖에 적어 두는 두 가지 방식

Write에는 수명이 다른 두 가지가 있습니다. LangChain 글은 한 세션 안에서 쓰는 scratchpad와 여러 세션에 걸쳐 남는 메모리를 나눕니다. Scratchpad는 파일에 쓰는 도구 호출로 만들 수도, 런타임 상태 객체의 필드로 만들 수도 있다고 합니다. 세션을 넘는 메모리의 예로는 많은 코딩 에이전트가 지시를 특정 파일에 저장해 항상 컨텍스트에 넣는 방식을 들고, Claude Code의 `CLAUDE.md`와 Cursor, Windsurf의 rules 파일을 예로 듭니다. [\[LangChain: Context Engineering\]](https://blog.langchain.com/context-engineering-for-agents/)

같은 글은 메모리 선택의 어려움도 짚습니다. Simon Willison이 공유한 사례로, ChatGPT가 메모리에서 그의 위치 정보를 가져와 요청한 이미지에 예상치 않게 넣은 일을 소개합니다. 원하지 않은 기억이 끼어들면 사용자는 컨텍스트 창이 자기 것이 아니라고 느낄 수 있다는 것입니다.

장애 분석 에이전트에서 scratchpad는 이번 장애의 todo와 조사 메모이고, 세션을 넘는 메모리는 "자동이체 배치는 월초에 처리 건수가 평소의 세 배" 같은 운영 지식입니다. 저는 후자를 에이전트가 자동으로 쓰게 하기보다, 장애 회고 때 사람이 검토해 runbook에 넣는 편을 권합니다. 잘못 쓰인 운영 지식은 다음 장애의 poisoning이 되기 때문입니다.

### Select: 도구와 문서를 고릅니다

Breunig는 후속 글에서 선택의 효과를 숫자로 정리했습니다. DeepSeek-v3에서는 도구가 30개를 넘으면 올바른 도구를 고르는 일이 중요해지고, RAG로 30개 미만의 도구만 골라 넣었을 때 프롬프트가 크게 짧아지고 도구 선택 정확도가 최대 3배 좋아졌다는 연구를 소개합니다. 작은 모델은 문제가 훨씬 일찍 시작되어, Llama 3.1 8b는 도구 46개를 받았을 때 실패한 벤치마크를 19개만 받았을 때는 통과했다고 합니다. [\[Drew Breunig: How to Fix Your Context\]](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html)

이 결과는 3절의 "도구 목록을 고정하라"는 조언과 충돌하는 것처럼 보입니다. 저는 둘을 이렇게 나눕니다. 세션을 시작할 때 업무에 맞는 도구 묶음을 고르는 것은 Select이고, 세션 도중에 그 묶음을 바꾸지 않는 것이 캐시 원칙입니다. 장애 분석 에이전트라면 "배치 장애" 묶음을 세션 시작 시 한 번 고르고 끝까지 유지합니다.

### Compress: 요약에는 대가가 있습니다

Compress의 대표적인 예로 LangChain 글은 Claude Code의 auto-compact를 듭니다. 컨텍스트 창의 95%를 넘으면 사용자와 에이전트가 주고받은 전체 과정을 요약한다는 것입니다.

요약에는 대가가 있습니다. Manus는 에이전트가 이전 상태 전체를 바탕으로 다음 행동을 정하는데, 어떤 관측이 열 스텝 뒤에 결정적일지 미리 알 수 없으므로 되돌릴 수 없는 압축에는 위험이 따른다고 지적합니다. [\[Manus: Context Engineering for AI Agents\]](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

그래서 Manus가 택한 방법은 파일 시스템을 컨텍스트로 쓰는 것입니다. 웹 페이지 내용은 URL이 남아 있으면 컨텍스트에서 빼고, 문서 내용은 경로가 남아 있으면 생략합니다. 필요하면 다시 읽을 수 있으니 정보는 사라지지 않습니다.

Cognition은 행동과 대화 이력을 핵심 세부 사항, 사건, 결정으로 압축하는 전용 모델을 두는 방식을 소개하면서, 제대로 하기 어렵다는 점도 함께 적었습니다. [\[Cognition: Don't Build Multi-Agents\]](https://cognition.ai/blog/dont-build-multi-agents)

요약과 잘라 내기는 비용 구조도 다릅니다. LangChain 글은 LLM으로 핵심을 추리는 요약과, 오래된 메시지를 지우는 것 같은 고정 규칙으로 걸러 내는 trimming을 구분합니다. 요약은 정보를 더 잘 보존하는 대신 그 자체가 LLM 호출이라 비용과 지연이 들고, 요약 모델이 틀리면 그 틀린 요약이 poisoning의 출발점이 됩니다. Trimming은 싸고 결정적이지만 무엇이 사라지는지 모델이 판단하지 않습니다.

그래서 저는 순서를 이렇게 둡니다. 먼저 결정적인 규칙으로 줄이고(오래된 관측 접기, 상한 넘는 결과 offload), 그래도 부족할 때만 LLM 요약을 쓰며, 요약할 때도 원본 파일 경로를 요약 안에 남깁니다. 3절의 캐시 관점에서도, 이력 중간을 자주 고쳐 쓰는 요약은 그 지점 뒤의 캐시를 깨므로 드물게, 큰 단위로 하는 편이 낫습니다.

장애 분석에서 되돌릴 수 있는 압축은 이런 모양입니다. 로그 조회 결과 전체는 `incident/logs/step-12.txt`에 쓰고, 이력에는 "step 12: 배치 서버 A 로그 4,210줄, ERROR 0건, WARN 37건(커넥션 풀 대기), 전체는 파일 참조" 한 줄만 남깁니다.

### Isolate: 무거운 조사는 다른 창에서 합니다

Breunig는 컨텍스트를 별도의 스레드로 떼어 내는 것을 context quarantine이라고 부르고, 에이전트 유형마다 전용 도구 묶음과 지시를 줄 수 있다는 이점도 짚습니다. [\[Drew Breunig: How to Fix Your Context\]](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html)

Anthropic의 리서치 시스템이 이 방식을 씁니다. 서브에이전트가 각자의 컨텍스트에서 많이 읽고, 리드에게는 압축한 결과만 돌려줍니다. 리드 에이전트는 먼저 계획을 메모리에 저장하는데, 컨텍스트가 20만 토큰을 넘으면 잘리지만 계획은 남아야 하기 때문입니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/built-multi-agent-research-system)

장애 분석에서는 배치 서버 로그, DB 대기 이벤트, 네트워크 지표를 각각 따로 조사하게 하고, 메인 에이전트는 세 요약만 받아 원인을 판단하는 구성이 후보입니다. 다만 격리한 쪽은 서로의 발견을 보지 못하므로, 결론은 한곳에서 내리는 편이 안전합니다.

### 목표를 뒤쪽으로 다시 꺼냅니다

긴 이력 속에서 목표가 묻히는 문제에는 별도의 장치가 필요합니다.

Manus는 복잡한 작업에서 `todo.md` 파일을 만들고 단계마다 갱신합니다. 할 일 목록을 계속 다시 쓰면서 전체 계획을 컨텍스트의 끝부분, 즉 모델의 최근 주의 범위로 끌어오는 것입니다. Manus의 작업은 평균 50회 정도의 도구 호출이 필요하다고 하고, 글은 이것을 lost-in-the-middle 문제를 피하고 목표 이탈을 줄이는 방법으로 설명합니다.

장애 분석 에이전트의 todo는 이렇게 생길 수 있습니다. 아래는 예시입니다.

```text
# todo (step 31 갱신)
목표: 06-03 자동이체 배치 2시간 지연의 원인 찾기
[x] 배치 시작과 종료 시각 확인 (01:00 시작, 05:12 종료, 평소 03:05)
[x] 배치 서버 A 로그: ERROR 없음, 커넥션 풀 대기 WARN 37건
[ ] DB 대기 이벤트: 01:40~04:50 구간 확인
[ ] 같은 시간대 다른 배치와 겹침 여부
기각한 가설: DB 락 대기 (step 15) -> 락 대기 이벤트 0건으로 기각 (step 22)
```

마지막 줄이 poisoning을 막는 장치이기도 합니다. 틀린 가설을 지우는 대신, 기각했다는 사실과 근거를 목표 바로 옆에 둡니다.

### 실패한 시도는 지우지 않습니다

컨텍스트를 깔끔하게 유지하려고 에러와 실패한 호출을 지우고 싶어질 수 있습니다.

Manus는 반대로 하라고 합니다. 실패한 행동과 그 결과가 컨텍스트에 남아 있어야 모델이 같은 실수를 반복할 가능성이 줄어든다는 것입니다. 실패를 지우면 증거가 사라지고, 증거가 없으면 모델이 적응할 수 없다고 표현합니다.

같은 글은 반대 방향의 위험도 짚습니다. 컨텍스트가 비슷한 행동과 관측의 반복으로 가득하면 모델이 그 패턴을 그대로 따라 하며 표류합니다. 그래서 직렬화 템플릿이나 표현을 조금씩 바꿔 구조화된 변형을 넣는다고 합니다.

줄여야 할 것은 중복된 대량의 관측이지, 무엇을 시도했고 어떻게 실패했는지에 대한 기록이 아닙니다.

### 실패 모드: 줄이는 장치가 새 오류가 될 때

네 전략은 각자 다른 방식으로 깨진다고 봅니다. 장애 분석 에이전트로 예를 들면 이렇습니다.

- Offload한 파일이 정리 작업으로 지워지거나 경로가 바뀌면, 한 줄 요약만 남고 원본으로 돌아갈 길이 끊깁니다. 경로를 남겼다면 그 파일의 보존 기간도 세션보다 길어야 합니다.
- 격리한 조사는 경계에 걸친 원인을 놓치기 쉽습니다. 이번 지연의 원인이 "자동이체 배치와 정산 배치가 같은 커넥션 풀을 나눠 쓴 것"이라면, 배치별로 나눈 조사들은 각자 "특이 사항 없음"을 돌려줄 수 있습니다.
- Select가 놓친 runbook 조각은 모델 입장에서 존재하지 않는 지식입니다. 증상 키워드가 빗나가면 정답 문서가 창 밖에 남습니다.

그래서 줄이는 장치를 넣을 때마다, 그 장치가 빼 버린 것을 사람이 볼 수 있는 기록도 함께 남기는 편이 안전합니다.

## 5. 컨텍스트 조립은 코드로 소유합니다

지금까지의 기법은 결국 "매 호출 직전에 컨텍스트를 어떤 순서로 무엇을 넣어 조립하는가"라는 함수 하나로 모입니다. 이 함수를 프레임워크의 기본값에 맡기지 않고 코드로 갖고 있는 것이 컨텍스트 엔지니어링의 실체라고 봅니다.

### 조립 함수의 모양

장애 분석 에이전트의 조립 함수를 의사 코드로 쓰면 이렇습니다. 아래는 설명을 위한 예시입니다.

```python
# 예시: 매 호출 직전에 컨텍스트를 조립하는 함수 (설명용 의사 코드)
def build_context(state, budget):
    ctx = []
    ctx += STATIC_TOOLS                      # 세션 시작 시 고른 묶음, 이후 불변
    ctx += [SYSTEM_PROMPT]                   # 시각, 요청 ID 같은 가변값 없음
    ctx += [cache_breakpoint()]

    for i, step in enumerate(state.history):
        if i >= len(state.history) - 5:
            ctx += [step.full]               # 최근 5개는 원문
        else:
            ctx += [step.one_line_with_path] # 이전은 한 줄 + 원본 파일 경로

    ctx += [select_runbook(state.symptoms, top_k=3)]
    ctx += [read_file("todo.md")]            # 목표와 기각한 가설을 맨 뒤로
    ctx += [f"현재 시각: {now()}"]            # 가변값은 끝에

    assert count_tokens(ctx) <= budget.total, "예산 초과: 요약 단계로"
    return ctx
```

이 함수가 있으면 "이번 호출에 모델이 무엇을 봤는가"를 언제든 재현할 수 있습니다. 반대로 이 함수가 프레임워크 안에 숨어 있으면, 품질이 떨어졌을 때 원인을 찾을 방법이 마땅치 않습니다.

### 증상에서 처방으로

증상별로 어떤 전략을 먼저 꺼낼지 정리하면 이렇습니다. 표는 제 정리입니다.

| 관찰한 증상 | 먼저 의심할 것 | 첫 처방 |
| --- | --- | --- |
| 비용이 스텝 수보다 가파르게 오름 | 캐시 무효화 | 가변값을 뒤로, 직렬화 고정 |
| 이미 한 조회를 반복함 | Distraction | 오래된 관측 접기, todo 재주입 |
| 틀린 가설을 계속 근거로 씀 | Poisoning | 기각 기록을 todo에 명시 |
| 엉뚱한 도구를 고름 | Confusion, 도구 과다 | 세션 시작 시 도구 묶음 선택 |
| 창 한도 에러 | 도구 결과 과다 | 결과 상한과 파일 offload |
| 긴 작업 끝에 목표를 잊음 | 위치 효과 | 목표를 컨텍스트 끝에 재배치 |

### 보수적인 엔터프라이즈 IT에서는

감사 추적이 필요한 조직이라면 "모델에게 보여 준 것"과 "기록으로 남기는 것"을 분리해야 한다고 봅니다.

Compaction은 모델 입력에만 적용하고, 원본 trace는 요약 전 상태 그대로 별도 저장소에 남기는 편이 안전합니다. 나중에 "왜 이런 판단이 나왔는가"를 설명하려면 요약본이 아니라 원본이 필요하기 때문입니다. 앞의 조립 함수가 만든 입력 자체를 호출마다 저장해 두면, 감사 때 모델이 본 화면을 그대로 재현할 수 있습니다.

세션을 넘어 지속되는 메모리는 더 조심스럽게 다뤄야 한다고 생각합니다. 고객 정보가 에이전트의 메모리 파일에 남는 순간, 그 파일은 보존 기간과 접근 권한을 따져야 하는 데이터가 됩니다. 장애 분석처럼 운영 로그를 읽는 에이전트도 로그 안의 계좌번호나 연락처를 파일로 offload하는 순간 같은 문제를 안게 되므로, offload 경로에도 기존 로그와 같은 마스킹과 보존 정책을 적용하는 편이 맞다고 봅니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 에이전트의 한 실행에서 마지막 LLM 호출의 입력을 통째로 꺼내 읽어 봅니다. 지시, 도구 결과, 메모리, 검색 결과가 각각 몇 토큰인지 세고, 항목별 예산과 넘칠 때의 처리를 표로 적습니다.
2. 시스템 프롬프트와 도구 정의에서 호출마다 바뀌는 값을 찾아 맨 뒤로 옮기고, 응답의 캐시 사용량 필드로 적중률을 확인합니다. 타임스탬프와 정렬되지 않은 JSON이 흔한 범인입니다.
3. 도구 결과에 상한을 두고, 큰 결과는 파일이나 저장소에 쓴 뒤 경로와 한 줄 요약만 컨텍스트에 남깁니다.
4. 긴 작업에는 목표, 진행 상황, 기각한 가설을 담은 todo 파일을 두고, 매 스텝 컨텍스트 끝에 다시 넣습니다.
5. 요약을 도입하기 전에 원본 이력과 호출별 입력을 어디에 보관할지부터 정합니다.

## 마치며

컨텍스트 엔지니어링은 새로운 기법이라기보다, 에이전트를 만들면 누구나 부딪히는 문제에 붙은 이름입니다.

창이 커진다고 문제가 사라지지는 않습니다. 넣을 수 있는 양이 늘 뿐, 모델이 주의를 기울일 수 있는 양이 같은 속도로 늘지는 않습니다.

무엇을 고정하고, 무엇을 덧붙이고, 무엇을 밖으로 내보낼지 정하고, 그 결정을 조립 함수 하나에 담는 것이 설계의 전부입니다.

프롬프트를 고치기 전에, 모델이 실제로 받은 입력 전체를 먼저 읽어 보시기 바랍니다.
