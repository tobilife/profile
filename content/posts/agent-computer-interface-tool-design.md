:::note
- 모델은 도구의 이름, 설명, 파라미터, 응답만 보고 행동합니다. 이 네 가지가 에이전트의 사용자 인터페이스입니다.
- 설명은 언제 쓰고 언제 쓰지 말아야 하는지까지 적고, 파라미터는 실수가 불가능한 모양으로 바꿉니다.
- 에러는 실패 사실이 아니라 다음에 무엇을 해야 하는지를 돌려줘야 하고, 도구 응답은 컨텍스트 예산 안으로 줄여야 합니다.
- 쓰기 도구는 위험 등급을 매기고, 등급에 따라 사람 승인 같은 gate를 harness 쪽에 둡니다.
:::

에이전트에 도구를 붙이는 일을 "이미 있는 REST API를 function calling 스키마로 감싸는 작업" 정도로 여기는 경우가 많습니다.

Anthropic은 다르게 봅니다. 사람과 컴퓨터 사이 인터페이스(HCI)에 들이는 만큼의 노력을 에이전트와 컴퓨터 사이 인터페이스(ACI)에도 들이라고 권하고, SWE-bench용 에이전트를 만들 때는 전체 프롬프트보다 도구를 다듬는 데 시간을 더 썼다고 적었습니다. [\[Anthropic: Building effective agents\]](https://web.archive.org/web/20250305014737/https://www.anthropic.com/engineering/building-effective-agents)

ACI라는 용어를 제안한 SWE-agent 논문은 LM 에이전트를 고유한 필요와 능력을 가진 새로운 종류의 최종 사용자로 보자고 합니다. [\[Yang et al.: SWE-agent\]](https://arxiv.org/abs/2405.15793)

**도구는 시스템 간 연동 규격이 아니라 모델이라는 사용자가 보는 화면이고, 화면이 나쁘면 모델이 아무리 좋아도 잘못 누릅니다.**

이 글은 하나의 예시를 끝까지 끌고 갑니다. 보험 콜센터 상담원을 돕는 에이전트입니다. 상담원이 "이 고객 계약 상태랑 최근 납입 내역 좀 봐 줘"라고 말하면 에이전트가 사내 시스템을 조회하고, 필요하면 주소 변경 같은 간단한 처리를 요청합니다. 이 에이전트의 도구를 하나씩 고쳐 가며 원칙을 보겠습니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 사내 계약 조회 API를 그대로 도구로 노출했다고 해봅시다.

도구 이름은 `search`이고, 설명은 "계약을 검색합니다" 한 줄입니다. 파라미터는 `q`, `type`, `flag` 세 개입니다.

에이전트는 고객 이름으로 계약을 찾으려고 `type`에 `"name"`을 넣습니다. 실제로 허용되는 값은 `"CUST_NM"`이었습니다. 돌아온 응답은 `400 Bad Request`가 전부입니다.

에이전트는 `type`을 바꿔 가며 같은 호출을 반복합니다. 어쩌다 조건 없이 호출이 성공하자 이번에는 계약 3,000건이 통째로 돌아와 컨텍스트를 채웁니다.

상담원은 그동안 전화를 붙잡고 기다립니다.

이 대화에서 모델이 잘못한 것은 많지 않습니다. 시스템 설계 관점에서 잘못된 건 네 가지입니다.

- 이름과 설명이 이 도구를 언제 써야 하는지 알려 주지 않았습니다.
- `type`에 무엇을 넣을 수 있는지 스키마에 없었습니다.
- 에러가 무엇을 고쳐야 하는지 말해 주지 않았습니다.
- 응답 크기에 상한이 없었습니다.

여기에 하나를 더하면, 같은 에이전트에 주소 변경 도구가 아무 구분 없이 함께 들어 있었다는 점입니다. 조회 도구가 이렇게 다뤄진다면 쓰기 도구도 비슷하게 다뤄졌을 가능성이 큽니다.

## 1. 이름과 설명: 모델이 읽는 유일한 문서입니다

사람 개발자는 API 문서를 읽고, 동료에게 묻고, 시행착오를 기억합니다. 모델에게는 도구 정의에 적힌 글이 전부입니다.

### 모델은 도구 정의를 어떻게 읽는가

매 호출마다 harness는 도구 정의 목록을 요청에 함께 넣습니다. 모델은 시스템 지시와 대화 이력과 이 정의들을 한꺼번에 읽고, 도구를 부를지, 부른다면 어느 것을 어떤 인자로 부를지 정합니다.

이때 모델이 판단에 쓸 수 있는 정보는 이름, 설명, 입력 스키마가 전부입니다. MCP 명세의 스키마도 도구 설명을 클라이언트가 LLM의 도구 이해를 돕는 데 쓸 수 있는, 모델에게 주는 일종의 힌트로 설명합니다. [\[MCP: Schema (2025-06-18)\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-06-18/schema.ts)

그리고 이 정의들은 매 턴 다시 들어갑니다. 도구 정의는 한 번 등록하고 끝나는 설정이 아니라, 모든 호출의 입력 일부입니다.

### 설명에 들어가야 할 네 가지

Anthropic의 tool use 문서는 도구 성능에 가장 큰 영향을 주는 요인으로 상세한 설명을 꼽습니다. 도구가 무엇을 하는지, 언제 써야 하고 언제 쓰지 말아야 하는지, 각 파라미터의 의미, 그리고 도구가 무엇을 돌려주지 않는지 같은 주의할 제약을 적고, 도구 하나에 최소 서너 문장을 쓰라고 합니다. 예시보다 설명이 먼저라는 말도 있습니다. [\[Anthropic: How to implement tool use\]](https://web.archive.org/web/20250719162157/https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use)

Anthropic의 다른 글은 판단 기준을 하나 줍니다. 설명과 파라미터만 보고 사용법이 분명한지, 아니면 곰곰이 생각해야 하는지 모델의 입장에서 따져 보라는 것입니다. 좋은 도구 정의에는 사용 예, 경계 사례, 입력 형식 요건, 다른 도구와의 분명한 경계가 들어 있다고 하고, 팀의 주니어 개발자를 위해 좋은 docstring을 쓴다고 생각하라고도 합니다. [\[Anthropic: Building effective agents\]](https://web.archive.org/web/20250305014737/https://www.anthropic.com/engineering/building-effective-agents)

앞의 `search` 도구를 고쳐 쓰면 이렇게 됩니다. 아래는 제가 만든 예시입니다.

```json
{
  "name": "contract_search_by_customer",
  "description": "고객 식별 정보로 보험 계약 목록을 조회합니다. 고객이 가진 계약을 찾거나 계약번호를 모를 때 사용합니다. 계약번호를 이미 알고 있다면 이 도구 대신 contract_get_detail을 사용하세요. 해지된 계약은 기본적으로 제외되며, 결과는 최근 계약일 순으로 최대 20건만 반환합니다. 납입 내역과 보장 내용은 반환하지 않습니다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "search_by": {
        "type": "string",
        "enum": ["customer_name", "customer_id", "phone_number"],
        "description": "무엇으로 찾을지 고릅니다. 동명이인이 많으므로 가능하면 customer_id나 phone_number를 씁니다."
      },
      "value": {
        "type": "string",
        "description": "검색할 값. phone_number는 하이픈 없이 숫자만 입력합니다. 예: 01012345678"
      },
      "include_terminated": {
        "type": "boolean",
        "description": "해지 계약 포함 여부. 생략하면 false입니다."
      }
    },
    "required": ["search_by", "value"]
  }
}
```

설명 다섯 문장이 각각 하는 일이 다릅니다. 무엇을 하는지, 언제 쓰는지, 언제 쓰지 말아야 하는지, 기본 동작과 상한, 무엇을 돌려주지 않는지입니다.

마지막 문장이 생각보다 중요합니다. 이 문장이 없으면 모델은 납입 내역을 찾으려고 이 도구를 계속 다시 부를 수 있습니다.

### 도구 사이의 경계와 이름

도구가 여러 개일 때는 경계가 문제입니다.

OpenAI 가이드는 문제의 본질이 도구의 개수가 아니라 유사성과 겹침이라고 합니다. 잘 정의된 서로 다른 도구 15개 이상을 무리 없이 다루는 구현이 있는 반면, 겹치는 도구 10개 미만으로도 고전하는 구현이 있다는 것입니다. [\[OpenAI: A practical guide to building agents\]](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

이름도 설계 대상입니다. Manus는 브라우저 관련 도구는 모두 `browser_`로, 명령줄 도구는 `shell_`로 시작하도록 접두사를 일관되게 맞췄다고 밝혔습니다. 특정 상태에서 특정 그룹의 도구만 고르도록 제약하기 쉬워진다는 이유입니다. [\[Manus: Context Engineering for AI Agents\]](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

상담 지원 에이전트의 도구 목록을 이 원칙으로 정리하면 이렇게 됩니다. 이름과 경계는 제가 만든 예시입니다.

| 도구 이름 | 하는 일 | 쓰지 말아야 할 때 |
| --- | --- | --- |
| `contract_search_by_customer` | 고객으로 계약 목록 조회 | 계약번호를 이미 알 때 |
| `contract_get_detail` | 계약번호로 상태와 보장 조회 | 계약번호를 모를 때 |
| `payment_get_history` | 계약번호로 최근 납입 내역 조회 | 미납 안내 문자 발송이 목적일 때 |
| `request_address_change` | 주소 변경 요청서 생성 | 고객 본인 확인 전 |

접두사 `contract_`, `payment_`, `request_`만 봐도 읽기와 쓰기가 갈립니다. 쓰기 성격의 도구는 모두 `request_`로 시작하게 해 두면, 뒤에서 볼 승인 gate를 이름 규칙으로 걸 수도 있습니다.

### 같은 정의도 모델에 따라 다르게 읽힙니다

도구 정의를 평가할 때는 어떤 모델이 그 정의를 읽는지도 함께 봐야 합니다. Anthropic의 문서는 복잡한 도구와 모호한 질의에는 더 큰 모델을 쓰라고 권하면서, 그런 모델이 여러 도구를 더 잘 다루고 필요할 때 되묻는다고 설명합니다. 단순한 도구에는 Haiku 계열을 쓸 수 있지만, 이 경우 빠진 파라미터를 추측해서 채울 수 있다고 경고합니다. [\[Anthropic: How to implement tool use\]](https://web.archive.org/web/20250719162157/https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use)

상담 에이전트에서 "빠진 값을 추측해 채운다"는 것은 고객번호를 지어낼 수 있다는 뜻입니다. 그래서 작은 모델을 쓸수록 식별자 파라미터는 필수로 두고, harness가 형식과 존재 여부를 검증한 뒤에 실행하는 편이 안전하다고 봅니다.

### 실패 모드: 설명이 길어질수록 내는 비용

설명을 자세히 쓰라는 조언에는 비용이 따라옵니다. 도구 정의는 매 호출의 입력에 들어가므로, 도구 20개에 각각 다섯 문장을 쓰면 그만큼이 모든 턴에 붙습니다.

그래서 저는 설명을 길게 쓰는 것과 도구 수를 줄이는 것을 함께 하는 편을 권합니다. 이 상담 에이전트에 쓰지 않는 도구는 정의에서 빼고, 남은 도구의 설명을 충실히 쓰는 것입니다.

반대로 하지 말아야 할 것도 있습니다. 대화 도중에 도구 정의를 넣고 빼는 것입니다. Manus는 도구 정의가 보통 컨텍스트 앞쪽에 놓여서 바뀌면 그 뒤의 캐시가 무효가 되고, 이전 행동이 지금은 없는 도구를 가리키면 모델이 혼란스러워한다고 설명합니다. 대신 정의는 그대로 두고 상태에 따라 고를 수 있는 행동을 디코딩 단계에서 제한하는 방식을 씁니다.

## 2. 파라미터: 실수가 불가능한 모양으로 바꿉니다

Anthropic은 이 원칙을 poka-yoke라고 부릅니다. 인자를 바꿔서 실수하기 어렵게 만들라는 뜻입니다. [\[Anthropic: Building effective agents\]](https://web.archive.org/web/20250305014737/https://www.anthropic.com/engineering/building-effective-agents)

같은 글의 사례가 구체적입니다. 에이전트가 루트 디렉터리에서 벗어난 뒤 상대 경로를 쓰는 도구에서 실수하자, 도구가 항상 절대 경로를 요구하도록 바꿨고, 그 뒤로 모델은 이 방식을 문제없이 사용했다고 합니다.

모델에게 더 조심하라고 지시한 것이 아니라, 틀릴 수 있는 선택지를 없앴다는 점이 중요합니다.

### 형식 부담을 없앱니다

형식에 대한 조언도 같은 맥락입니다. 같은 글은 같은 동작도 여러 형식으로 표현할 수 있다고 짚습니다. 파일 편집은 diff로도, 파일 전체를 다시 쓰는 방식으로도 할 수 있고, 코드는 Markdown 안에도 JSON 안에도 담을 수 있습니다. 사람에게는 차이가 없어도, diff는 새 코드를 쓰기 전에 바뀔 줄 수를 알아야 하고 JSON 안의 코드는 줄바꿈과 따옴표를 이스케이프해야 해서 모델에게는 훨씬 어렵다는 것입니다.

그래서 모델이 궁지에 몰리기 전에 생각할 토큰을 충분히 주고, 인터넷의 글에서 자연스럽게 보던 형식에 가깝게 하고, 수천 줄의 줄 수를 정확히 세거나 코드를 문자열로 이스케이프하는 것 같은 형식 부담을 없애라고 권합니다.

상담 에이전트에서는 날짜와 금액이 이 문제의 대표입니다. "지난달 납입분"을 모델이 `2025-06-01`로 바꿔 넣게 하는 대신, `period: "last_3_months"` 같은 enum을 두면 계산 실수를 harness 쪽으로 옮길 수 있습니다.

### 자주 나오는 실수와 파라미터 설계

자주 나오는 실수와 그에 맞는 파라미터 설계를 표로 정리하면 이렇습니다. 오른쪽 열은 제 의견입니다.

| 모델이 하기 쉬운 실수 | 파라미터 쪽에서 막는 방법 |
| --- | --- |
| 허용되지 않는 값을 지어냄 | 자유 문자열 대신 `enum` |
| 단위나 형식을 헷갈림 | 이름에 단위를 넣음(`amount_krw`), 설명에 형식 예시 |
| 작업 위치에 따라 달라지는 값을 씀 | 상대 경로, 상대 날짜 대신 절대값이나 정해진 기간 enum |
| 선택 인자를 엉뚱하게 채움 | 선택 인자를 줄이고 기본값을 설명에 명시 |
| 비슷한 식별자를 섞어 씀 | `contract_no`, `customer_id`처럼 이름을 구체적으로 |
| 여러 호출을 순서대로 조합하다 중간에 틀림 | 자주 함께 쓰는 동작을 도구 하나로 통합 |

### 자주 함께 쓰는 동작은 합칩니다

마지막 행은 SWE-agent 논문의 원칙과 같습니다. 논문은 효과적인 ACI의 설계 원칙으로 네 가지를 듭니다. 행동은 단순하고 이해하기 쉬워야 하고, 중요한 동작은 가능한 한 적은 수의 행동으로 합쳐야 하고, 환경의 피드백은 유익하되 간결해야 하고, guardrail이 오류 전파를 막고 회복을 앞당긴다는 것입니다. [\[Yang et al.: SWE-agent\]](https://arxiv.org/abs/2405.15793)

두 번째 원칙의 근거도 숫자로 있습니다. 논문의 ablation에서 전용 편집 명령을 없애고 셸의 기존 방법으로만 편집하게 한 구성은 SWE-bench Lite 해결률이 10.3%로, 전체 구성의 18.0%보다 7.7%p 낮았습니다.

상담 에이전트에서 "계약 목록 조회, 계약별 상세 조회, 계약별 납입 내역 조회"를 매번 세 단계로 조합한다면, `customer_get_summary` 하나로 합쳐 계약별 상태와 최근 납입 3회를 함께 돌려주는 도구를 검토할 만합니다. 상담원이 가장 자주 묻는 질문이 그 조합이라면 더욱 그렇습니다.

### 실패 모드: guardrail이 정당한 작업을 막을 때

파라미터를 좁히는 데에도 대가가 있습니다. SWE-agent 논문은 문법 오류가 생기는 편집을 막는 guardrail이 어떤 편집을 특정 순서로 하도록 강제하는 단점이 있다고 스스로 적습니다. 함수 인자 하나를 지우려면 그 인자를 쓰는 곳을 먼저 지우거나 한 번에 함께 지워야 한다는 식입니다.

그래서 guardrail을 넣을지는, 그것이 줄여 주는 흔한 실수와 그것이 방해하는 모델의 선호 작업 방식을 비교해 정하라고 합니다.

상담 에이전트에서 `period`를 enum으로만 받게 하면, "2023년 3월 납입분 확인" 같은 드문 요청은 처리할 수 없게 됩니다. 이럴 때는 enum에 `custom`을 두고 그때만 절대 날짜 두 개를 받게 하는 식으로, 흔한 경로는 좁히고 드문 경로는 열어 둡니다.

## 3. 에러 메시지: 다음 행동을 알려 주는 관측값입니다

사람용 API에서 에러는 로그에 남기고 개발자가 나중에 읽는 것입니다. 에이전트용 도구에서 에러는 바로 다음 스텝의 입력입니다.

### 에러는 두 층으로 나뉩니다

MCP 명세는 에러를 두 층으로 나눕니다. 알 수 없는 도구나 잘못된 인자 같은 프로토콜 에러는 JSON-RPC 에러로, API 실패나 잘못된 입력 데이터, 업무 로직 오류 같은 도구 실행 에러는 결과 안에 `isError: true`로 보고합니다. [\[MCP: Tools (2025-06-18)\]](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

Anthropic API도 같은 구조입니다. 도구가 실행 중에 실패하면 에러 메시지를 내용에 담고 `is_error`를 true로 돌려주라고 안내합니다. 필수 파라미터가 빠진 호출에 대해서도 에러를 알리는 결과를 돌려주면 모델이 빠진 정보를 채워 다시 시도한다고 설명하고, 잘못된 요청에 대해 모델은 수정하며 두세 번 재시도한 뒤 사용자에게 사과한다고 적습니다. [\[Anthropic: How to implement tool use\]](https://web.archive.org/web/20250719162157/https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use)

같은 문서는 개발 단계에서 이런 호출 오류가 보이면 도구 정의의 설명을 더 자세히 써서 다시 시도해 보는 것이 최선이라고도 합니다. 잘못된 호출은 모델의 실수이기 전에 설명이 부족하다는 신호라는 뜻으로 읽습니다.

즉 실행 에러는 숨기거나 예외로 던져 루프를 끊을 것이 아니라, 모델이 읽을 수 있는 글로 돌려줘야 합니다.

### 좋은 에러 메시지의 구성

그 글에 무엇을 담느냐가 설계입니다. 아래는 예시입니다.

```json
{
  "isError": true,
  "content": [
    {
      "type": "text",
      "text": "search_by 값 'name'은 허용되지 않습니다. 허용 값: customer_name, customer_id, phone_number. 고객 이름으로 찾으려면 search_by를 customer_name으로 바꿔 다시 호출하세요."
    }
  ]
}
```

무엇이 틀렸는지, 허용되는 것이 무엇인지, 다음에 어떻게 호출하면 되는지가 들어 있습니다.

업무 로직 오류도 같은 원칙을 따릅니다. 상담 에이전트에서 자주 나올 만한 경우를 정리하면 이렇습니다. 문구는 제가 만든 예시입니다.

| 상황 | 나쁜 에러 | 다음 행동을 알려 주는 에러 |
| --- | --- | --- |
| 동명이인이 많음 | `TOO_MANY_RESULTS` | "같은 이름의 고객이 43명입니다. phone_number나 customer_id로 다시 찾으세요." |
| 해지 계약만 있음 | `[]` | "유효 계약이 없습니다. 해지 계약 2건이 있으며 include_terminated=true로 볼 수 있습니다." |
| 본인 확인 전 쓰기 | `403` | "본인 확인이 완료되지 않았습니다. 상담원에게 본인 확인을 요청하고 결과를 기다리세요." |
| 기간계 점검 시간 | `503` | "계약 시스템 점검 중입니다(02:00~04:00). 재시도하지 말고 상담원에게 점검 중임을 알리세요." |

마지막 행처럼 "재시도하지 말라"는 지시도 에러의 중요한 내용입니다. 이것이 없으면 모델은 같은 호출을 반복합니다.

### Guardrail이 붙은 에러의 효과

SWE-agent는 이 원칙의 효과를 숫자로 보여 줍니다. 편집 명령에 linter를 붙여, 문법 오류가 생기는 편집은 반영하지 않고 오류 내용과 함께 다시 시도하게 했습니다. 이 장치를 뺀 구성은 SWE-bench Lite 해결률이 15.0%로 3.0%p 낮았습니다. [\[Yang et al.: SWE-agent\]](https://arxiv.org/abs/2405.15793)

출력이 없는 경우도 같은 논문에 나옵니다. 명령이 아무것도 출력하지 않으면 빈 문자열 대신 명령이 성공했고 출력이 없었다는 문장을 돌려줍니다. 빈 응답은 모델에게 성공인지 실패인지 알 수 없는 신호이기 때문입니다.

형식이 잘못된 모델 출력을 다루는 방식도 참고할 만합니다. 논문의 harness는 형식이 틀린 생성에 에러 응답을 보내 다시 쓰게 하고, 올바른 생성을 받으면 첫 번째를 제외한 과거 에러 메시지를 지운다고 설명합니다. 에러는 회복에 쓰고, 회복한 뒤에는 컨텍스트에서 치우는 것입니다.

### 실패 모드: 에러가 너무 많이 말할 때

에러를 자세히 쓰라는 원칙에도 한계가 있다고 봅니다. 에러 메시지는 모델의 컨텍스트에 들어가고, 모델의 답변을 거쳐 사용자 화면에 나갈 수 있습니다.

그래서 SQL 문, 내부 테이블 이름, 스택 트레이스, 다른 고객의 정보처럼 다음 행동에 필요 없는 내용은 빼야 합니다. MCP 명세도 서버가 도구 출력을 정제해야 하고, 클라이언트는 도구 결과를 LLM에 넘기기 전에 검증해야 한다고 적습니다. 원본 예외는 harness의 로그에 남기고, 모델에게는 고칠 대상과 다음 행동만 줍니다.

## 4. 응답 크기: 도구 결과는 컨텍스트 예산을 씁니다

도구가 돌려준 내용은 전부 다음 호출의 입력 토큰이 됩니다. 그리고 다음 호출에도, 그다음 호출에도 남습니다.

### 얼마나 보여 줄지는 성능 변수입니다

SWE-agent의 검색 명령은 결과를 최대 50건까지만 돌려줍니다. 그보다 많으면 결과를 보여 주지 않고, 더 구체적인 질의를 쓰라고 안내합니다. 파일 뷰어는 한 번에 최대 100줄만 보여 주고 위아래로 이동하는 명령을 줍니다. [\[Yang et al.: SWE-agent\]](https://arxiv.org/abs/2405.15793)

논문의 ablation은 이 숫자가 임의의 값이 아니라는 것을 보여 줍니다.

| 조정한 것 | 구성 | SWE-bench Lite 해결률 |
| --- | --- | --- |
| 파일 뷰어 창 크기 | 30줄 | 14.3% |
| 파일 뷰어 창 크기 | 100줄 (기본) | 18.0% |
| 파일 뷰어 창 크기 | 파일 전체 | 12.7% |
| 검색 인터페이스 | 요약된 결과 (기본) | 18.0% |
| 검색 인터페이스 | 결과를 하나씩 넘겨 보는 방식 | 12.0% |
| 검색 인터페이스 | 전용 검색 없음 | 15.7% |
| 이력 관리 | 최근 관측 5개만 온전히 유지 (기본) | 18.0% |
| 이력 관리 | 전체 이력 유지 | 15.0% |

너무 적게 보여 줘도, 너무 많이 보여 줘도 나빠집니다. 결과를 하나씩 넘겨 보게 한 검색은 에이전트가 모든 결과를 끝까지 넘겨 보다 비용 예산이나 컨텍스트를 소진해, 검색 도구가 아예 없는 것보다 나빴다고 합니다.

논문은 그 이유를 이렇게 설명합니다. 사람은 불필요한 정보를 유연하게 무시하지만, LM에게는 모든 내용이 메모리와 계산에서 고정 비용이고, 주의를 흩뜨리는 컨텍스트는 성능을 해칠 수 있습니다.

### 지난 관측은 harness가 접습니다

응답 크기는 도구가 돌려줄 때 한 번, harness가 이력을 다시 조립할 때 또 한 번 조절할 수 있습니다.

SWE-agent의 harness는 최근 5개를 제외한 이전 관측을 각각 한 줄로 접어 넣습니다. 계획과 행동의 이력은 남기고 지난 관측의 내용은 대부분 지워서, 같은 컨텍스트로 더 많은 상호작용을 할 수 있게 한다는 설명입니다. 앞 표에서 전체 이력을 유지한 구성이 3.0%p 낮았던 것이 이 장치의 효과입니다. [\[Yang et al.: SWE-agent\]](https://arxiv.org/abs/2405.15793)

상담 에이전트로 옮기면, 통화 초반에 조회한 계약 목록 전체는 이후 턴에서 "계약 3건 조회함, 유효 2건" 같은 한 줄로 바꿔 넣는 방식입니다. 원본은 harness의 로그에 남아 있으니, 필요하면 다시 조회할 수 있습니다.

### 큰 결과는 참조와 구조로 돌려줍니다

큰 결과를 다루는 방법으로는 내용 대신 참조를 돌려주는 방식이 있습니다.

MCP 명세에는 도구가 리소스 링크를 반환하는 형태가 정의되어 있습니다. 도구는 URI를 돌려주고, 클라이언트가 필요할 때 가져옵니다. 구조화된 결과를 위한 `structuredContent`와 `outputSchema`도 같은 버전에 들어 있습니다. 구조화된 결과를 돌려주는 도구는 하위 호환을 위해 직렬화한 JSON을 텍스트 블록으로도 함께 돌려주라고 권합니다. [\[MCP: Tools (2025-06-18)\]](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

Manus도 같은 방향입니다. 웹 페이지 내용은 URL이 남아 있는 한 컨텍스트에서 빼도 되고, 문서 내용은 경로가 남아 있으면 생략해도 된다는 식으로 복원 가능한 축약을 씁니다. [\[Manus: Context Engineering for AI Agents\]](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

상담 에이전트의 납입 내역 도구에 이 원칙을 적용하면 응답은 이런 모양이 됩니다. 아래는 예시입니다.

```json
{
  "content": [
    {
      "type": "text",
      "text": "계약 202401230001 최근 3개월 납입: 3회 중 2회 정상, 2025-06 미납. 전체 24회 이력은 resource 링크로 볼 수 있습니다."
    },
    {
      "type": "resource_link",
      "uri": "claims-internal://payments/202401230001?months=24",
      "name": "payment_history_24m",
      "mimeType": "application/json"
    }
  ],
  "structuredContent": {
    "contract_no": "202401230001",
    "period": "last_3_months",
    "paid_count": 2,
    "unpaid_months": ["2025-06"],
    "has_more": true
  }
}
```

모델은 요약 한 문장과 구조화된 필드로 다음 판단을 하고, 전체 이력은 정말 필요할 때만 따로 가져옵니다.

### 실패 모드: 너무 적게 돌려줄 때

상한에도 비용이 있습니다. SWE-agent 논문은 검색 결과를 50건 이하로 제한하는 guardrail의 단점으로, 결과가 많을 때 에러를 돌려주면 모델이 새 검색어를 만들어 다시 호출해야 하고 그것이 비싼 연산일 수 있다는 점을 듭니다. 관측을 간결하게 유지하는 것과 모델 호출을 더 하는 것 사이의 거래라는 것입니다.

그래서 저는 상한을 넘었을 때 아무것도 돌려주지 않기보다, 앞의 예처럼 건수와 좁히는 방법, 그리고 가장 그럴듯한 몇 건을 함께 돌려주는 편을 권합니다. 어느 쪽이 나은지는 실제 질의로 재 봐야 합니다.

## 5. 위험 등급: 쓰기 도구는 다르게 다룹니다

조회 도구가 잘못 불리면 시간과 토큰을 잃습니다. 쓰기 도구가 잘못 불리면 고객의 주소가 바뀝니다. 같은 인터페이스 원칙 위에 한 겹을 더 얹어야 합니다.

### 위험은 도구 단위로 매깁니다

OpenAI 가이드는 도구마다 읽기 전용인지 쓰기인지, 되돌릴 수 있는지, 필요한 계정 권한, 금전적 영향을 기준으로 낮음, 중간, 높음의 위험 등급을 매기고, 이 등급에 따라 고위험 도구는 실행 전에 guardrail 점검을 거치거나 사람에게 넘기라고 합니다. [\[OpenAI: A practical guide to building agents\]](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

MCP는 이런 성격을 도구 정의에 적을 자리를 마련해 두었습니다. 2025-06-18 스키마의 도구 annotation에는 환경을 바꾸지 않는지(`readOnlyHint`), 파괴적인 변경을 할 수 있는지(`destructiveHint`), 같은 인자로 반복 호출해도 추가 효과가 없는지(`idempotentHint`), 외부의 열린 세계와 상호작용하는지(`openWorldHint`)를 나타내는 힌트가 있습니다. [\[MCP: Schema (2025-06-18)\]](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-06-18/schema.ts)

다만 명세는 신뢰하는 서버에서 온 것이 아니라면 클라이언트가 이 annotation을 신뢰하지 말아야 한다고 못 박습니다. 힌트는 분류를 돕는 정보이지, 통제 장치가 아닙니다. [\[MCP: Tools (2025-06-18)\]](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

상담 에이전트의 도구에 등급을 매기면 이렇게 됩니다. 등급과 처리는 제가 만든 예시입니다.

| 도구 | 읽기/쓰기 | 되돌리기 | 개인정보 | 등급 | harness 처리 |
| --- | --- | --- | --- | --- | --- |
| `contract_search_by_customer` | 읽기 | 해당 없음 | 포함 | 중간 | 조회 사유와 함께 감사 로그 |
| `contract_get_detail` | 읽기 | 해당 없음 | 포함 | 중간 | 감사 로그 |
| `payment_get_history` | 읽기 | 해당 없음 | 포함 | 중간 | 감사 로그 |
| `request_address_change` | 쓰기 | 어려움 | 포함 | 높음 | 상담원 확인 화면을 거친 뒤에만 실행 |

### 승인은 모델이 아니라 harness가 겁니다

MCP 명세는 신뢰와 안전을 위해 도구 호출을 거부할 수 있는 사람이 항상 루프 안에 있어야 한다고 권고합니다. 어떤 도구가 모델에 노출되는지 보여 주고, 호출될 때 분명히 표시하고, 작업에 대해 확인을 받으라는 것입니다. 클라이언트 쪽 권고로는 민감한 작업에 대한 사용자 확인, 서버 호출 전에 입력을 사용자에게 보여 주기, 도구 결과 검증, 호출 시간 제한, 감사용 사용 기록이 나열되어 있습니다. [\[MCP: Tools (2025-06-18)\]](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

상담 에이전트에서 이 권고를 흐름으로 옮기면 이렇습니다.

```text
모델: request_address_change(contract_no, new_address) 호출 요청
   |
   v
harness: 도구 등급표 조회 -> "높음"
   |
   v
상담원 화면에 확인 카드 표시: 계약번호, 변경 전 주소, 변경 후 주소
   |                         |
   | 상담원 승인              | 상담원 거절 또는 수정
   v                         v
실행 -> 결과를 모델에 전달    거절 사유를 도구 결과로 모델에 전달
   |
   v
감사 로그: 요청 시각, 승인자, 입력값, 결과
```

모델은 "주소를 바꿔 달라"는 요청을 만들 수 있을 뿐이고, 실행 여부는 상담원과 harness가 정합니다. 프롬프트에 "주소 변경 전에는 반드시 확인하라"고 쓰는 것과 구조적으로 다른 점입니다.

### 도구도 사용성 테스트를 거칩니다

화면을 출시하기 전에 사용성 테스트를 하듯, 도구도 실제 사용자인 모델에게 써 보게 하고 관찰해야 합니다.

SWE-agent 팀은 인터페이스를 다듬을 때 두 가지 방법을 썼다고 밝힙니다. 에이전트의 행동을 직접 들여다보며 어려움을 찾아 개선안을 내는 것과, ACI 설정을 grid search로 비교해 가장 나은 구성을 고르는 것입니다. [\[Yang et al.: SWE-agent\]](https://arxiv.org/abs/2405.15793) Anthropic도 많은 예시 입력으로 모델이 도구를 어떻게 쓰는지 돌려 보고 어떤 실수를 하는지 보며 반복하라고 권합니다. [\[Anthropic: Building effective agents\]](https://web.archive.org/web/20250305014737/https://www.anthropic.com/engineering/building-effective-agents)

상담 에이전트라면 상담 녹취에서 자주 나오는 요청 30개 정도를 뽑아 돌리고, 아래 항목을 도구별로 세어 보는 것으로 시작할 수 있습니다. 항목은 제가 정한 예시입니다.

- 잘못된 도구를 고른 횟수와 그때 대신 골랐어야 할 도구
- 스키마 검증에 걸린 호출 수와 걸린 파라미터
- 같은 도구를 같은 인자로 다시 부른 횟수
- 에러를 받은 뒤 다음 호출에서 회복한 비율
- 도구 결과가 차지한 토큰의 평균과 최대값

숫자가 나쁜 도구부터 설명, 파라미터, 에러, 응답 크기 순으로 고칩니다. 대부분은 프롬프트가 아니라 이 네 곳에서 원인이 보입니다.

### 보수적인 엔터프라이즈 IT에서는

레거시 시스템의 프로시저나 전문 인터페이스를 도구로 감쌀 때, 기존 규격을 그대로 노출하고 싶은 유혹이 큽니다.

저는 그 사이에 에이전트용 얇은 계층을 따로 두는 편이 안전하다고 봅니다. 약어로 된 컬럼명과 코드값을 풀어 쓰고, 조회 건수에 상한을 두고, 읽기 도구와 쓰기 도구를 이름부터 분리하고, 에러 코드를 다음 행동을 알려 주는 문장으로 바꾸는 계층입니다. 기존 Java 서비스나 Oracle 프로시저는 그대로 두고, 이 계층만 에이전트를 위한 화면으로 설계하는 것입니다.

결재선이 있는 조직이라면 앞의 등급표가 곧 승인 정책의 초안이 됩니다. 어떤 도구가 누구의 확인을 거쳐야 하는지가 표 한 장에 드러나고, 그 표를 harness의 설정으로 그대로 옮길 수 있기 때문입니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 지금 쓰는 도구 정의를 꺼내, 설명만 읽고 언제 쓰고 언제 쓰지 말아야 하는지, 무엇을 돌려주지 않는지 답할 수 있는지 확인합니다. 답할 수 없으면 서너 문장 이상으로 다시 씁니다.
2. 자유 문자열 파라미터를 찾아 `enum`, 형식 예시, 절대값 요구 중 하나로 좁히고, 드문 경로를 위한 출구를 하나 남깁니다.
3. 에러 응답을 하나씩 일부러 일으켜 보고, 각 메시지에 고칠 대상, 허용 값, 다음 호출 방법, 재시도 여부가 들어 있는지 봅니다. 내부 정보가 새는지도 함께 봅니다.
4. 응답 크기의 상한을 정합니다. 넘으면 잘라 내지 말고 건수와 좁히는 방법, 또는 참조를 돌려줍니다.
5. 도구마다 위험 등급을 매기고, 높은 등급 도구 앞에 harness 쪽 승인 gate를 둡니다. 그다음 실제 입력 여러 개로 돌려 보고 모델이 어디서 틀리는지 기록합니다. Anthropic은 도구를 수십 번 써 보고 설명을 고쳐 쓰는 테스트 에이전트를 만들었고, 고친 설명을 쓴 에이전트의 작업 완료 시간이 40% 줄었다고 밝혔습니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/built-multi-agent-research-system)

## 마치며

에이전트가 도구를 잘못 쓸 때 프롬프트에 주의 문구를 더하는 것은 가장 쉬운 대응입니다.

하지만 대부분의 경우 고쳐야 할 곳은 도구 쪽입니다.

이름과 설명이 선택을 돕고, 파라미터가 실수를 막고, 에러가 다음 행동을 알려 주고, 응답이 예산 안에 들어오고, 위험한 도구 앞에 gate가 있으면 모델은 같은 지능으로 훨씬 덜 헤맵니다.

도구 정의는 한 번 쓰고 끝나는 연동 규격이 아니라, 사용자를 관찰하며 계속 고치는 인터페이스로 다루시기 바랍니다.
