:::note
- 서브에이전트의 핵심 가치는 역할 분담이 아니라 컨텍스트 격리입니다. 탐색의 잡음은 서브에이전트 안에 남고 메인에는 요약만 올라옵니다.
- 격리의 대가는 정보 손실입니다. 브리프에 적지 않은 제약은 서브에이전트에게 없는 것이고, 요약에서 빠진 근거는 메인에게 없는 것입니다.
- 브리프에는 목표, 이미 정해진 것, 범위, 도구, 반환 형식, 완료 기준을 적고, 결과는 근거 위치와 확인하지 못한 것까지 정해진 형식으로 돌려받는 편이 안전합니다.
- 읽기는 나누고 쓰기는 모읍니다. 맥락을 공유해야 하는 작업, 서로 의존하는 수정 작업에는 쓰지 않는 쪽이 낫습니다.
:::

"에이전트 하나로 부족하면 여러 개를 띄우면 된다"는 말을 자주 듣습니다. 리서치 담당, 구현 담당, 리뷰 담당을 두면 사람 팀처럼 일이 나뉠 것이라는 기대입니다.

하네스 입장에서 서브에이전트가 실제로 하는 일은 조직도를 그리는 것이 아닙니다. **서브에이전트는 일을 나누는 장치이기 전에 컨텍스트를 나누는 장치이고, 나눈 경계를 넘을 때마다 정보가 줄어듭니다.**

Anthropic은 2025년 9월 29일 Claude Agent SDK를 소개하면서 서브에이전트가 유용한 이유를 두 가지로 들었습니다. 여러 작업을 동시에 돌릴 수 있다는 것, 그리고 각자 격리된 컨텍스트 윈도우를 쓰면서 전체 컨텍스트가 아니라 관련 있는 정보만 오케스트레이터에게 돌려준다는 것입니다. [\[Anthropic: Building agents with the Claude Agent SDK\]](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

같은 날 나온 컨텍스트 엔지니어링 글은 여기에 숫자를 붙입니다. 서브에이전트 하나가 수만 토큰 이상을 쓰며 탐색하더라도, 돌려주는 것은 보통 1,000~2,000 토큰으로 압축한 요약이라는 것입니다. [\[Anthropic: Effective context engineering for AI agents\]](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

수만 토큰이 1,000~2,000 토큰이 된다는 것은 장점이면서 이 글의 주제이기도 합니다. 무엇이 남고 무엇이 버려지는지를 설계하지 않으면, 버려지는 쪽에 중요한 것이 섞입니다. 컨텍스트 엔지니어링의 일반론이나 멀티 에이전트 구성의 찬반은 다른 글에서 다뤘으므로, 여기서는 경계 하나를 넘을 때 하네스가 무엇을 해야 하는지에 집중합니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 사용자가 코딩 에이전트와 한 시간째 보험금 정산 배치의 성능 문제를 보고 있다고 해봅시다. 대화 초반에 두 가지가 정해졌습니다. 운영 DB 스키마는 건드릴 수 없다는 것, 그리고 인덱스 추가안은 이미 DBA가 반려했다는 것입니다.

메인 에이전트는 컨텍스트를 아끼려고 서브에이전트를 띄우며 이렇게 지시합니다.

```text
정산 배치가 느린 원인을 조사하고 개선안을 제안해 줘.
```

서브에이전트는 파일 수십 개를 읽고 깔끔한 보고를 돌려줍니다.

```text
원인은 CONTRACT_HIST 테이블 풀 스캔입니다.
인덱스 추가와 테이블 파티셔닝을 권장합니다.
```

메인 에이전트는 이 보고를 그대로 사용자에게 전합니다. 한 시간 전에 기각된 안이 자신 있는 문장으로 되돌아온 것입니다.

모델이 틀린 것이 아닙니다. 서브에이전트는 받은 지시 안에서 합리적으로 일했습니다. 문제는 설계에 있습니다.

- 메인 컨텍스트에만 있던 제약 두 가지가 경계를 넘지 못했습니다.
- 반환 형식이 정해져 있지 않아, 어떤 파일을 보고 그 결론을 냈는지가 요약에서 빠졌습니다.
- 메인은 서브에이전트가 무엇을 확인하지 않았는지 알 방법이 없었고, 받은 결론을 검증하지도 않았습니다.

이 정산 배치 조사를 끝까지 들고 가면서, 각 문제를 하네스의 어느 지점에서 막을 수 있는지 보겠습니다.

## 1. 서브에이전트가 주는 것에는 전부 대가가 붙어 있다

### 경계에서 실제로 오가는 것

서브에이전트 호출을 하네스 수준에서 풀어 보면 단순합니다. 메인 에이전트에게 서브에이전트는 도구 하나입니다. 도구 호출의 인자로 지시문이 들어가고, 도구 결과로 서브에이전트의 마지막 응답이 돌아옵니다. 그 사이에 서브에이전트가 읽은 파일, 실행한 검색, 버린 가설은 서브에이전트의 컨텍스트 안에서만 살다가 사라집니다.

```text
메인 컨텍스트                          서브에이전트 컨텍스트 (새로 시작)
┌──────────────────────┐              ┌───────────────────────────────┐
│ 사용자와 1시간 대화     │              │ 서브에이전트 system prompt      │
│ - 스키마 변경 불가      │   지시문     │ 지시문 (브리프)                 │
│ - 인덱스안 반려         │ ──────────> │ Read, Grep 결과 수십 건          │
│ ...                   │              │ 가설 1, 2, 3 ... 기각된 가설      │
│                       │   최종 응답   │ 최종 응답                        │
│ 도구 결과: 최종 응답     │ <────────── │                                 │
└──────────────────────┘              └───────────────────────────────┘
        남는 것: 지시문과 최종 응답             사라지는 것: 나머지 전부
```

그러니 경계를 넘는 정보는 정확히 두 덩어리, 내려가는 지시문과 올라오는 최종 응답뿐입니다. 이 글에서 설계 대상이라고 부르는 것이 이 두 덩어리입니다.

### 얻는 것과 대가

서브에이전트에서 얻는 것을 네 가지로 나눠 보면, 각각에 대가가 짝지어져 있습니다.

| 얻는 것 | 의미 | 대가 |
| --- | --- | --- |
| 깨끗한 컨텍스트 | 메인 대화의 잡음 없이 한 가지 일만 봅니다 | 메인이 알던 맥락도 같이 사라집니다 |
| 병렬성 | 서로 독립인 조사를 동시에 돌립니다 | 토큰 사용량이 늘고 결과가 겹치거나 어긋날 수 있습니다 |
| 압축된 결과 | 탐색 과정은 버리고 결론만 메인에 올라옵니다 | 근거와 불확실성이 요약에서 빠지기 쉽습니다 |
| 도구 제한 | 서브에이전트마다 쓸 수 있는 도구를 좁힙니다 | 필요한 도구가 없으면 일을 끝내지 못합니다 |

제품 문서도 같은 축으로 설명합니다. Claude Code 문서는 서브에이전트가 메인 대화와 분리된 자체 컨텍스트 윈도우를 쓰고, 그래서 메인 대화가 오염되지 않고 상위 목표에 집중할 수 있다고 적습니다. 서브에이전트별로 허용 도구를 지정할 수 있다는 점도 함께 듭니다. [\[Claude Code Docs: Subagents, 2025-10-07 스냅샷\]](https://web.archive.org/web/20251007103749/https://docs.claude.com/en/docs/claude-code/sub-agents)

### 잘 맞는 일의 조건

Anthropic의 표현으로는, 서브에이전트가 잘 맞는 일은 많은 양의 정보를 뒤져야 하는데 그 대부분이 쓸모없는 작업입니다. 예로 든 이메일 에이전트는 검색 서브에이전트 여러 개를 병렬로 띄워 각자 다른 질의를 돌리고, 전체 스레드가 아니라 관련 발췌만 돌려받습니다. [\[Anthropic: Building agents with the Claude Agent SDK\]](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

정산 배치 조사는 이 조건에 잘 맞습니다. 배치 설정, SQL 매퍼, 청크 처리 코드, 공통 DAO를 다 읽어야 하지만, 결론에 필요한 것은 그중 몇 줄입니다. 반대로 사용자와 개선안을 놓고 논의하는 일은 맞지 않습니다. 한 시간 동안 쌓인 합의가 전부 필요한 일이기 때문입니다.

제가 중요하다고 보는 건 질문의 순서입니다. "리뷰어", "아키텍트" 같은 역할 이름부터 정하면 사람 조직을 흉내 내게 됩니다. "어떤 탐색이 메인 컨텍스트를 더럽히는가"부터 물으면 서브에이전트가 필요한 자리가 훨씬 적게, 그리고 분명하게 나옵니다.

### 비용: 토큰, 지연, 대기

비용은 세 가지로 나타납니다.

첫째는 토큰입니다. Anthropic의 리서치 시스템 글은 자사 데이터에서 에이전트가 채팅보다 약 4배, 멀티 에이전트 시스템이 약 15배의 토큰을 썼다고 밝혔습니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/multi-agent-research-system)

둘째는 지연입니다. Claude Code 문서는 성능 고려 사항에 서브에이전트가 호출될 때마다 백지에서 시작하고, 일에 필요한 컨텍스트를 모으느라 지연이 생길 수 있다고 적습니다.

셋째는 대기입니다. 같은 리서치 글은 리드 에이전트가 서브에이전트들을 동기적으로 실행해 한 묶음이 끝날 때까지 기다리고, 그것이 병목이 된다고 적었습니다. 가장 느린 서브에이전트 하나가 전체 속도를 정합니다.

## 2. 경계를 넘을 때 잃는 것: 적지 않은 맥락은 없는 맥락이다

### 내려갈 때 잃는 것

백지에서 시작한다는 것은 메인 대화에서 합의된 제약, 이미 시도한 것, 사용자의 선호가 전부 없다는 뜻입니다. 서브에이전트가 아는 것은 브리프에 적힌 것, 자기 정의 파일의 system prompt, 그리고 스스로 찾아낼 수 있는 것뿐입니다. [\[Claude Code Docs: Subagents, 2025-10-07 스냅샷\]](https://web.archive.org/web/20251007103749/https://docs.claude.com/en/docs/claude-code/sub-agents)

정산 배치 사례에서 "스키마 변경 불가"는 코드 어디에도 적혀 있지 않습니다. DBA의 반려도 마찬가지입니다. 회의에서 정해진 것, 사람에게 들은 것, 한 시간 전 대화에서 기각된 것은 서브에이전트가 파일을 아무리 잘 읽어도 찾을 수 없는 종류의 정보입니다.

### 올라올 때 잃는 것

요약은 손실 압축입니다. 결론은 남고, 그 결론이 얼마나 단단한지는 빠집니다. "풀 스캔이 원인"이라는 문장만으로는 실행 계획을 확인한 것인지, SQL 모양을 보고 추정한 것인지 알 수 없습니다.

Anthropic은 멀티 에이전트 리서치 시스템 글에서 이 문제를 전화 게임에 비유하고, 한 가지 완화책을 소개했습니다. 서브에이전트가 결과물을 외부 저장소에 직접 쓰고, 조정자에게는 가벼운 참조만 넘기는 방식입니다. 그러면 결과가 리드 에이전트의 재서술을 거치지 않아 충실도와 성능이 함께 좋아진다는 설명입니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/multi-agent-research-system)

정산 배치에 적용하면, 서브에이전트가 근거가 된 SQL과 실행 계획 해석을 `investigation/settlement-01.md` 같은 파일에 남기고 메인에는 결론과 파일 경로만 돌려주는 식입니다. 메인은 필요할 때만 그 파일을 엽니다.

### 무엇을 남길지는 미리 정해야 한다

1,000~2,000 토큰이라는 예산 안에 무엇을 넣을지는 서브에이전트가 그때그때 정하게 두면 안 된다고 봅니다. 모델은 대개 결론과 그 결론을 꾸미는 설명을 남기고, 부정적인 결과와 불확실성을 먼저 버립니다. 메인에게 가장 비싼 정보가 먼저 버려지는 셈입니다.

제가 쓰는 기준을 표로 적으면 이렇습니다.

| 반드시 올린다 | 파일로 남기고 경로만 올린다 | 버려도 된다 |
| --- | --- | --- |
| 결론과 가능성의 순위 | 근거가 된 코드와 SQL 원문 | 읽었지만 무관했던 파일 목록 |
| 근거 위치 (경로와 줄) | 기각한 가설과 기각 이유 | 중간 추론 과정의 서술 |
| 확인하지 못한 것 | 측정값, 로그 발췌 | 도구 호출 순서 |
| 브리프의 제약과 충돌한 지점 | | |

기각한 가설을 파일로 남기는 이유는 다음 위임 때문입니다. 같은 조사를 다시 맡길 때 그 파일을 브리프에 붙이면, 새 서브에이전트가 같은 막다른 길을 다시 가지 않습니다.

### 넘기는 방식에 따라 잃는 것이 다르다

위임에는 성격이 다른 두 가지 방식이 있습니다. OpenAI Agents SDK 문서가 이 구분을 분명하게 보여 줍니다.

Handoff는 다른 에이전트가 대화를 넘겨받는 방식입니다. 문서에 따르면 넘겨받은 에이전트는 마치 대화를 이어받은 것처럼 이전 대화 이력 전체를 보고, 이를 바꾸려면 입력 필터를 지정합니다. 이전 이력에서 도구 호출을 모두 지우는 필터 같은 것이 기본 제공됩니다. [\[OpenAI Agents SDK: Handoffs, 2025-09-28 커밋\]](https://github.com/openai/openai-agents-python/blob/14d7d591e2b960f58cbd601e2b26f3993301618b/docs/handoffs.md)

다른 하나는 에이전트를 도구로 쓰는 방식입니다. 중앙 에이전트가 제어권을 넘기지 않고 전문 에이전트들을 조율합니다. 도구가 된 에이전트의 출력을 중앙 에이전트에 돌려주기 전에 가공하는 출력 추출 함수도 지정할 수 있습니다. [\[OpenAI Agents SDK: Tools, 2025-09-28 커밋\]](https://github.com/openai/openai-agents-python/blob/14d7d591e2b960f58cbd601e2b26f3993301618b/docs/tools.md)

두 방식의 차이를 제 나름대로 정리하면 다음과 같습니다.

| 구분 | 제어권 | 기본으로 넘어가는 맥락 | 주된 위험 | 하네스가 손댈 곳 |
| --- | --- | --- | --- | --- |
| Handoff | 받는 쪽으로 이동 | 이전 대화 전체 | 필요 없는 이력까지 따라가 컨텍스트가 무거워짐 | 입력 필터 |
| 도구로서의 에이전트, 서브에이전트 | 메인에 남음 | 호출할 때 넘긴 지시 | 지시에 빠진 제약이 사라짐 | 브리프와 출력 추출 |

앞의 정산 배치 사례는 두 번째 줄의 위험이 그대로 터진 경우입니다. 격리를 택했다면 넘길 맥락을 직접 골라 적는 일이 설계자의 몫이 됩니다.

### 어느 방식을 고를 것인가

제 기준은 이렇습니다. 받는 쪽이 사용자와 계속 대화해야 하면 handoff가 맞습니다. 상담 에이전트가 청구 담당 에이전트에게 고객을 넘기는 경우처럼, 이후의 대화 주인이 바뀌는 일입니다. 반대로 메인이 결과를 받아 다음 판단에 써야 하면 도구 방식이 맞습니다. 정산 배치 조사는 메인이 결과를 받아 사용자와 개선안을 논의해야 하므로 도구 방식입니다.

handoff에서도 정보 손실은 생깁니다. 입력 필터로 이력을 줄이면 줄인 만큼 사라지고, 줄이지 않으면 받는 쪽 컨텍스트가 처음부터 무겁습니다. 어느 쪽이든 경계에서 무엇이 넘어가는지를 명시적으로 정하는 일은 피할 수 없습니다.

## 3. 브리프는 한 줄 지시가 아니라 작업 지시서다

### 네 칸에 두 칸을 더한다

Anthropic은 같은 리서치 시스템 글에서, 서브에이전트에게 필요한 것을 네 가지로 정리했습니다. 목표, 출력 형식, 사용할 도구와 출처에 대한 안내, 명확한 작업 경계입니다. 처음에는 "반도체 부족 사태를 조사하라" 같은 짧은 지시를 주었는데, 서브에이전트들이 과제를 다르게 해석하거나 같은 검색을 반복했다고 합니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/multi-agent-research-system)

저는 여기에 두 가지를 더 넣는 편이 안전하다고 봅니다. 이미 정해진 것과 완료 기준입니다. 정산 배치 사례의 브리프를 다시 쓰면 이렇습니다.

```text
[브리프 예시]
목표: 정산 배치(SettlementJob)의 실행 시간이 긴 원인을 찾는다.

이미 정해진 것:
- 운영 DB 스키마 변경 불가 (테이블, 파티션, 인덱스 모두)
- 인덱스 추가안은 DBA가 반려함. 다시 제안하지 말 것.
- 배치 실행 주기와 청크 크기 변경은 허용됨.

범위: batch/settlement/ 아래 코드와 SQL 매퍼. 다른 배치는 보지 않는다.
도구: 읽기와 검색만 사용. 파일 수정 금지.

반환 형식: 아래 JSON 스키마를 따른다. 근거 원문은 investigation/settlement-01.md 에 쓴다.
완료 기준: 원인 후보마다 근거 위치가 하나 이상 있을 것.
```

"이미 정해진 것"에 반려된 안을 적는 것이 첫 번째 실패를 막습니다. 허용된 변경을 함께 적어 두면 서브에이전트가 탐색 방향을 스스로 좁힙니다.

브리프의 각 칸이 무엇을 막는지 짝지어 보면, 칸 하나를 비웠을 때 어떤 실패가 돌아올지 미리 알 수 있습니다.

| 칸 | 비워 두면 생기는 일 | 정산 배치 사례에서 |
| --- | --- | --- |
| 목표 | 서브에이전트가 과제를 넓게 또는 다르게 해석함 | 성능이 아니라 정합성 문제까지 조사함 |
| 이미 정해진 것 | 기각된 안이 되돌아옴 | 인덱스 추가 권고 |
| 범위 | 무관한 코드를 읽느라 토큰과 시간을 씀 | 다른 배치 수십 개를 훑음 |
| 도구 | 의도하지 않은 변경, 또는 필요한 도구 부족 | 조사 중 설정 파일 수정 |
| 반환 형식 | 근거와 불확실성이 빠진 산문 | "풀 스캔이 원인" 한 줄 |
| 완료 기준 | 너무 일찍 멈추거나 끝없이 탐색함 | 첫 후보를 찾자마자 보고 |

### 반환 형식은 스키마로 고정한다

반환 형식을 문장으로만 적어 두면 서브에이전트는 대개 그럴듯한 산문을 돌려줍니다. 메인이 그 산문에서 근거와 불확실성을 다시 골라내야 합니다. 형식을 스키마로 고정하면 하네스가 결과를 기계적으로 검사할 수 있습니다.

```json
{
  "_comment": "예시: 조사형 서브에이전트의 반환 스키마",
  "findings": [
    {
      "cause": "정산 대상 조회 SQL이 계약 이력 전체를 읽은 뒤 애플리케이션에서 필터링",
      "likelihood": "high",
      "evidence": [
        { "path": "batch/settlement/mapper/SettlementTarget.xml", "line": 42 },
        { "path": "batch/settlement/step/TargetReader.java", "line": 88 }
      ],
      "fix_without_schema_change": "조회 조건을 SQL로 내리고 기존 인덱스 컬럼을 조건에 사용"
    }
  ],
  "not_checked": [
    "실제 운영 실행 계획 (접근 권한 없음)",
    "다른 배치와의 동시 실행 여부"
  ],
  "artifact": "investigation/settlement-01.md"
}
```

반환 형식의 `not_checked` 칸이 핵심이라고 봅니다. "확인하지 못한 것"을 적게 하지 않으면, 요약은 본 것만으로 구성되고 메인은 그것을 전부라고 받아들입니다. 정산 배치 사례에서 서브에이전트가 운영 실행 계획을 보지 못했다는 사실은, 결론의 강도를 사용자에게 설명할 때 그대로 필요한 정보입니다.

### 정의 파일과 브리프의 역할을 나눈다

Claude Code에서는 서브에이전트를 YAML frontmatter가 붙은 Markdown 파일로 정의합니다. `name`, `description`이 필수이고 `tools`와 `model`은 선택입니다. `tools`를 생략하면 MCP 도구를 포함해 메인 스레드의 도구를 모두 물려받습니다. 프로젝트 수준 정의는 `.claude/agents/`에, 사용자 수준 정의는 `~/.claude/agents/`에 두고, 이름이 겹치면 프로젝트 쪽이 우선합니다. [\[Claude Code Docs: Subagents, 2025-10-07 스냅샷\]](https://web.archive.org/web/20251007103749/https://docs.claude.com/en/docs/claude-code/sub-agents)

```yaml
# .claude/agents/batch-investigator.md 의 frontmatter (예시)
---
name: batch-investigator
description: 배치 프로그램의 성능 원인을 조사한다. 코드를 수정하지 않고 근거 위치와 함께 보고한다. 배치 지연, 처리량 저하 조사 요청에 사용한다.
tools: Read, Grep, Glob
model: inherit
---
```

같은 문서는 Claude Code가 요청의 내용, 서브에이전트 정의의 `description`, 현재 맥락과 가용 도구를 보고 위임을 결정한다고 설명합니다. 그래서 `description`은 소개문이 아니라 언제 이 서브에이전트를 부를지에 대한 규칙에 가깝습니다. Claude Agent SDK에서는 같은 정의를 코드의 `agents` 매개변수로 넘길 수 있고, 같은 이름이면 코드로 정의한 쪽이 파일보다 우선합니다. [\[Claude Agent SDK Docs: Subagents, 2025-10-06 스냅샷\]](https://web.archive.org/web/20251006073255/https://docs.claude.com/en/api/agent-sdk/subagents)

저는 역할을 이렇게 나눕니다. 정의 파일 본문에는 언제나 유효한 규칙, 곧 반환 스키마, 근거 표기 방식, 수정 금지 같은 것을 고정합니다. 호출마다 달라지는 제약, 곧 이번 대화에서 반려된 안이나 이번 범위는 브리프에 넣습니다. 매번 같아야 하는 것을 브리프에 맡기면 메인 에이전트가 언젠가 빠뜨립니다.

### 돌아온 결과는 하네스가 먼저 검사한다

반환 형식을 스키마로 고정하면, 메인 에이전트가 결과를 읽기 전에 하네스가 몇 가지를 코드로 확인할 수 있습니다.

```python
# 예시: 서브에이전트 결과를 메인 컨텍스트에 넣기 전의 검사
def check_result(result: dict, brief: dict, repo) -> list[str]:
    problems = []
    for f in result.get("findings", []):
        if not f.get("evidence"):
            problems.append(f"근거 없는 결론: {f['cause']}")
        for ev in f.get("evidence", []):
            if not repo.line_exists(ev["path"], ev["line"]):
                problems.append(f"존재하지 않는 근거 위치: {ev['path']}:{ev['line']}")
        for banned in brief["rejected_options"]:          # 예: "인덱스 추가"
            if banned in f.get("fix_without_schema_change", ""):
                problems.append(f"반려된 안을 다시 제안: {banned}")
    if "not_checked" not in result:
        problems.append("확인하지 못한 것 칸 누락")
    return problems   # 비어 있지 않으면 결과와 함께 메인에 경고로 넣거나 재요청
```

문자열 포함 검사는 거칠지만, 반려된 안이 그대로 되돌아오는 실패는 이 정도로도 상당 부분 잡힙니다. 근거 위치가 실제로 존재하는지 확인하는 것은 모델이 그럴듯한 경로를 지어내는 경우를 걸러 냅니다. 나머지, 곧 근거가 결론을 정말 뒷받침하는지는 메인 에이전트나 사람이 근거 몇 개를 직접 열어 확인해야 합니다.

### 브리프가 깨지는 방식

브리프에도 실패 모드가 있습니다. 메인 에이전트가 브리프를 쓰는 주체이므로, 메인이 제약을 잊으면 브리프에도 빠집니다. 브리프 템플릿의 칸을 고정해 두면 "이미 정해진 것" 칸이 비어 있다는 사실 자체가 눈에 띕니다.

브리프가 지나치게 길어지는 것도 문제입니다. 메인 대화의 절반을 브리프에 옮겨 적으면 컨텍스트를 격리한 의미가 없습니다. 브리프가 대화 요약만큼 길어진다면, 그 일은 격리하지 말고 메인이 직접 하는 편이 낫다는 신호로 봅니다.

## 4. 병렬은 읽기에만: 쓰기는 한 곳으로 모은다

### 병렬 조사의 흐름

정산 배치 조사를 조금 키워 봅시다. 원인 후보가 SQL, 청크 처리, 외부 연동 대기의 세 방향으로 나뉜다면 서로 독립적인 읽기이므로 병렬로 돌릴 수 있습니다.

```text
메인 에이전트
  │  브리프 3개 작성 (공통: 이미 정해진 것, 반환 스키마 / 개별: 범위)
  ├──> 서브 A: SQL 매퍼와 조회 조건      ──> investigation/a.md
  ├──> 서브 B: 청크 크기와 커밋 주기     ──> investigation/b.md
  └──> 서브 C: 외부 연동 호출과 재시도    ──> investigation/c.md
  │
  │  결과 3개 수신 (findings, not_checked, artifact 경로)
  │  하네스 검사: 근거 위치 존재, 반려안 재등장, 칸 누락
  │
  ├── 겹치는 결론 병합, 서로 모순되는 결론 표시
  └── 사용자에게 보고 (확인하지 못한 것 포함)
        │
        └── 수정은 메인이 직접, 한 번에 하나씩
```

마지막 줄이 이 절의 요점입니다. 조사는 셋으로 나눴지만, 개선안을 코드에 반영하는 일은 메인 한 곳에서 합니다.

### 노력의 규모를 미리 정한다

에이전트는 일의 크기에 맞는 노력을 스스로 가늠하는 데 서툽니다. Anthropic의 리서치 시스템은 이를 프롬프트에 규칙으로 넣었습니다. 단순한 사실 확인은 에이전트 하나와 도구 호출 3~10회, 직접 비교는 서브에이전트 2~4개와 각 10~15회, 복잡한 조사는 역할을 분명히 나눈 서브에이전트 10개 이상이라는 식입니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/multi-agent-research-system)

수치 자체는 그 시스템의 것이지만, 규모를 규칙으로 고정한다는 발상은 그대로 가져올 만합니다. 정산 배치처럼 원인이 셋으로 나뉘는 조사라면 서브에이전트 셋, 각각 호출 상한을 둔다는 식으로 브리프에 적어 둘 수 있습니다.

### 조율을 모델에게 맡길지 코드에게 맡길지

OpenAI Agents SDK 문서는 조율 방식을 두 가지로 나눕니다. LLM이 다음에 무엇을 할지 정하게 하는 방식과, 코드로 에이전트의 흐름을 정하는 방식입니다. 문서는 코드로 조율하면 속도, 비용, 성능 면에서 더 결정적이고 예측 가능해진다고 설명하고, 예로 서로 의존하지 않는 작업을 `asyncio.gather`로 병렬 실행하는 방법을 듭니다. [\[OpenAI Agents SDK: Orchestrating multiple agents, 2025-09-28 커밋\]](https://github.com/openai/openai-agents-python/blob/14d7d591e2b960f58cbd601e2b26f3993301618b/docs/multi_agent.md)

Anthropic이 2024년 말에 정리한 패턴 분류에서도 같은 구분이 보입니다. 하위 작업을 미리 알 수 없을 때는 중앙 LLM이 동적으로 쪼개는 오케스트레이터-워커 구성이 맞고, 미리 알 수 있으면 정해진 흐름의 병렬화로 충분하다는 것입니다. [\[Anthropic: Building effective agents\]](https://www.anthropic.com/engineering/building-effective-agents)

정산 배치 조사에서 세 방향이 처음부터 보인다면, 메인 에이전트에게 몇 개를 띄울지 맡기지 않고 하네스가 세 개를 띄우는 편이 비용도 결과도 예측하기 쉽습니다.

### 왜 쓰기는 모으는가

Anthropic의 리서치 시스템 글은 한계를 직접 적어 두었습니다. 모든 에이전트가 같은 컨텍스트를 공유해야 하거나 에이전트 사이에 의존이 많은 영역은 잘 맞지 않고, 대부분의 코딩 작업은 리서치보다 진정으로 병렬화할 수 있는 부분이 적다는 것입니다. [\[Anthropic: How we built our multi-agent research system\]](https://www.anthropic.com/engineering/multi-agent-research-system)

Cognition은 6월에 낸 글에서 같은 지점을 더 강하게 짚었습니다. 행동에는 암묵적인 결정이 담기고, 서로 상충하는 결정은 나쁜 결과로 이어진다는 원칙입니다. 같은 글은 당시 Claude Code가 하위 작업 에이전트를 쓰되 병렬로 코드를 쓰게 하지 않고, 주로 잘 정의된 질문에 답하는 일에 쓴다고 관찰했습니다. [\[Cognition: Don't Build Multi-Agents\]](https://cognition.ai/blog/dont-build-multi-agents)

그래서 제 기준은 단순합니다. 읽기는 나누고, 쓰기는 모읍니다. 조사와 검색과 검증은 격리해도 잃는 것이 적지만, 코드 수정은 앞선 결정을 전부 알고 있어야 하는 일이기 때문입니다. 정산 배치에서 서브 A가 SQL 조건을 바꾸자고 하고 서브 B가 청크 크기를 바꾸자고 할 때, 둘을 동시에 적용할지 하나씩 적용해 측정할지는 둘 다 본 메인만 정할 수 있습니다.

### 결과를 합치는 일은 메인의 몫이다

병렬 조사의 결과는 대개 깔끔하게 맞물리지 않습니다. 서브 A는 SQL 조건이 원인이라고 하고, 서브 B는 커밋 주기가 원인이라고 할 수 있습니다. 둘 다 근거가 있다면 어느 한쪽이 틀린 것이 아니라 원인이 둘일 수도 있습니다.

이때 메인이 하지 말아야 할 일은 두 결론을 평균 내듯 섞는 것입니다. "SQL과 커밋 주기를 모두 개선하면 빨라질 것"이라는 문장은 그럴듯하지만, 어느 쪽이 얼마나 기여하는지는 아무도 확인하지 않았습니다.

제가 권하는 순서는 이렇습니다. 먼저 결론들이 같은 근거 위치를 가리키는지 봅니다. 같은 곳을 다르게 해석했다면 그 위치를 메인이 직접 엽니다. 서로 다른 곳을 가리킨다면 각각을 독립된 후보로 두고, 사용자에게 하나씩 적용해 측정하자고 제안합니다. 두 서브에이전트의 `not_checked`가 서로의 결론을 가리키는 경우, 예를 들어 A가 커밋 주기는 보지 않았다고 적었다면, 그 빈칸이 곧 다음 조사의 범위가 됩니다.

### 쓰지 말아야 할 때

넘기기 전에 확인할 것을 목록으로 만들면 이렇습니다. 하나라도 아니라면 메인 에이전트가 직접 하는 쪽이 낫습니다.

- 메인 대화의 맥락 없이도 브리프 몇 문장으로 설명할 수 있는 일인가
- 결과가 정해진 형식의 요약으로 충분한가, 중간 과정이 나중에 필요하지 않은가
- 다른 작업과 같은 파일이나 같은 결정을 건드리지 않는가
- 브리프를 쓰고 결과를 검사하는 비용보다 탐색 비용이 확실히 큰가
- 돌아온 결과를 검증할 방법이 있는가

## 5. 보수적인 환경에서는 권한과 기록의 경계로도 쓴다

### 컨텍스트의 경계를 권한의 경계로 쓴다

금융이나 보험처럼 통제가 중요한 환경에서는 서브에이전트의 다른 면이 쓸모 있다고 봅니다. 컨텍스트의 경계가 곧 권한의 경계가 될 수 있기 때문입니다.

Claude Agent SDK 문서는 도구 제한의 예로 문서 검토용 서브에이전트에 Read와 Grep 도구만 주는 경우를 듭니다. 분석은 하되 실수로라도 파일을 고칠 수 없게 하는 구성입니다. [\[Claude Agent SDK Docs: Subagents, 2025-10-06 스냅샷\]](https://web.archive.org/web/20251006073255/https://docs.claude.com/en/api/agent-sdk/subagents)

운영 데이터 조회, 레거시 코드 분석처럼 읽기만 해야 하는 일을 읽기 전용 서브에이전트에 묶어 두면, "이 에이전트가 무엇을 바꿀 수 있는가"라는 질문에 설정 파일 한 장으로 답할 수 있습니다. 정산 배치 조사에서 서브에이전트에 `Read, Grep, Glob`만 준 것도 같은 이유입니다.

주의할 점이 있습니다. `tools`를 생략하면 모든 도구를 물려받으므로, 읽기 전용이어야 할 서브에이전트는 반드시 목록을 명시해야 합니다. 생략이 곧 전체 허용이라는 기본값은 통제 관점에서 가장 먼저 점검할 부분입니다.

### 민감한 데이터는 경계 안에서 줄여서 올린다

격리는 개인정보를 다룰 때도 쓸 수 있습니다. 예를 들어 정산 오류를 조사하면서 실제 청구 건을 봐야 한다고 해봅시다. 메인 대화가 고객 이름과 계좌 번호로 채워지는 것은 피하고 싶습니다.

이 경우 조회는 서브에이전트가 하고, 반환 스키마에는 건수, 금액 합계, 마스킹된 표본 몇 건만 허용하도록 정해 둘 수 있습니다. 메인 컨텍스트와 그 대화 로그에는 원본이 남지 않습니다. 다만 서브에이전트 컨텍스트 안에서는 원본이 모델에 들어가므로, 이것이 모델에 개인정보를 보내지 않는 방법은 아니라는 점을 분명히 해 두어야 합니다. 줄어드는 것은 노출 범위와 기록 범위이지 노출 자체가 아닙니다.

### 브리프와 반환이 곧 감사 기록이다

기록도 마찬가지입니다. 브리프와 반환 결과는 경계를 넘는 유일한 정보이므로, 이 둘만 남겨도 어떤 지시에서 어떤 결론이 나왔는지를 추적할 수 있습니다. 하네스가 위임마다 한 줄씩 남기는 기록을 예로 들면 이렇습니다.

```json
{
  "_comment": "예시: 위임 1건의 감사 기록",
  "delegation_id": "d-20251008-0012",
  "parent_session": "s-7f3a",
  "subagent": "batch-investigator",
  "definition_commit": "a1b2c3d",
  "tools_granted": ["Read", "Grep", "Glob"],
  "brief_sha256": "9e1f...",
  "result_sha256": "c47a...",
  "harness_checks": { "missing_evidence": 0, "rejected_option_repeated": 0 },
  "artifact": "investigation/settlement-01.md"
}
```

`definition_commit`을 남기는 이유는 서브에이전트 정의가 바뀌기 때문입니다. Claude Code 문서는 프로젝트 서브에이전트 정의를 버전 관리에 넣어 팀이 함께 개선하라고 권합니다. [\[Claude Code Docs: Subagents, 2025-10-07 스냅샷\]](https://web.archive.org/web/20251007103749/https://docs.claude.com/en/docs/claude-code/sub-agents) 정의가 바뀐 이력이 곧 통제의 이력이 되고, 어떤 결론이 어느 버전의 정의에서 나왔는지를 나중에 재현할 수 있습니다.

### 승인선을 둘 자리

보수적인 조직에서 가장 걱정하는 것은 에이전트가 모르는 사이에 무언가를 바꾸는 일입니다. 읽기와 쓰기를 나눠 두면 승인 지점이 하나로 모입니다. 서브에이전트들은 조사만 하고, 수정은 메인 에이전트가 사람의 확인을 받은 뒤 한 번에 하나씩 합니다. 승인 대상이 "에이전트 다섯 개가 한 일"이 아니라 "메인이 제안한 변경 하나"가 됩니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 최근 세션 하나를 골라 메인 컨텍스트를 가장 많이 차지한 도구 결과가 무엇인지 봅니다. 대부분 버려진 탐색성 읽기라면 그것이 첫 후보입니다.
2. 그 한 가지 일에만 읽기 전용 서브에이전트를 붙입니다. `tools`를 명시하고, 역할 이름을 여러 개 만들지 않습니다.
3. 브리프 템플릿을 고정합니다. 목표, 이미 정해진 것, 범위, 도구, 반환 형식, 완료 기준의 여섯 칸이고, 반환 스키마는 정의 파일 본문에 둡니다.
4. 반환 스키마에 근거 위치와 확인하지 못한 것을 넣고, 하네스가 근거 위치의 존재와 반려안의 재등장을 먼저 검사하게 합니다. 남은 결과 중 일부는 근거를 직접 열어 확인합니다.
5. 브리프, 결과, 정의 파일의 커밋을 위임마다 기록하고, 수정 작업의 병렬화는 그 다음 단계로 미룹니다. 하더라도 파일이 겹치지 않는 경우로 한정합니다.

## 마치며

서브에이전트를 설계한다는 것은 팀을 꾸리는 일보다 경계를 긋는 일에 가깝습니다. 경계 안쪽에서는 잡음이 줄어들고, 경계를 넘는 순간에는 정보가 줄어듭니다. 그래서 설계의 대상은 에이전트의 수가 아니라 경계를 넘어가는 두 문서, 곧 브리프와 반환 결과입니다. 이 둘을 먼저 써 보면 서브에이전트가 정말 필요한 자리인지도 함께 드러납니다.
