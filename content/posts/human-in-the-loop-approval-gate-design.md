:::note
- 승인 게이트는 tool 종류가 아니라 되돌릴 수 있는지와 잘못되면 어디까지 번지는지로 정하고, 같은 tool이라도 호출 인자를 보고 판정합니다.
- 승인 요청은 대상, 변경 내용, 되돌리는 방법, 평소와 다른 점을 하네스가 데이터에서 직접 만들어 보여 줘야 합니다. tool 이름과 버튼만으로는 사람이 판단할 수 없습니다.
- 보내기는 초안으로, 실행은 미리보기나 요청서로 한 단계 낮추면 승인이 필요한 지점 자체가 줄어듭니다. 승인 피로는 교육이 아니라 요청 수를 줄여서 풉니다.
- 승인은 멈춤과 재개가 가능한 상태 저장 위에서 동작해야 하고, 결정은 누가 무엇을 보고 언제 무엇을 정했는지와 함께 기록합니다.
:::

에이전트의 위험을 이야기하면 흔히 이런 답이 나옵니다. "위험한 작업 앞에 사람 승인을 넣으면 안전하다."

방향은 맞습니다. MCP 명세도 신뢰와 안전을 위해 tool 호출을 거부할 수 있는 사람이 항상 루프 안에 있어야 한다고 권고하고, 애플리케이션이 실행 전에 확인 창을 보여 줘야 한다고 적습니다. [\[MCP Specification 2025-06-18: Tools\]](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

그런데 승인 단계를 넣는 것과 사람이 실제로 판단하는 것은 다른 일입니다.

**승인 버튼이 있다는 사실이 아니라, 그 버튼 앞에서 사람이 판단할 수 있느냐가 Human-in-the-loop의 품질을 결정합니다.**

Anthropic이 2026년 8월 7일에 공개한 자료가 이 차이를 수치로 보여 줍니다. Claude Code 사용자는 권한 요청의 97%를 승인했습니다. 유료 테스터 1,053명이 참여한 통제 실험에서 세션 중간의 권한 요청 하나를 명백히 위험한 명령으로 바꿔 끼웠더니, 사람이 그것을 걸러낸 비율은 13.6%였습니다. [\[Claude: Auto mode is now the default in Claude Code\]](https://claude.com/resources/articles/auto-mode-default-in-claude-code)

NIST의 생성형 AI 프로파일은 이런 현상을 Human-AI Configuration 위험으로 분류하고, 자동화된 시스템을 지나치게 따르는 것을 automation bias라고 부릅니다. [\[NIST AI 600-1: Generative AI Profile\]](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

이 글은 승인 게이트를 어디에 두고, 그 앞에 무엇을 보여 주고, 승인 자체를 어떻게 줄이고, 승인을 기다리는 동안과 그 이후를 어떻게 설계할지를 다룹니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사가 단순 청구 건의 접수부터 지급까지를 돕는 에이전트를 운영한다고 해봅시다. 이 글 전체에서 쓸 예시입니다.

에이전트의 tool은 다섯 개입니다. 청구 건 조회, 첨부 서류 요약, 고객 안내 메일 발송, 수령 계좌 변경, 보험금 지급 실행입니다. 지급 실행 앞에는 담당자 승인이 걸려 있고, 담당자 화면에 이런 창이 뜹니다.

```text
에이전트가 process_payout 도구를 실행하려 합니다.

        [ 승인 ]   [ 거절 ]
```

담당자는 오늘 이 창을 이미 수십 번 봤습니다. 대부분 소액 통원비였고 전부 승인했습니다. 이번에도 승인을 누릅니다.

그런데 이번 건은 지급액이 평소보다 자릿수가 하나 더 많았고, 수령 계좌는 30분 전에 같은 에이전트가 변경한 계좌였으며, 그 명의는 피보험자와 달랐습니다. 계좌 변경 tool에는 승인이 걸려 있지 않았습니다.

담당자의 부주의를 탓하기 쉽지만, 시스템 설계 관점에서 보면 문제는 다른 곳에 있습니다.

- 승인 요청에 금액, 대상 계좌, 평소와 다른 점, 되돌릴 수 있는지가 없었다.
- 3만 원 지급과 300만 원 지급이 같은 게이트를 지났다.
- 지급만 게이트를 지나고, 지급 대상을 바꾸는 계좌 변경은 게이트가 없었다.
- 누가 무엇을 보고 승인했는지 남지 않았다.

## 1. 게이트는 되돌림 가능성과 영향 범위로 정한다

모든 tool 호출에 승인을 붙이면 곧 아무도 읽지 않습니다. 반대로 아무 데도 안 붙이면 사고가 납니다. 그래서 기준이 필요합니다.

### 두 가지 질문

제가 권하는 기준은 두 가지 질문입니다. 되돌릴 수 있는가, 그리고 잘못되면 어디까지 번지는가.

| 되돌림 | 영향 범위 | 일반적인 예 | 예시 에이전트의 tool | 게이트 |
| --- | --- | --- | --- | --- |
| 가능 | 작업 공간 안 | 파일 읽기, 로컬 수정, 초안 작성 | 청구 건 조회, 서류 요약 | 승인 없음. 기록만 |
| 가능 | 작업 공간 밖 | 브랜치 push, 티켓 상태 변경 | 청구 건에 메모 남기기 | 사전 규칙으로 허용하거나 묶어서 승인 |
| 불가 | 한 건 | 메일 발송, 소액 지급 | 고객 안내 메일, 한도 이하 지급 | 건별 승인, 또는 한 단계 낮추기 |
| 불가 | 여러 건, 돈의 흐름, 공용 자원 | 일괄 삭제, 운영 DB 변경, 대량 발송 | 수령 계좌 변경, 한도 초과 지급 | 건별 승인과 2인 확인 |

예시의 사고는 이 표에서 바로 보입니다. 수령 계좌 변경은 이후 모든 지급의 행선지를 바꾸는 동작입니다. 그 자체로 돈이 움직이지는 않지만 영향 범위는 지급보다 큽니다. tool 이름만 보면 "정보 수정"이라 가볍게 분류되기 쉬운데, 영향 범위로 보면 가장 무거운 칸에 들어갑니다.

### 하네스가 판정하는 순서

게이트 판정은 모델이 아니라 하네스가 합니다. 한 번의 tool 호출에서 하네스가 하는 일을 단계로 풀면 이렇습니다.

1. 모델이 tool 호출을 제안합니다.
2. 하네스가 금지 규칙부터 봅니다. 걸리면 실행하지 않고 거절 사유를 모델에 돌려줍니다.
3. 확인 규칙을 봅니다. 걸리면 승인 요청을 만들고 멈춥니다.
4. 허용 규칙을 봅니다. 걸리면 실행합니다.
5. 어느 규칙에도 안 걸리면 기본값을 따릅니다. 예시처럼 돈이 오가는 시스템이라면 기본값은 확인이어야 합니다.

Claude Code의 권한 규칙이 이 순서를 따릅니다. 규칙은 deny, ask, allow 순서로 평가되고 그 순서에서 처음 맞는 것이 결과를 정합니다. 규칙의 구체성은 순서를 바꾸지 않아서, 넓은 deny 규칙은 더 좁은 allow 규칙에 맞는 호출도 막고, ask 규칙에 걸린 호출은 더 구체적인 allow 규칙이 있어도 묻습니다. [\[Claude Code Docs: Permissions\]](https://web.archive.org/web/20260816101136/https://code.claude.com/docs/en/permissions)

이 순서가 주는 성질이 중요합니다. 누군가 편의를 위해 allow 규칙을 넓게 추가해도, 금지와 확인 규칙을 뚫지 못합니다. 위험한 칸의 규칙을 deny와 ask에 두면, 나중에 들어오는 allow 규칙이 그것을 덮어쓰지 못합니다.

### 제품의 기본값도 같은 축을 따른다

Claude Code는 작업 디렉터리 안의 읽기 전용 작업에는 승인을 요구하지 않고, 셸 명령과 파일 수정에는 기본으로 요구합니다. [\[Claude Code Docs: Permissions\]](https://web.archive.org/web/20260816101136/https://code.claude.com/docs/en/permissions)

OpenAI Codex는 샌드박스와 승인 정책을 두 층으로 둡니다. 기본인 Auto 프리셋에서는 작업 공간 안의 읽기, 수정, 명령 실행은 자동이고, 작업 공간 밖을 수정하거나 네트워크에 접근하려면 승인을 묻습니다. 그리고 앱이나 MCP tool이 스스로 파괴적이라는 표시를 붙였다면, 다른 표시가 함께 있더라도 그 호출은 항상 승인을 요구합니다. [\[OpenAI Codex: Agent approvals and security\]](https://web.archive.org/web/20260630015902/https://developers.openai.com/codex/agent-approvals-security)

두 제품 모두 경계선을 작업 공간 안이냐 밖이냐에 긋고 있습니다. 영향 범위를 환경으로 먼저 좁혀 두면 승인이 필요한 지점이 줄어든다는 뜻입니다.

### 같은 tool이라도 인자를 보고 판정한다

게이트를 호출 내용에 따라 다르게 걸 수도 있습니다. OpenAI Agents SDK는 tool의 승인 필요 여부를 고정값 대신 함수로 줄 수 있고, 이 함수는 실행 문맥, 파싱된 tool 인자, tool 호출 ID를 받습니다. 인자가 비었거나 JSON이 깨졌거나 객체가 아니면 함수를 부르지 않고 수동 승인으로 넘깁니다. 판단할 수 없으면 닫힌 쪽으로 실패하는 설계입니다. [\[OpenAI Agents SDK: Human-in-the-loop\]](https://github.com/openai/openai-agents-python/blob/80e1baaefdfff291b3d7e55987219107c9736d80/docs/human_in_the_loop.md)

예시의 지급 tool이라면 판정 함수는 이런 모양이 됩니다. 아래는 제가 만든 예시이고, 특정 SDK의 시그니처를 그대로 옮긴 것이 아닙니다.

```python
# 예시: 지급 tool의 게이트 판정. 판단 근거는 모델이 아니라 원장과 규정에서 가져온다
def payout_gate(args: dict, ledger, policy) -> str:
    claim = ledger.get_claim(args["claim_id"])            # 모델이 준 값이 아니라 원장 조회
    account = ledger.get_payee_account(claim.id)
    if account.changed_within(hours=24):
        return "two_person"                                # 최근 변경된 계좌로의 지급
    if account.holder_name != claim.insured_name:
        return "two_person"                                # 명의 불일치
    if args["amount"] > claim.approved_amount:
        return "deny"                                      # 사정 금액 초과는 실행 불가
    if args["amount"] > policy.single_approval_limit:
        return "human"                                     # 전결 한도 초과
    return "auto"                                          # 한도 이하, 정상 계좌
```

이 함수에서 중요한 것은 판정 근거를 어디서 가져오느냐입니다. 금액 한도와 계좌 명의는 모델이 tool 인자로 넘긴 설명이 아니라 원장에서 다시 읽습니다. 모델이 "피보험자 본인 계좌입니다"라고 적어 보내도 게이트는 그 문장을 보지 않습니다.

:::caution
tool이 스스로 붙인 "읽기 전용", "파괴적" 같은 표시는 참고 자료일 뿐입니다. MCP 명세는 신뢰할 수 있는 서버에서 온 것이 아니면 클라이언트가 tool annotation을 신뢰하지 말아야 한다고 명시합니다. [\[MCP Specification 2025-06-18: Tools\]](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) 게이트 기준은 하네스 쪽에서 직접 정해야 합니다.
:::

### 게이트를 돌아가는 경로도 게이트 대상이다

예시의 사고에는 한 가지 특징이 더 있습니다. 승인이 걸린 지급 자체는 정상 경로로 지나갔고, 문제는 승인이 없는 계좌 변경이 먼저 일어났다는 데 있었습니다. 게이트가 걸린 동작의 입력을 바꾸는 동작은, 게이트가 걸린 동작과 같은 칸으로 보는 편이 안전하다고 봅니다.

같은 이유로 에이전트가 게이트 설정 자체를 바꿀 수 있어서도 안 됩니다. Anthropic이 auto mode 분류기의 기본 차단 규칙으로 묶어 둔 범주에도, 로그를 끄거나 에이전트 자신의 권한 설정을 고쳐서 감시와 방어를 어렵게 만드는 동작이 들어 있습니다. [\[Anthropic: How we built Claude Code auto mode\]](https://www.anthropic.com/research/claude-code-auto-mode) 판정 함수의 한도값과 허용 규칙 파일은 에이전트의 쓰기 권한 밖에 두고, 바꾸려면 사람의 변경 절차를 거치게 해야 합니다.

### 실패 모드와 비용

- tool 이름으로만 분류하면 예시의 계좌 변경처럼 이름은 가볍고 영향은 무거운 동작을 놓칩니다. 분류는 "이 동작이 이후 무엇을 바꾸는가"로 해야 합니다.
- 인자 기반 판정은 판정 함수 자체가 새 코드라 버그가 생깁니다. 판정 함수의 입력과 결과를 매번 기록해 두어야, 게이트가 열렸어야 할 때 닫히지 않은 사례를 나중에 찾을 수 있습니다.
- 판정 근거를 원장에서 다시 읽으면 조회가 한 번 더 듭니다. 돈이 오가는 tool에서는 감수할 만한 비용이라고 봅니다.

## 2. 승인 요청은 결정에 필요한 것을 보여 줘야 한다

승인 요청은 사람에게 보내는 인터페이스입니다. tool 이름과 JSON 덩어리를 던지면 사람은 읽지 않고 누릅니다.

### 요청에 들어가야 할 것

승인 요청에 들어가야 한다고 보는 항목은 다음과 같습니다.

- 무엇을 하려는가. tool 이름이 아니라 사람의 말로 쓴 한 줄
- 대상이 무엇인가. 청구 건, 계좌, 수신자, 테이블, 브랜치
- 무엇이 바뀌는가. 변경 전과 후, 금액, 건수
- 되돌릴 수 있는가. 가능하다면 방법, 불가능하다면 불가능하다는 표시
- 왜 하려는가. 사용자의 어떤 요청이나 어떤 업무 규칙에서 나온 행동인지
- 평소와 다른 점. 한도 초과, 처음 보는 대상, 최근 변경, 요청에 없던 행동

아래는 이 항목을 담은 승인 요청의 예시입니다.

```json
{
  "action": "보험금 지급 실행",
  "tool": "process_payout",
  "target": {
    "claim_id": "CLM-2026-081734",
    "payee_account": "○○은행 ***-**-4821",
    "payee_holder": "피보험자와 다른 명의"
  },
  "change": { "amount_krw": 3000000, "approved_amount_krw": 3000000, "typical_amount_krw": 300000 },
  "reversible": false,
  "requested_by": "청구 접수 대화 12번째 메시지: 빨리 지급해 주세요",
  "flags": [
    "지급액이 이 상품 평균의 10배",
    "수령 계좌가 31분 전 에이전트에 의해 변경됨",
    "계좌 명의 불일치"
  ],
  "related_actions": ["update_payee_account (14:02, 승인 없음)"],
  "options": ["approve", "edit", "reject", "escalate"]
}
```

`flags`와 `related_actions`가 이 요청의 핵심입니다. 담당자가 한 번에 봐야 할 것은 금액이 아니라 "왜 이번 건이 평소와 다른가"입니다. `options`에 edit와 escalate가 있는 점도 봐 주시기 바랍니다. 승인과 거절만 있으면 사람은 조금 틀린 요청을 통째로 거절하거나 그냥 승인합니다. 금액만 고쳐서 통과시키거나 상위 결재자에게 넘길 수 있어야 합니다.

### 요약은 모델의 말이 아니라 데이터에서 만든다

여기서 하나 짚을 점이 있습니다. 승인 요청의 문구를 에이전트에게 쓰게 하면, 에이전트가 자기 행동을 정당화하는 문장이 요청에 들어갑니다.

Anthropic은 승인을 대신하는 분류기를 만들면서 이 문제를 직접 다뤘습니다. 분류기에는 에이전트가 쓴 설명 문장을 빼고 사용자 메시지와 실제 실행될 명령만 보여 줍니다. 에이전트가 "사용자가 앞에서 암묵적으로 승인했으니 안전하다" 같은 그럴듯한 합리화를 만들어 분류기를 설득하지 못하게 하려는 것이고, 에이전트가 말한 것이 아니라 한 것을 판단하게 하려는 것이라고 설명합니다. [\[Anthropic: How we built Claude Code auto mode\]](https://www.anthropic.com/research/claude-code-auto-mode)

사람에게 보여 주는 승인 요청도 같은 원칙을 따르는 편이 낫다고 봅니다. 위 예시의 `target`, `change`, `flags`, `related_actions`는 모두 하네스가 원장과 실행 기록에서 직접 채운 값입니다. 에이전트의 설명을 넣고 싶다면 그것이 에이전트의 말이라는 표시를 붙여 별도 칸에 둡니다.

### 무엇을 승인 단위로 삼을까

승인의 단위도 중요합니다. Anthropic의 8월 자료에 따르면 개별 권한 요청의 거절률은 3%인데, 계획을 통째로 보여 주고 승인받을 때는 39%가 거절됩니다. [\[Claude: Auto mode is now the default in Claude Code\]](https://claude.com/resources/articles/auto-mode-default-in-claude-code)

명령 한 줄보다 계획 전체가 사람이 판단하기 쉬운 단위라는 뜻으로 읽습니다. 예시라면 "계좌 변경"과 "지급"을 따로 묻는 대신 "이 청구 건을 새 계좌로 300만 원 지급하는 처리 계획"을 한 번에 보여 주는 편이, 담당자가 두 동작의 관계를 알아채기 쉽습니다. 가능하면 잘게 쪼갠 승인 열 번보다 의미 있는 묶음 한 번이 낫습니다.

### 한 번의 승인이 어디까지 유효한가

승인의 범위도 요청에 드러나야 합니다. Anthropic은 분류기가 놓친 사례를 분석하면서, 분류기가 위험 자체는 알아보았지만 세션 안의 승인처럼 보이는 근거가 이 행동의 영향 범위까지 덮는 동의인지 확인하지 못한 경우가 많았다고 짚습니다. "PR을 정리해 줘"라는 말은 force-push를 지시한 것이 아니고, 비슷한 행동을 한 번 승인했다고 패턴이 되지는 않는다는 것입니다. [\[Anthropic: How we built Claude Code auto mode\]](https://www.anthropic.com/research/claude-code-auto-mode)

사람의 승인에도 같은 원칙이 적용됩니다. 제품들은 이것을 유효 범위로 다룹니다.

| 제품 | 승인 범위의 단위 | 문서가 밝힌 동작 |
| --- | --- | --- |
| Claude Code | tool 종류별로 다름 | "다시 묻지 않기"를 고르면 셸 명령은 저장소와 명령 단위로 영구 저장, 파일 수정은 세션이 끝날 때까지만 유지 |
| OpenAI Agents SDK | 호출 ID, 또는 실행 동안의 tool | 기본 승인은 해당 호출 ID에만 적용. `always_approve`를 주면 같은 실행의 남은 기간 동안 같은 tool에 적용되고, 직렬화한 실행 상태에 함께 저장됨 |

출처는 각각 Claude Code 권한 문서와 OpenAI Agents SDK의 HITL 문서입니다. [\[Claude Code Docs: Permissions\]](https://web.archive.org/web/20260816101136/https://code.claude.com/docs/en/permissions) [\[OpenAI Agents SDK: Human-in-the-loop\]](https://github.com/openai/openai-agents-python/blob/80e1baaefdfff291b3d7e55987219107c9736d80/docs/human_in_the_loop.md)

예시의 지급 tool이라면 승인 범위는 언제나 "이번 한 건"이어야 한다고 봅니다. 지급에 "다시 묻지 않기"가 있으면 안 됩니다.

### 실패 모드와 비용

- 항목을 다 넣으면 요청이 길어지고, 긴 요청은 또 안 읽힙니다. 평소와 다른 점이 없는 건은 짧게, `flags`가 있는 건만 길게 보여 주는 식으로 길이에 차등을 두는 편이 낫습니다.
- `flags`를 만드는 규칙이 없으면 이 칸은 늘 비어 있습니다. 평균 금액, 최근 변경 여부, 명의 일치 같은 기준값을 하네스가 조회할 수 있어야 합니다.
- 묶음 승인은 묶음 안의 위험한 한 줄을 묻어 버릴 수 있습니다. 묶음에도 가장 위험한 동작을 맨 위에 올리는 규칙이 필요합니다.

## 3. 위험한 행동은 한 단계 낮춘다

승인보다 먼저 검토할 방법이 있습니다. 행동 자체를 덜 위험한 형태로 바꾸는 것입니다.

| 원래 행동 | 한 단계 낮춘 형태 | 사람이 하는 일 |
| --- | --- | --- |
| 메일 발송 | 초안 저장 | 읽고 직접 보내기 |
| 운영 DB 수정 | 변경 SQL과 영향 건수 미리보기 | 검토 후 정해진 절차로 실행 |
| main에 push | 브랜치에 push하고 PR 생성 | 리뷰와 머지 |
| 일괄 삭제 | 삭제 대상 목록 출력, 또는 보관 처리 | 목록 확인 |
| 보험금 지급 실행 | 지급 요청서 생성 | 기존 결재선에서 승인 |
| 수령 계좌 변경 | 변경 요청 등록 | 본인 확인 절차를 거쳐 반영 |

### 낮추기는 tool 목록을 바꾸는 것이다

이 방식의 동작은 단순합니다. 에이전트에게 실행 tool을 주지 않고, 그 자리에 산출물을 만드는 tool을 줍니다.

예시라면 `process_payout` 대신 `create_payout_request`를, `update_payee_account` 대신 `submit_account_change_request`를 줍니다. 에이전트는 요청서를 만들 수 있지만 지급을 실행할 수는 없습니다. 지급은 기존 지급 시스템이 결재를 확인한 뒤에 실행합니다.

프롬프트로 "직접 지급하지 마라"고 당부하는 것보다 확실한 이유가 여기 있습니다. 실행 tool이 없으면 모델이 지시를 어기거나 프롬프트 주입에 넘어가도 실행할 수단이 없습니다.

### 사람이 익숙한 자리에서 판단한다

이 방식의 다른 장점은 사람의 판단이 원래 하던 업무 흐름 안에서 일어난다는 것입니다. 초안을 읽고 보내는 것, PR을 리뷰하는 것, 결재 문서를 보는 것은 이미 익숙한 일입니다. 낯선 승인 창보다 주의를 기울이기 쉽고, 그 업무 흐름에는 이미 검토 기준과 기록이 있습니다.

### 실패 모드와 비용

- 낮춘 산출물이 자동으로 실행되는 연결이 생기면 낮춘 의미가 없습니다. 예를 들어 지급 요청서가 일정 시간 안에 거절되지 않으면 자동 승인되는 규칙이 있다면, 게이트는 시간 초과 하나로 열립니다.
- 모든 것을 낮추면 사람의 일이 늘어납니다. 소액이고 정상 계좌인 지급까지 요청서로 돌리면 담당자는 요청서 피로를 겪게 됩니다. 1절의 판정 함수처럼 낮출 대상을 위험한 칸으로 한정해야 합니다.
- 낮춘 형태가 존재하지 않는 동작도 있습니다. 실시간으로 처리해야 하는 거래 차단처럼 초안 단계를 둘 수 없는 동작은 승인이나 자동 판단으로 다뤄야 합니다.

## 4. 승인 피로는 사람 문제가 아니라 설계 문제다

승인 요청이 많아지면 사람은 내용을 보지 않게 됩니다. Anthropic은 이것을 approval fatigue라고 부릅니다. [\[Anthropic: How we built Claude Code auto mode\]](https://www.anthropic.com/research/claude-code-auto-mode)

### 숫자가 말하는 것

8월 자료에는 세션 길이에 따른 수치도 있습니다. 통제 실험에서 사람은 세션 초반에는 위험한 명령의 약 17%를 막았지만, 승인 요청을 50번 넘게 본 뒤에는 약 5%로 떨어졌습니다. [\[Claude: Auto mode is now the default in Claude Code\]](https://claude.com/resources/articles/auto-mode-default-in-claude-code)

피로는 설정 파일에도 나타납니다. 같은 자료에 따르면 2026년 6월 기준 활성 CLI 사용자의 49.5%가 Bash 허용 규칙을 직접 만들었고, 62%는 권한 우회 모드를 쓰거나 Bash에 "다시 묻지 않기"를 누른 적이 있습니다. 묻는 횟수가 많으면 사람은 묻지 않게 만드는 쪽으로 움직인다는 뜻입니다.

교육이나 주의 환기로는 풀리지 않는다고 봅니다. 승인 요청의 수를 줄여야 합니다.

### 줄이는 순서

- 읽기 전용 작업은 묻지 않는다.
- 되돌릴 수 있고 작업 공간 안에 머무는 작업은 환경을 격리해서 묻지 않는다.
- 반복되는 안전한 명령은 좁은 범위의 규칙으로 허용한다. 인터프리터 전체를 허용하는 식의 넓은 규칙은 사실상 전부 허용과 같다.
- 여러 단계는 계획으로 묶어 한 번에 승인받는다.
- 위험한 행동은 낮춰서 승인 자체를 없앤다.
- 남은 것 중 규칙으로 판정할 수 있는 것은 1절의 판정 함수로 자동 처리한다.

남는 승인은 정말 사람이 봐야 하는 것만이어야 합니다. 예시의 에이전트라면 하루 수십 건이던 지급 승인이, 정상 계좌의 한도 이하 지급을 자동 처리하고 계좌 변경을 요청서로 낮춘 뒤에는 한도 초과와 명의 불일치 건 몇 개로 줄어드는 그림을 기대할 수 있습니다.

### 자동 판단에 넘길 때의 경계

승인을 분류기 같은 자동 판단에 넘기는 방법도 있습니다. Claude Code의 auto mode가 그 예입니다. 권한 요청 대신 tool 호출마다 분류기를 거치게 하고, 분류기는 되돌릴 수 없거나 파괴적이거나 작업 환경 밖을 향하는 동작을 막는 데 초점을 둡니다. 앞의 통제 실험에서 같은 위험 명령을 사람은 13.6% 걸렀고 auto mode는 89% 막았습니다. [\[Claude: Auto mode is now the default in Claude Code\]](https://claude.com/resources/articles/auto-mode-default-in-claude-code)

하지만 같은 회사의 기술 글은 한계도 분명히 적습니다. 실제 과잉 행동 52건으로 만든 데이터에서 전체 파이프라인의 미탐률은 17%였고, 이것이 받아들일 만한지는 무엇과 비교하느냐에 달려 있으며, 위험도가 높은 인프라 작업에서 신중한 사람의 검토를 그대로 대체하는 것은 아니라고 적습니다. 기본 설정에서 분류기가 신뢰하는 것은 지금 작업 중인 git 저장소뿐이라는 점도 밝힙니다. [\[Anthropic: How we built Claude Code auto mode\]](https://www.anthropic.com/research/claude-code-auto-mode)

그래서 누가 승인할지를 칸별로 나누는 편이 맞다고 봅니다.

| 칸 | 판정 주체 | 예시 에이전트에서 |
| --- | --- | --- |
| 되돌림 가능, 작업 공간 안 | 규칙 (묻지 않음) | 조회, 서류 요약 |
| 되돌림 가능, 작업 공간 밖 | 규칙 또는 분류기 | 청구 건 메모 |
| 되돌림 불가, 한 건, 한도 이하 | 판정 함수 또는 분류기, 이상 시 사람 | 정상 계좌 소액 지급 |
| 되돌림 불가, 한도 초과 | 사람 | 전결 한도 초과 지급 |
| 돈의 흐름이나 공용 자원을 바꿈 | 사람 2인 | 수령 계좌 변경, 명의 불일치 지급 |

자동 판단은 사람이 어차피 읽지 않던 승인을 대신하는 용도이고, 되돌릴 수 없고 영향 범위가 큰 칸은 사람에게 남겨야 한다고 봅니다.

### 실패 모드와 비용

- 자동 판단을 넣으면 사람이 그 결과를 다시 믿기 시작합니다. 이것도 automation bias입니다. 자동 판단이 통과시킨 건 중 일부를 표본으로 사람이 다시 보는 절차를 두는 편이 낫습니다.
- 분류기는 호출마다 토큰과 지연을 더합니다. 같은 자료는 분류기가 tool 호출마다 소량의 추가 토큰을 쓴다고 밝힙니다.
- 승인 수를 줄이는 과정에서 위험한 칸까지 규칙으로 열어 버리는 실수가 생깁니다. 허용 규칙을 추가할 때마다 그 규칙이 어느 칸을 여는지 표에 대조하는 리뷰를 두는 편이 안전합니다.

## 5. 멈춤과 재개는 상태 저장 문제이고, 결정은 기록으로 남긴다

실무에서 승인은 몇 초 만에 오지 않습니다. 담당자가 회의 중일 수도 있고, 2인 확인의 두 번째 사람이 다음 날 아침에 처리할 수도 있습니다. 에이전트 프로세스가 그동안 살아 있으리라고 기대하면 안 됩니다.

### interrupt와 resume의 동작

에이전트 프레임워크들은 이것을 interrupt와 resume으로 풉니다.

LangGraph에서는 노드 안에서 `interrupt()`를 호출하면 그 값이 호출자에게 전달되고, checkpointer가 그래프 상태를 저장한 채 무기한 기다립니다. 나중에 같은 `thread_id`로 재개 명령을 보내면 그 값이 `interrupt()`의 반환값이 됩니다. [\[LangGraph: Interrupts\]](https://web.archive.org/web/20260810094806/https://docs.langchain.com/oss/python/langgraph/interrupts)

OpenAI Agents SDK는 승인 대기 중인 tool 호출을 실행 결과의 interruption 목록으로 돌려줍니다. 이를 실행 상태 객체로 바꿔 승인이나 거절을 기록하고 재개합니다. 이 상태 객체는 문자열이나 JSON으로 직렬화해 데이터베이스나 큐에 저장했다가 나중에 복원하도록 설계되어 있고, 거절할 때 모델이 받을 메시지를 호출별로 지정할 수도 있습니다. [\[OpenAI Agents SDK: Human-in-the-loop\]](https://github.com/openai/openai-agents-python/blob/80e1baaefdfff291b3d7e55987219107c9736d80/docs/human_in_the_loop.md)

예시의 지급 건에 적용하면 흐름은 이렇습니다.

```text
[에이전트] process_payout 제안
     │
     ▼
[하네스] 게이트 판정 ── auto ──> 실행 + 기록
     │ human / two_person
     ▼
 상태 저장 (체크포인트, 실행 상태 직렬화)
     │
     ├──> 승인 요청 생성 (하네스가 원장에서 직접 채움) ──> 담당자 결재함
     │
     └──> 프로세스 종료 가능
                                │
                 담당자: 승인 / 금액 수정 / 거절 / 상위 결재 (몇 분 ~ 며칠)
                                │
                                ▼
 상태 복원 ──> 대상 상태 재조회 ──> 결정 기록 ──> 승인: 실행 / 거절: 사유를 모델에 전달
```

"대상 상태 재조회"는 제가 넣은 단계입니다. 승인을 기다리는 동안 청구 건이 취소되거나 계좌가 다시 바뀌었을 수 있으니, 실행 직전에 원장을 다시 읽어 승인 요청을 만들 때의 값과 같은지 확인하는 편이 안전하다고 봅니다.

### 재개의 함정

여기에 함정이 하나 있습니다. LangGraph 문서에 따르면 재개할 때 노드는 interrupt 지점이 아니라 노드의 처음부터 다시 실행됩니다. interrupt 앞의 코드가 다시 돈다는 뜻이고, 그래서 interrupt 앞에 있는 부수 효과는 멱등해야 합니다. 문서는 부수 효과를 interrupt 뒤에 두거나 별도 노드로 분리하라고 권합니다. [\[LangGraph: Interrupts\]](https://web.archive.org/web/20260810094806/https://docs.langchain.com/oss/python/langgraph/interrupts)

예시라면 승인 요청을 만드는 노드 안에서 "고객에게 심사 중 안내 메일 발송"을 interrupt 앞에 두면, 재개할 때마다 고객이 같은 메일을 또 받습니다. 메일 발송은 별도 노드로 빼고, 지급 실행은 interrupt 뒤에 두고, 지급 tool에는 청구 건 ID로 만든 멱등 키를 붙여야 합니다.

### 결정 기록은 부산물이 아니라 산출물이다

결정 기록은 이 흐름의 부산물이 아니라 산출물입니다. NIST 프로파일은 측정 단계의 권장 조치로, 사람 운영자나 다른 시스템이 생성형 AI의 결정을 override한 사례를 모니터링하고 문서화하라고 제시합니다. [\[NIST AI 600-1: Generative AI Profile\]](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

기록에 남길 항목은 이 정도라고 봅니다. 아래는 제가 만든 예시입니다.

```yaml
# 예시: 승인 결정 기록 한 건
decision_id: DEC-2026-08-17-00412
claim_id: CLM-2026-081734
tool_call_id: call_7f3a
gate_result: two_person            # 판정 함수의 결과와 근거
gate_reasons: [account_changed_24h, holder_mismatch]
request_snapshot_ref: audit://approval/DEC-2026-08-17-00412.json   # 사람이 실제로 본 그대로
deciders:
  - { role: 지급담당, decision: escalate, at: "2026-08-17T14:41:05+09:00" }
  - { role: 지급팀장, decision: reject, reason: "계좌 명의 확인 필요", at: "2026-08-17T16:12:30+09:00" }
time_to_decision_sec: 5485
scope: this_call_only
executed: false
```

`request_snapshot_ref`가 가리키는 것은 승인 요청의 원문입니다. 나중에 "담당자가 그때 무엇을 보고 승인했는가"를 묻는다면, 지금 시점의 데이터가 아니라 그 시점에 화면에 있던 내용을 보여 줘야 하기 때문입니다.

걸린 시간은 품질 지표로도 쓸 수 있습니다. 긴 승인 요청이 1초 만에 승인되는 일이 잦다면 게이트가 형식이 되었다는 신호입니다. 승인율이 100%에 가까운 게이트도 같은 신호입니다.

### 보험과 금융 조직에서는

보험이나 금융 조직에는 이미 결재선과 전결 규정이 있습니다. 금액과 위험도에 따라 누가 승인하는지가 정해져 있고, 그 기록이 감사 대상입니다.

에이전트의 승인 게이트를 별도 체계로 새로 만들기보다, 에이전트가 기존 결재 요청서를 올리는 주체가 되게 하는 편이 맞다고 봅니다. 1절의 판정 함수가 쓰는 한도는 전결 규정의 한도를 그대로 쓰고, 3절의 요청서는 기존 결재 시스템으로 들어가고, 5절의 기록은 기존 감사 로그에 남습니다. 그러면 감사인에게 설명할 체계가 하나 늘지 않습니다.

### 실패 모드와 비용

- 체크포인트 저장소가 운영 데이터베이스와 다른 보관 규정을 따르면, 승인 대기 중인 상태에 들어 있는 고객 정보가 규정 밖에 남습니다. OpenAI SDK 문서도 직렬화된 상태에 앱 문맥과 tool 입력이 들어간다는 점을 밝히고 있습니다.
- 승인 대기 건이 쌓이면 에이전트 처리량이 사람의 처리 속도에 묶입니다. 대기 시간 상한과 상한 초과 시의 처리, 예를 들어 자동 거절과 고객 안내를 정해 두어야 합니다.
- 기록 항목을 늘리면 저장 비용이 늘지만, 돈이 오가는 tool의 결정 기록은 줄일 대상이 아니라고 봅니다.

## 6. 오늘 바로 적용할 수 있는 순서

1. 에이전트가 가진 tool을 전부 나열하고, 이름이 아니라 그 동작이 이후 무엇을 바꾸는지를 기준으로 되돌림 가능성과 영향 범위의 네 칸에 나눕니다.
2. 되돌릴 수 없는 칸의 tool마다 초안, 미리보기, 요청서로 낮출 수 있는지 먼저 검토하고, 낮출 수 있으면 실행 tool을 목록에서 뺍니다.
3. 남은 게이트에 인자 기반 판정 함수를 붙입니다. 판정 근거는 모델의 인자가 아니라 원장과 규정에서 다시 읽습니다.
4. 승인 요청 화면을 다시 만듭니다. 대상, 변경 내용, 되돌림 여부, 평소와 다른 점, 관련 동작을 하네스가 직접 채우고, 수정과 상위 결재 선택지를 넣습니다.
5. 승인 대기 중에 프로세스를 죽였다가 재개해 보고, 중복 실행되는 부수 효과가 없는지 확인합니다. 결정 로그를 남기고 승인율과 결정까지 걸린 시간을 주기적으로 봅니다.

## 마치며

Human-in-the-loop는 사람을 끼워 넣는 것으로 끝나지 않습니다. 사람이 판단할 수 있는 정보와 단위로 요청이 도착해야 하고, 그 요청의 수가 읽을 수 있을 만큼 적어야 하고, 기다리는 동안 시스템이 안전하게 멈춰 있어야 합니다. 그러려면 게이트를 고르는 기준, 요청의 내용, 행동을 낮추는 방법, 멈춤과 재개, 기록이 함께 설계되어야 합니다. 승인율이 100%에 가깝다면 안전하다는 뜻이 아니라 게이트를 다시 봐야 한다는 신호일 수 있습니다.
