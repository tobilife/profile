:::note
- 에이전트 eval의 채점 대상은 마지막 답변이 아니라 환경에 남은 결과(outcome)입니다. "접수되었습니다"라는 문장과 DB의 접수 레코드는 다른 것입니다.
- 한 번 돌려서 통과했다는 사실은 정보가 적습니다. 같은 task를 여러 번(trial) 깨끗한 환경에서 돌리고, "한 번이라도 성공"(pass@k)과 "매번 성공"(pass^k)을 구분해서 봐야 합니다.
- grader는 코드, 모델, 사람 세 종류이고 쓰는 순서가 있습니다. 코드로 되는 것은 코드로, 안 되는 것만 모델로, 사람은 보정용으로 씁니다.
- capability suite와 regression suite는 목표 통과율이 다릅니다. 그리고 어떤 숫자든 transcript를 읽어 grader의 실수를 걸러 내기 전까지는 믿지 않습니다.
:::

모델을 평가해 본 팀은 에이전트 평가도 비슷할 것이라고 생각하기 쉽습니다. 질문 목록을 만들고, 답을 받고, 정답과 비교하면 된다는 생각입니다.

하지만 **에이전트는 답을 내는 시스템이 아니라 환경의 상태를 바꾸는 시스템이고, 그래서 채점할 대상이 달라집니다.**

Anthropic은 2026년 1월 9일에 공개한 글에서 에이전트가 여러 턴에 걸쳐 도구를 쓰고 환경의 상태를 바꾸며 적응하기 때문에, 실수가 전파되고 누적될 수 있다고 설명합니다. [\[Anthropic: Demystifying evals for AI agents\]](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

OpenAI의 평가 가이드는 같은 이야기를 다른 각도에서 합니다. 시스템에서 비결정성이 들어오는 지점을 찾고 거기에 eval을 두라는 것입니다. 단일 턴, 워크플로, 단일 에이전트, 멀티 에이전트로 갈수록 그 지점이 늘어납니다. [\[OpenAI: Evaluation best practices\]](https://web.archive.org/web/20251216184720/https://platform.openai.com/docs/guides/evaluation-best-practices)

이 글은 에이전트 eval을 구성하는 단위를 하나씩 정의하고, 하나의 예를 끝까지 따라가며 각 단위가 실제로 어떻게 돌아가는지, 어디서 숫자가 거짓말을 하는지 정리합니다.

## 먼저, 이런 상황부터 봅시다

예를 들어 보험사의 보험금 청구 접수 에이전트를 만들었다고 해봅시다. 고객이 앱 채팅으로 입원 보험금을 청구하면, 에이전트가 계약을 조회하고, 업로드된 진단서와 영수증을 확인하고, 접수 API를 호출해 청구 건을 만든 뒤 접수 번호를 안내합니다. 이 글은 끝까지 이 에이전트를 예로 씁니다.

팀은 테스트 질문 30개로 답변 품질을 채점했습니다. 채점은 "최종 답변에 접수 완료 안내와 접수 번호 형식의 문자열이 들어 있는가"를 LLM에게 묻는 방식입니다. 통과율은 93%였습니다.

배포 후 이런 대화가 발생합니다.

```text
고객: 지난주 입원 건 보험금 청구하려고요. 서류는 올렸어요.

에이전트: (계약 조회 도구 호출 -> 성공)
에이전트: (서류 확인 도구 호출 -> 진단서, 영수증 확인)
에이전트: (청구 접수 도구 호출 -> 타임아웃 오류)
에이전트: 청구가 접수되었습니다. 접수 번호는 CLM-2026-00418 이며,
          심사 결과는 영업일 기준 3일 안에 안내드립니다.
```

답변은 정중하고 형식도 완벽합니다. eval 기준으로는 통과입니다. 그런데 청구 테이블에는 그 접수 번호가 없습니다. 에이전트가 앞선 대화의 형식을 흉내 내 번호를 지어냈기 때문입니다.

Anthropic 글은 정확히 이 구분을 용어로 나눕니다. transcript는 한 번의 실행에서 일어난 모든 것의 기록이고, outcome은 실행이 끝났을 때 환경에 남은 최종 상태입니다. 항공권 예약 에이전트가 transcript 끝에 "예약되었습니다"라고 말하는 것과, 환경의 SQL 데이터베이스에 예약이 존재하는 것은 별개라는 예시가 나옵니다.

위 사례에서 잘못된 것은 모델만이 아니라 eval 설계입니다. **채점기가 outcome이 아니라 문장을 보고 있었고, 도구가 실패하는 상황을 한 번도 만들어 보지 않았습니다.**

## 1. 평가 단위부터 다시 정의한다: task, trial, transcript, outcome

### 단위가 한 층에서 여러 층으로 늘어난다

단일 턴 평가의 단위는 (입력, 출력) 한 쌍입니다. 에이전트 평가는 단위가 여러 층입니다. Anthropic 글의 정의를 표로 옮기면 이렇습니다.

| 용어 | 뜻 | 단일 턴 평가에서의 대응물 |
| --- | --- | --- |
| task | 입력과 성공 기준이 정해진 테스트 하나 | 질문 하나 |
| trial | task를 한 번 시도한 것 | 없음 (보통 1회로 가정) |
| grader | 성능의 한 측면을 점수화하는 로직. task 하나에 여러 개, grader 하나에 여러 assertion | 정답 비교 |
| transcript | trial의 전체 기록 (출력, 도구 호출, 추론, 중간 결과) | 출력 텍스트 |
| outcome | trial이 끝난 뒤 환경의 최종 상태 | 없음 |
| evaluation harness | 지시와 도구를 주고, task를 동시에 돌리고, 모든 단계를 기록하고, 채점하고, 집계하는 인프라 | 채점 스크립트 |
| agent harness | 모델이 에이전트로 동작하게 하는 시스템. 이것을 평가하는 것 | 없음 |

표에서 "없음"인 줄들이 에이전트 eval의 본체라고 봅니다. 특히 마지막 두 줄을 구분하는 것이 중요합니다. 평가 대상은 모델 하나가 아니라 모델과 agent harness의 조합이고, 그것을 evaluation harness가 돌립니다. Anthropic 글도 eval 속 에이전트가 운영 환경의 에이전트와 대체로 같게 동작해야 한다고 강조합니다.

### 한 번의 eval 실행은 이렇게 돈다

청구 접수 에이전트의 task 하나를 evaluation harness가 처리하는 순서를 따라가 봅니다.

```text
[evaluation harness]
  |
  +-- 1. task 로드: 입력, 초기 상태, 주입할 장애, grader 목록
  |
  +-- 2. 환경 초기화: 테스트 DB 를 스냅샷으로 되돌림, 작업 디렉터리 새로 만듦
  |                 접수 API 대역에 "첫 호출 타임아웃" 장애 설정
  |
  +-- 3. agent harness 실행 (운영과 같은 프롬프트, 도구, 설정)
  |        고객 역할은 스크립트 또는 사용자 시뮬레이터 모델이 맡음
  |
  +-- 4. transcript 기록: 모든 메시지, 도구 호출과 인자, 도구 응답, 오류
  |
  +-- 5. outcome 수집: 청구 테이블, 서류 테이블, 발송 알림 큐의 최종 상태
  |
  +-- 6. grader 실행: outcome 검사 -> transcript 검사 -> 모델 루브릭
  |
  +-- 7. trial 결과 저장 후 2번으로 돌아가 k 번 반복 -> pass@k, pass^k 집계
```

2번과 5번이 단일 턴 평가에는 없던 단계입니다. 그리고 이 두 단계가 eval 도입 비용의 대부분을 차지합니다.

### 비결정성이 들어오는 지점마다 eval을 둔다

OpenAI 가이드는 아키텍처를 네 가지로 나누고, 각 구조에서 비결정성이 어디로 들어오는지 설명합니다. 워크플로는 여러 모델 호출을 이어 붙일 뿐 새로운 종류의 비결정성을 더하지 않으므로 각 호출을 따로 평가할 수 있고, 단일 에이전트는 도구 선택과 도구 인자 추출이, 멀티 에이전트는 에이전트 사이의 분류와 handoff가 새로운 비결정성의 원천이 된다는 것입니다.

청구 접수 에이전트에 대응시키면 eval을 둘 지점이 이렇게 정리됩니다.

| 구조의 층 | 비결정성이 들어오는 곳 | 청구 접수 에이전트에서의 eval |
| --- | --- | --- |
| 단일 모델 호출 | 의도 분류, 응답 생성 | 고객 발화가 청구, 조회, 해지 중 무엇인지 맞게 분류하는가 |
| 워크플로 | 각 호출의 출력이 다음 호출의 입력이 됨 | 서류 확인 단계의 출력이 접수 단계에 그대로 전달되는가 |
| 단일 에이전트 | 도구 선택, 인자 추출 | 계약 번호와 입원일을 대화에서 정확히 뽑아 접수 도구에 넣는가 |
| 멀티 에이전트 | 분류와 handoff | 서류 검증 에이전트로 넘길 때 필요한 맥락이 빠지지 않는가 |

위 층의 eval은 빠르고 싸며 원인을 좁혀 주고, 아래 층의 eval은 느리고 비싸지만 실제 결과를 봅니다. 저는 outcome을 보는 끝에서 끝까지의 task를 기준으로 삼고, 위 층의 eval은 실패 원인을 찾을 때 쓰는 진단용 묶음으로 두는 편을 권합니다.

### trial: 한 번 통과는 증거가 약하다

모델 출력은 실행마다 달라집니다. 그래서 같은 task를 여러 번 돌려야 합니다.

여러 번 돌리면 숫자를 읽는 법도 두 가지가 됩니다. Anthropic 글은 pass@k와 pass^k를 구분합니다. pass@k는 k번 중 한 번이라도 성공할 확률이고, pass^k는 k번 모두 성공할 확률입니다.

글에 나온 계산이 직관적입니다. trial당 성공률이 75%인 에이전트를 3번 돌려 모두 성공할 확률은 0.75의 세제곱, 약 42%입니다. k=1에서는 두 지표가 같지만, k=10쯤 가면 pass@k는 100%에 가까워지고 pass^k는 0%로 떨어져 정반대의 이야기를 한다고 설명합니다.

pass^k는 원래 τ-bench 논문이 에이전트 행동의 신뢰성을 재려고 제안한 지표입니다. 이 논문은 언어 모델이 흉내 내는 사용자와 도메인 도구·정책을 가진 에이전트의 대화를 만들고, 대화가 끝난 시점의 데이터베이스 상태를 주석으로 단 목표 상태와 비교하는 방식으로 채점합니다. 논문은 당시 최고 수준의 함수 호출 에이전트도 과제의 절반을 넘기지 못했고, 소매 도메인에서 pass^8이 25% 미만이었다고 보고합니다. [\[τ-bench 논문\]](https://arxiv.org/abs/2406.12045)

어느 쪽을 볼지는 제품이 정합니다.

| 제품의 성격 | 볼 지표 | 이유 |
| --- | --- | --- |
| 여러 후보 중 하나만 맞으면 되는 도구 (코드 제안, 검색 후보) | pass@k | 사람이 후보 중에서 고른다 |
| 고객이 매번 같은 결과를 기대하는 에이전트 (청구 접수, 환불, 계약 변경) | pass^k | 한 번의 실패가 곧 한 고객의 사고다 |
| 내부 사용자가 결과를 확인하고 다시 시킬 수 있는 보조 도구 | pass@1과 실패 유형 | 재시도 비용과 실패의 성격이 더 중요하다 |

청구 접수처럼 "가끔 실패"가 곧 민원이 되는 업무는 pass^k로 봐야 한다고 생각합니다.

### 환경: trial마다 깨끗하게 시작한다

상태를 바꾸는 시스템을 평가하려면 상태를 초기화할 수 있어야 합니다.

Anthropic 글은 trial 간에 공유된 상태(남은 파일, 캐시, 자원 고갈)가 에이전트 성능이 아니라 인프라 문제로 인한 상관된 실패를 만들거나 점수를 부풀릴 수 있다고 지적합니다. 내부 eval에서 Claude가 이전 trial의 git 기록을 살펴보고 부당한 이점을 얻은 사례도 언급합니다. 여러 trial이 CPU 메모리 부족처럼 같은 환경 제약 때문에 실패했다면, 그 trial들은 서로 독립이 아니므로 결과를 믿을 수 없다는 설명도 있습니다.

청구 접수 에이전트라면 초기화 대상은 세 가지입니다.

- 테스트 DB: 계약, 서류, 청구 테이블을 task가 정한 스냅샷으로 되돌립니다.
- 외부 시스템 대역: 접수 API, 알림 발송을 대역으로 바꾸고, task마다 정상 응답, 타임아웃, 중복 오류 같은 장애를 주입합니다.
- 에이전트 상태: 메모리나 이전 대화 요약을 쓰는 구조라면 trial마다 비웁니다.

### 실패 모드와 비용

실무적으로는 이 조건이 eval 도입의 가장 큰 비용입니다. 테스트용 DB 스냅샷, 격리된 작업 디렉터리, 외부 API의 대역이 먼저 있어야 합니다. 보험사의 기간계처럼 테스트 환경 하나를 띄우는 데도 결재가 필요한 곳이라면, 기간계 전체가 아니라 에이전트가 호출하는 API 경계에서 대역을 세우는 편이 현실적이라고 봅니다.

trial 횟수도 비용입니다. task 50개에 trial 5회면 에이전트 실행이 250번이고, 각 실행이 도구 호출 열 번을 한다면 모델 호출은 그보다 훨씬 많습니다. 그래서 저는 변경마다 돌리는 빠른 묶음(trial 1~2회)과 배포 전에 돌리는 전체 묶음(trial 5회 이상)을 나누는 편을 권합니다.

## 2. grader는 세 종류이고, 쓰는 순서가 있다

### 세 종류의 강점과 약점

Anthropic 글은 grader를 코드 기반, 모델 기반, 사람으로 나누고, 각 grader가 transcript나 outcome의 일부를 평가한다고 설명합니다.

| grader | 방법의 예 | 강점 | 약점 |
| --- | --- | --- | --- |
| 코드 기반 | 문자열·정규식 검사, 통과/실패 테스트, 정적 분석, outcome 검증, 도구 호출 검증, transcript 분석(턴 수, 토큰) | 빠르고 저렴, 객관적, 재현 가능, 디버깅 쉬움 | 유효한 변형에 취약, 뉘앙스 부족 |
| 모델 기반 | 루브릭 채점, 자연어 단언, 쌍대 비교, 참조 기반 평가, 다중 judge 합의 | 뉘앙스, 열린 과제와 자유 형식 출력 처리 | 비결정적, 코드보다 비쌈, 사람과의 보정 필요 |
| 사람 | 전문가 검토, 표본 점검, A/B 테스트, 평가자 간 일치도 | 기준점 품질, 모델 grader 보정에 사용 | 느리고 비쌈, 전문가 확보가 어려움 |

권고는 명확합니다. 가능한 곳은 결정적 grader, 필요한 곳은 LLM grader, 사람은 검증용으로 신중하게 쓰라는 것입니다.

task 점수를 합치는 방식도 정해야 합니다. 같은 글은 가중합이 기준을 넘어야 하는 방식, 모든 grader를 통과해야 하는 이진 방식, 그 혼합을 예로 듭니다. 여러 단계로 이루어진 과제에는 부분 점수를 두라고도 권합니다. 문제를 파악하고 고객 확인까지 했지만 환불을 처리하지 못한 지원 에이전트는, 바로 실패한 에이전트보다 의미 있게 낫다는 설명입니다.

### 청구 접수 task 하나에 grader를 여러 개 붙인다

앞의 사례에 적용하면 task 하나에 grader를 여러 개 붙이게 됩니다. 아래는 그 구성을 보여 주는 예시입니다.

```yaml
# 예시: task 정의 하나
id: claim-intake-timeout-001
input: "지난주 입원 건 보험금 청구하려고요. 서류는 올렸어요."
setup:
  db_snapshot: policy_active_with_uploaded_docs
  fault: claim_api_timeout_once        # 접수 API 가 첫 호출에서 타임아웃
  user_simulator: scripted              # 고객 발화는 스크립트로 고정
trials: 5
graders:
  - type: code                          # outcome: 접수가 실제로 생겼는가
    check: "claims 테이블에 policy_id 로 1건, status=RECEIVED, 서류 2건 연결"
  - type: code                          # outcome: 중복 접수가 없는가
    check: "같은 policy_id, 같은 입원일로 claims 2건 이상 없음"
  - type: code                          # 금지 행동: 근거 없는 완료 안내
    check: "접수 도구 성공 응답 없이 '접수되었습니다' 문장 또는 CLM- 번호 출력 없음"
  - type: code                          # 규정된 순서: 본인 확인 전 계약 조회 금지
    check: "verify_identity 성공 이전에 get_policy 호출 없음"
  - type: model                         # 안내 품질
    rubric: "재시도 중이거나 실패했을 때 사실대로 알리고 다음 단계를 안내했는가. 판단 근거가 부족하면 Unknown"
scoring: "code grader 전부 통과 필수, model grader 는 기록만"
pass_criteria: "5회 중 5회 (pass^5)"
```

코드 grader가 네 개, 모델 grader가 하나입니다. 앞의 사례에서 문제가 된 "지어낸 접수 번호"는 세 번째 코드 grader가 잡고, 타임아웃 뒤 재시도로 생길 수 있는 중복 접수는 두 번째가 잡습니다. 모델 grader는 말투와 안내의 질만 봅니다.

### 모델 grader는 보정해서 쓴다

모델 기반 grader의 루브릭에 "판단 근거가 부족하면 Unknown"을 넣은 것은 Anthropic 글의 조언을 따른 것입니다. 정보가 부족할 때 빠져나갈 길을 주어야 채점 모델이 판정을 지어내지 않는다는 설명입니다.

같은 글은 두 가지를 더 권합니다. 과제의 각 차원을 구조화된 루브릭으로 나누고 차원마다 격리된 LLM judge로 채점하라는 것, 그리고 LLM judge를 사람 전문가와 면밀히 보정해 둘 사이의 차이가 작다는 확신을 얻으라는 것입니다. 시스템이 안정되면 사람 검토는 가끔만 해도 충분하다고 합니다.

보정을 실제로 하는 방법은 단순하다고 봅니다. 청구 접수 transcript 50건을 뽑아 심사 실무자 두 명과 LLM judge가 같은 루브릭으로 채점하고, 사람끼리의 일치율과 사람과 judge의 일치율을 비교합니다. 사람끼리도 자주 갈리는 항목이라면 루브릭이 모호한 것이고, 사람끼리는 맞는데 judge만 다르다면 judge 프롬프트를 고칠 차례입니다.

### 경로를 채점할 것인가, 결과를 채점할 것인가

여기서 두 자료의 강조점이 조금 다릅니다.

Anthropic 글은 도구 호출 순서처럼 특정 단계를 따랐는지 검사하는 방식이 지나치게 경직되어 깨지기 쉬운 테스트가 된다고 말합니다. 에이전트가 설계자가 예상하지 못한 유효한 방법을 자주 찾기 때문입니다. 그래서 경로가 아니라 산출물을 채점하는 편이 대개 낫다고 권합니다.

OpenAI 가이드는 단일 에이전트 구조에서 에이전트가 맞는 도구를 고르는지(tool selection), 대화에서 뽑아낸 인자로 도구를 정확히 호출하는지(data precision)를 평가 항목으로 제시합니다.

저는 둘이 충돌한다고 보지 않습니다. 기준은 "그 경로가 요구사항인가"입니다.

- 성공 여부는 outcome으로 채점합니다.
- "본인 확인 전에는 계약 정보를 조회하지 않는다"처럼 순서 자체가 규정인 것만 transcript에서 검사합니다. 위 예시의 네 번째 grader가 이것입니다.
- 나머지 경로 정보는 채점이 아니라 진단에 씁니다. 도구 인자 정확도가 떨어졌다면 outcome 실패의 원인을 찾는 단서로 씁니다.

### 대화형 에이전트는 사용자도 흉내 내야 한다

청구 접수 에이전트는 대화형 에이전트입니다. Anthropic 글은 대화형 에이전트 eval이 대부분 두 번째 LLM으로 사용자를 흉내 내야 한다는 점에서 다른 eval과 다르다고 설명합니다. 성공도 여러 차원이라고 합니다. 티켓이 해결되었는가(상태 검사), 10턴 안에 끝났는가(transcript 제약), 말투가 적절했는가(LLM 루브릭)를 함께 본다는 예입니다.

같은 글이 언급하는 τ2-bench는 τ-bench의 후속으로, 사용자가 수동적인 정보 제공자에 머물지 않고 에이전트와 함께 도구를 써서 공유 환경의 상태를 바꾸는 이중 제어 환경을 다룹니다. 기술 지원처럼 고객이 직접 무언가를 해야 하는 상황을 평가하려는 것입니다. [\[τ²-bench 논문\]](https://arxiv.org/abs/2506.07982)

청구 접수에서도 고객이 서류를 다시 올려야 하는 경우가 이에 해당합니다. 이런 task는 사용자 시뮬레이터에 "요청받으면 서류를 다시 업로드한다"는 도구를 주고, 재업로드 후의 서류 테이블을 outcome으로 채점합니다.

다만 사용자 시뮬레이터도 모델이므로 비결정성이 하나 더 들어옵니다. 저는 처음에는 고객 발화를 스크립트로 고정한 task로 시작하고, 에이전트 쪽 실패가 충분히 줄어든 뒤에 시뮬레이터 task를 늘리는 편을 권합니다. 실패 원인이 에이전트인지 시뮬레이터인지 가르기 쉬워지기 때문입니다.

### 실패 모드와 비용

grader 쪽의 대표적인 실패는 세 가지라고 봅니다. 코드 grader가 너무 좁아 유효한 답을 떨어뜨리는 것, 모델 grader가 보정 없이 쓰여 점수가 흔들리는 것, 그리고 grader 자체의 버그입니다. Anthropic 글은 마지막 경우를 직접 경고합니다. 채점 버그나 agent harness의 제약 때문에 에이전트가 잘하고도 낮은 점수를 받는 미묘한 실패가 있다는 것입니다.

비용 면에서는 모델 grader가 trial 수만큼 곱해진다는 점을 기억해야 합니다. 차원마다 judge를 따로 쓰면 더 늘어납니다. 그래서 코드로 판정되는 차원은 반드시 코드로 빼고, 모델 grader는 정말 뉘앙스가 필요한 차원에만 남기는 순서가 비용 면에서도 맞습니다.

## 3. suite는 둘로 나눈다: capability는 오르고, regression은 지킨다

### 두 suite는 묻는 질문이 다르다

Anthropic 글은 eval suite를 두 종류로 구분합니다.

capability eval은 "이 에이전트가 무엇을 잘할 수 있는가"를 묻습니다. 낮은 통과율에서 시작해 팀이 올라갈 언덕을 제공합니다.

regression eval은 "예전에 다루던 과제를 여전히 다루는가"를 묻습니다. 통과율이 100%에 가까워야 하고, 떨어지면 무언가 망가졌다는 신호입니다.

출시와 최적화를 거쳐 통과율이 높아진 capability eval은 regression suite로 "졸업"시켜 계속 돌린다고 합니다. "이걸 할 수 있는가"를 재던 task가 "이걸 여전히 안정적으로 하는가"를 재게 되는 것입니다.

```text
실제 실패 사례 (버그 트래커, 상담 이관 기록)
     |
     v
[capability suite]  낮은 통과율에서 시작, 개선 목표
     |  (pass^k 가 안정적으로 높아짐)
     v
[regression suite]  100% 근처 유지, 프롬프트·모델·도구 변경마다 실행
     |  (통과율 하락)
     v
  변경 차단 또는 조사 -> 원인이 새 실패 유형이면 capability suite 에 task 추가
```

이 구분이 없으면 한 숫자가 두 가지 뜻을 갖게 됩니다. 통과율 70%가 "어려운 문제를 풀어 가는 중"인지 "되던 것이 깨졌다"인지 알 수 없습니다.

### 포화와 0%는 둘 다 신호다

같은 글은 포화도 경고합니다. 100%인 eval은 회귀는 잡지만 개선 신호는 주지 않습니다. SWE-bench Verified 점수가 30%에서 시작해 최신 모델이 80%를 넘으며 포화에 가까워졌다는 예와 함께, 포화에 가까워질수록 큰 능력 향상이 작은 점수 변화로 보여 결과가 기만적일 수 있다고 설명합니다.

반대쪽 끝도 신호입니다. 여러 번 돌려도 통과율이 0%인 task, 즉 pass@100이 0%인 task는 최신 모델에서는 에이전트가 무능해서가 아니라 task나 grader가 깨졌다는 신호인 경우가 대부분이라고 합니다. Terminal-Bench를 감사해 보니 스크립트를 쓰라고 하면서 경로를 지정하지 않았는데 테스트는 특정 경로를 가정한 task가 있었다는 예도 나옵니다. grader가 검사하는 모든 것은 task 설명에서 분명해야 한다는 것이 교훈입니다.

청구 접수 예에서 비슷한 함정은 이런 것입니다. task가 "청구를 접수하라"고만 하고, grader는 청구 유형 코드가 "입원"이어야 한다고 검사합니다. 고객 발화에 입원이라는 말이 없다면 에이전트는 실패할 수밖에 없습니다.

### 해야 하는 경우와 하지 말아야 하는 경우를 함께 넣는다

Anthropic 글은 한쪽만 테스트하면 한쪽으로만 최적화된다고 경고합니다. 검색해야 할 때 검색하는지만 테스트하면 거의 모든 것을 검색하는 에이전트가 될 수 있다는 예를 들고, Claude.ai의 웹 검색 eval을 만들 때 검색해야 하는 질의와 하지 말아야 하는 질의를 모두 넣었다고 설명합니다.

청구 접수 에이전트라면 "접수해야 하는 경우"만큼 "접수하면 안 되는 경우"가 중요합니다. 실효된 계약, 서류가 빠진 청구, 본인 확인 실패, 같은 건의 중복 청구가 그렇습니다.

### 새 task를 어디에 넣을지 고른다

| task의 출처 | 넣을 suite | 통과 기준 |
| --- | --- | --- |
| 운영에서 발견된 새 실패 유형 | capability | 처음엔 낮아도 됨, 추세를 본다 |
| 이미 해결해 안정적으로 통과하는 실패 유형 | regression | pass^k 100% 근처 |
| 규정 위반 (본인 확인 전 조회, 근거 없는 완료 안내) | regression, 처음부터 | 1회라도 실패하면 배포 차단 |
| 하지 말아야 하는 경우 (실효 계약, 중복 청구) | 둘 다 | 해야 하는 경우와 비슷한 비율로 |
| 사용자 시뮬레이터가 필요한 긴 대화 | capability | 실패 원인 분류가 끝난 뒤 regression으로 |

세 번째 줄은 제 의견입니다. 규정 위반은 "개선해 나갈 능력"이 아니라 처음부터 지켜야 하는 선이므로, capability suite를 거치지 않고 바로 regression suite에 넣는 편이 맞다고 봅니다.

### eval이 없을 때 팀이 겪는 일

Anthropic 글은 eval 없이 개발하는 방식이 초기 프로토타입 단계를 지나 운영과 확장 단계에 들어서면 무너지기 시작한다고 설명합니다. 전환점은 대개 사용자가 변경 이후 에이전트가 나빠졌다고 말하는데, 팀이 추측과 확인 외에는 검증할 방법이 없을 때라고 합니다. 그때의 디버깅은 반응형이 됩니다. 불만을 기다리고, 손으로 재현하고, 고치고, 다른 것이 망가지지 않았기를 바라는 순환입니다.

같은 글은 eval이 이른 시기에는 제품 팀이 에이전트의 성공이 무엇인지 정의하도록 강제하고, 나중에는 일관된 품질 기준을 지키게 한다고 말합니다. 예로 영상 편집 에이전트를 만든 Descript가 "망가뜨리지 않는다, 요청한 것을 한다, 잘한다"라는 세 차원으로 eval을 세우고, 손 채점에서 LLM grader로 옮겨 갔다고 소개합니다.

청구 접수 에이전트에 이 세 차원을 그대로 대입해 볼 수 있습니다. 망가뜨리지 않는다는 중복 접수나 잘못된 계약 연결이 없어야 한다는 regression 영역이고, 요청한 것을 한다는 접수가 실제로 생겼는가의 outcome 영역이며, 잘한다는 안내의 명확성과 말투 같은 모델 grader의 영역입니다. 세 차원이 각각 다른 suite와 grader 종류에 대응한다는 점이 이 구분의 쓸모라고 봅니다.

### 실패 모드: 숫자 하나로 보고하기

이 단계에서 흔한 실패는 두 suite를 합친 통과율 하나를 보고하는 것입니다. 그 숫자는 새 task를 추가할 때마다 떨어지므로, 팀은 어려운 task를 추가하지 않으려는 압력을 받게 됩니다. capability suite의 통과율은 낮아도 괜찮다는 합의가 먼저 있어야 eval이 개선 도구로 작동한다고 봅니다.

## 4. 점수를 믿기 전에 transcript를 읽는다

### 모델이 eval보다 나은 답을 찾을 때

eval도 코드이고, 코드에는 버그가 있습니다.

Anthropic 글이 드는 예가 흥미롭습니다. 항공권 예약을 다루는 τ2-bench 문제에서 Opus 4.5가 정책의 빈틈을 찾아 사용자에게 더 나은 해법을 냈는데, 작성된 기준대로는 "실패"로 채점되었다는 것입니다. 최신 모델이 정적인 eval의 한계를 넘는 창의적 해법을 찾을 수 있다는 사례로 소개됩니다.

그래서 이 글은 누군가 eval의 세부를 파고들어 transcript를 읽기 전까지는 점수를 액면 그대로 받아들이지 않는다는 원칙을 적습니다. 채점이 불공정하거나, task가 모호하거나, 유효한 해법이 감점되거나, harness가 모델을 제약한다면 eval을 고쳐야 한다는 것입니다. 실패가 공정해 보여야 한다는 표현도 씁니다. 에이전트가 무엇을 틀렸고 왜 틀렸는지가 분명해야 한다는 뜻입니다.

### task 품질의 기준과 참조 해법

task 품질의 기준도 제시합니다. 좋은 task는 도메인 전문가 두 명이 독립적으로 같은 합격 여부 판정에 도달하는 task입니다. 그리고 모든 grader를 통과하는 참조 해법을 하나 만들어 두면 task가 풀 수 있는 문제이고 grader가 제대로 설정되었음을 증명할 수 있다고 합니다.

청구 접수 예라면 참조 해법은 "사람 상담원이 같은 상황에서 했을 도구 호출 순서와 최종 DB 상태"입니다. 이것을 테스트 환경에서 한 번 재현해 모든 grader를 통과하는지 확인하면, grader의 버그 상당수가 에이전트를 돌리기 전에 드러납니다.

### transcript를 읽고 실패를 분류한다

transcript를 읽는 목적은 실패의 원인을 가르는 것입니다. 저는 아래 네 가지로 분류합니다.

| 분류 | 판단 기준 | 고칠 곳 |
| --- | --- | --- |
| 에이전트 실수 | task가 명확하고, 다른 해법도 없는데 틀렸다 | 프롬프트, 도구 설명, agent harness |
| grader 실수 | 에이전트의 결과가 유효한데 감점되었다 | grader 코드나 루브릭 |
| task 모호 | 전문가끼리도 판정이 갈린다, 필요한 정보가 task에 없다 | task 설명 |
| 환경 문제 | 타임아웃, 자원 부족, 이전 trial의 잔여 상태 | evaluation harness |

통과율은 이 분류가 끝난 뒤에 보고합니다. 첫 실행에서 실패의 상당수가 grader 실수나 환경 문제로 분류된다면, 그 eval의 숫자는 아직 에이전트에 대해 말하지 않는 것입니다.

### eval 하나로 모든 것을 잡을 수는 없다

Anthropic 글은 안전공학의 스위스 치즈 모델을 빌려 어떤 평가 층도 모든 문제를 잡지 못한다고 말합니다. 빠른 반복을 위한 자동 eval, 실제 상황을 보여 주는 운영 모니터링, 보정을 위한 주기적인 사람 검토를 함께 쓰는 팀이 가장 효과적이라는 것입니다.

운영 쪽에서는 OpenAI 문서가 워크플로 수준의 오류를 찾는 용도로 trace grading을 권합니다. [\[OpenAI: Agent evals\]](https://web.archive.org/web/20251226015100/https://platform.openai.com/docs/guides/agent-evals) trace grading은 결정, 도구 호출, 추론 단계를 담은 에이전트의 끝에서 끝까지의 기록에 구조화된 점수나 라벨을 붙여 어디서 잘했고 어디서 틀렸는지 찾는 과정이라고 설명합니다. [\[OpenAI: Trace grading\]](https://web.archive.org/web/20251221132607/https://platform.openai.com/docs/guides/trace-grading)

OpenAI 가이드에는 아키텍처 결정에 관한 조언도 있습니다. 멀티 에이전트 구조로 갈지는 eval이 결정해야 하고, 처음부터 멀티 에이전트로 시작하면 불필요한 복잡성이 생긴다는 것입니다. 청구 접수 에이전트를 접수, 서류 검증, 안내 에이전트로 나누고 싶어질 때, 단일 에이전트의 eval 결과에서 그 분리가 필요하다는 근거가 먼저 나와야 한다고 읽힙니다.

### 소유권과 보험·금융 조직에서의 쓸모

eval suite는 계속 관리해야 하는 산출물입니다. Anthropic 글은 전담 eval 팀이 핵심 인프라를 맡고, 도메인 전문가와 제품 팀이 task 대부분을 기여하고 직접 돌리는 방식이 가장 효과적이었다고 적습니다.

보험사라면 이 구조가 자연스럽다고 봅니다. evaluation harness는 개발 조직이 만들고, 청구 접수 task는 보상 실무자가 씁니다. "이 상황에서 접수하면 안 된다"를 가장 잘 아는 사람은 실무자이기 때문입니다.

판단 근거를 남겨야 하는 조직이라면 transcript는 이중으로 쓸모가 있다고 봅니다. eval을 위해 남긴 전체 실행 기록의 형식이 곧 운영 환경의 감사 추적 형식이 될 수 있습니다. 도구 호출, 인자, 응답, 최종 상태 변경이 같은 형식으로 남으면, eval에서 쓰던 grader 코드를 운영 기록에 그대로 돌려 표본 점검을 할 수 있습니다. eval용 로그와 운영용 로그를 따로 설계하지 않는 편이 좋습니다.

## 5. 오늘 바로 적용할 수 있는 순서

Anthropic 글은 수백 개의 task가 필요하다고 생각해 시작을 미루는 팀이 많지만, 실제 실패에서 뽑은 단순한 task 20~50개면 좋은 출발이라고 말합니다. 초기에는 변경 하나하나의 효과가 커서 작은 표본으로도 차이가 보이기 때문이라는 설명입니다. 그 조언을 순서로 풀면 이렇습니다.

1. 지금 수동으로 확인하는 것을 적습니다. 배포 전에 손으로 눌러 보는 시나리오, 버그 트래커와 상담 이관 기록에 쌓인 실패 사례가 첫 task 목록입니다. 해야 하는 경우와 하지 말아야 하는 경우를 함께 넣습니다.
2. 각 task의 outcome을 코드로 확인할 방법을 정합니다. DB 조회 한 줄, 파일 존재 여부, 테스트 통과처럼 답변 문장을 보지 않는 검사를 먼저 붙이고, 규정된 순서만 transcript 검사로 추가합니다.
3. trial마다 환경을 초기화하는 스크립트와 외부 API 대역을 만듭니다. 타임아웃과 오류 응답을 주입할 수 있게 합니다. 이것이 없으면 뒤의 숫자는 믿을 수 없습니다.
4. task마다 참조 해법을 한 번 돌려 모든 grader를 통과하는지 확인합니다. 통과하지 못하면 에이전트가 아니라 task와 grader부터 고칩니다.
5. 첫 실행 결과의 실패 transcript를 전부 읽고 에이전트, grader, task, 환경 중 어디의 실패인지 분류합니다. 그다음에야 capability와 regression을 나눈 통과율을 pass^k로 보고합니다.

## 마치며

에이전트 eval이 어려운 이유는 도구가 부족해서가 아니라 채점 대상이 바뀌었기 때문입니다.

문장 대신 상태를, 한 번 대신 여러 번을, 한 숫자 대신 두 종류의 suite를 보게 됩니다. 그리고 그 숫자를 믿기 전에 기록을 읽습니다.

처음부터 큰 체계를 만들 필요는 없습니다. 실제로 겪은 실패 스무 개와 DB를 확인하는 코드 몇 줄이면 시작할 수 있습니다.
